# 开播对决 设计文档（规则与数据格式的唯一标准）

版本 0.2 · 2026-10-15。现有代码（`UnityProject/Assets/StreamDuel/Core/`）已经实现了本文档第 1～6 节，测试见 `Engine.Tests/BattleTests.cs`。

## 0. 定位

**只做对战**：玩家对玩家（本机/局域网/以后的联网）和玩家对电脑。不做闯关、每日挑战、成就、教学关卡等单机养成内容（2026-10-15 用户确定）。

- 6 对 6 回合制对战，玩家对电脑（以后加联网对战）。玩法机制借鉴赛尔号的竞技对战，所有名字、文案、数值、美术为本项目自制。
- 非官方同人作品，免费、非商业、开源。主播名单是可替换的内容包（见第 7 节）。
- 设计核心：**每个效果都有明确的判定时机和驱散规则，并且显示给玩家看。** 同样的描述文字背后不允许藏着不同的时机。

## 1. 术语

| 术语 | 含义 | 代码里的名字 |
|---|---|---|
| 主播 | 一个战斗单位 | `StreamerDef` / 战斗中 `Fighter` |
| 人气 | 体力。降到 0 叫“下播” | `hp` |
| 互动 / 抗压 | 物攻 / 物防 | `atk` / `def` |
| 才艺 / 定力 | 特攻 / 特防 | `spa` / `sdef` |
| 反应 | 速度 | `spd` |
| 赛道 | 属性 | `type` |
| 人设 | 专属特质，每位主播 1 个，永久生效，不能被消除 | `PersonaDef` |
| 直播间效果 | 挂在主播身上的持续效果 | `FieldDef` / `FieldInst` |
| 第五技能 | 每位主播 4 个普通技能 + 1 个第五技能，规则上和普通技能相同，界面上单独标出 | `fifth` |

## 2. 一场对战

- 双方各 6 位主播，按 1～6 号位排列，开局各派 1 号位上场。
- 某方 6 位都下播即输；双方同时全灭为平局；打满 120 回合按剩余人气比例之和判定。
- 随机数只来自对战自带的 `Rng`（mulberry32，种子在开战时给定），同样的种子和同样的操作序列必须得到完全相同的日志。

**开局禁用**：用 `BattleOptions.BanOne = true` 启用时，先进入 `Phase.Ban`，双方看到对手原始六人阵容，各自调用 `ChooseBan(side, foeIndex)` 禁用对手一位。每方只能确认一次，双方都确认后才同时移除对应主播，其余顺序不变，重新编号为 1～5，改为五对五；原 1 号位被禁时原 2 号位成为首发。禁用不消耗回合，在“开场”节点写明双方禁用了谁；禁用期间不触发登场人设。若同时启用 `LeadPick`，禁用后进入 `Phase.Lead`，首发下标针对剩余五人；否则直接开场。后续人设按剩余号位判断，因此五人队伍没有 6 号位。电脑禁用对己方全队平均对位威胁最高的对手，同分时只使用对战的 `Rng`。

`BattleOptions` 还包含可选种子 `Seed` 和首发开关 `LeadPick`，旧构造函数保持默认不禁用的行为。命令行用 `--ban` 启用，支持手动选择及 `--auto` 自动禁用。回放保存禁用前的原始队伍、`banOne: true` 和按确认顺序的 `type: "ban"` 事件（`side`、原始对手下标 `to`、结算前 `rng` 状态）。可选 `names` 保存双方显示名以复现日志；旧记录缺省 `banOne` 时不禁用，缺省 `names` 时沿用“你/对手”。

**首发选择**：构造对战时可启用 `leadPick`，双方先看到彼此的完整阵容，在 `Phase.Lead` 各自调用 `ChooseLead(side, index)` 确认首发。两边确认后，将各自所选主播移到 1 号位，其余主播保持原有相对顺序，按剩余人数重新连续编号（未禁用时 1～6，禁用后 1～5）；按重排后的号位应用人设规则。随后在“开场”节点记录双方首发并触发登场人设，开始第 1 回合。选择首发不消耗回合，双方确认前不能结算行动或触发登场人设。电脑按对对手全队的平均对位分选择首发，同分时只用对战的 `Rng` 决定。`leadPick` 默认 false，保留原有直接派出 1 号位的行为。

回放记录保留禁用和重排前的原始队伍；启用首发时写入 `leadPick: true`，并按确认顺序保存 `type: "lead"` 的 `side`、`to`（首发阶段开始时的己方队伍下标；有禁用时为移除后的队伍）及结算前 `rng` 状态。回放先恢复相应禁用或首发阶段，再重放选择和后续行动；旧记录缺省 `leadPick` 时不选择首发。

新建对战的记录使用 `version: 2`，并在开局时将当前 `ContentDb.ContentHash()` 保存为 `contentHash`。读取缺省 `version` 的旧记录时按版本 1 处理；未提供指纹的旧记录仍可回放。提供了指纹的记录必须与当前内容指纹完全一致，否则 `Replay.Run` 在开始对战前抛出“内容不一致”错误，并显示记录和当前的指纹。内容包 id 仍须匹配。

### 2.1 回放分享码

`ShareCode.Encode(record)` 把对战记录转换为 `SD1-` 加无填充 base64url 文本。载荷先放 `BattleRecord.ToJson()` 的 UTF-8 字节经 Deflate 压缩后的数据，再放压缩数据的 32 位 FNV-1a 校验值（初值 2166136261、质数 16777619，按小端序追加 4 字节）。记录 JSON 的可读格式保持不变，版本、内容指纹、原始行动、禁用/首发、名字以及每个事件的随机流位置均保留。

`ShareCode.Decode(code)` 忽略 `char.IsWhiteSpace` 识别的全部空白，检查大小写敏感的 `SD1-` 前缀、无填充 base64url 字符与规范尾比特、载荷校验、Deflate、严格 UTF-8 和记录 JSON；无效输入统一抛出中文 `FormatException`。分享码只携带记录，接收方仍须有匹配的规则和内容包；回放继续经过 `Replay.Run` 的内容指纹与包 id 校验。FNV 校验用于发现复制或传输损坏，不提供身份认证。

为限制外部分享码的内存占用，原始 JSON 最多 1 MiB（1,048,576 个 UTF-8 字节），压缩数据最多 1,049,600 字节，去空白后的完整分享码最多 1,399,476 字符；编码与解码均检查上限。解压时逐块限制输出大小，并拒绝提前结束或尾随数据的压缩流。普通完整对局的目标长度小于 1,500 字符，不截断或丢弃事件来缩短分享码；自定义长名字或异常大的记录不保证这一短码长度。

命令行 `--share` 在完成对局后输出分享码，联网对局仍须先完成双方终局校验。分享导出失败单独报告并使退出码为 1，不阻止已完成对局保存原始回放和档案。`--replay-code <码>` 使用与文件回放相同的加载、播放和战报流程，不新增档案战绩或回放文件；与 `--replay`、联网选项及 `--hash` 互斥。回放完整播放后也可用 `--share` 导出原记录，提前退出不输出。回放的战报与分享分别导出；一项导出失败仍尝试另一项，最终退出码为 1。

## 3. 一个回合

### 3.1 选择行动

双方同时选择，选项有：

| 行动 | 说明 |
|---|---|
| 使用技能 `Skill(i)` | i = 0..4，4 是第五技能。PP 为 0 的技能不能用（人设“团魂”例外，见 6.2） |
| 换人 `SwitchTo(j)` | 换成后排第 j 位（未下播、不是场上的）。换人占用这一回合 |
| 跳过 `Pass` | 只在被控制或无事可做时由界面提供 |

服务器（`Battle.Normalize`）会把非法选择纠正：被控制 → `PassControlled`；所有技能都没 PP → `Struggle`（硬撑：互动、威力 40、反噬造成伤害的 1/4）；其它非法 → `Pass`。**被控制时仍然可以换人，但「锁麦」等禁止主动换人的直播间效果仍然生效。**

### 3.2 结算顺序（节点）

每一回合严格按下面的顺序。日志每一行都带节点名。

| 顺序 | 节点 | 发生什么 |
|---|---|---|
| 1 | 换人 | 所有换人先执行（按双方当前反应高低排序）。下场者清空能力等级和所有直播间效果，状态保留；上场者触发“登场”类人设 |
| 2 | 回合开始 | 触发“回合开始”类人设 |
| 3 | 先手行动 | 先手方行动（见 3.3） |
| 4 | 后手行动 | 后手方行动；如果此时它已下播则不行动 |
| 5 | 回合结束 | 按反应顺序，对双方场上主播依次结算：弱化类状态 → 直播间效果 → 人设 |
| 6 | 补位 | 回合数 +1；场上主播已下播的一方选择补位，补位的主播触发“登场”类人设 |

任意时刻有一方全灭，立即结束，后面的步骤不再执行。

### 3.3 谁先手

1. 先制高者先手。实际先制 = 技能先制 + 身上直播间效果的先制修正 + 人设修正。
2. 先制相同，反应（含能力等级）高者先手。
3. 都相同，随机。
只有一方行动（另一方换人）时，那一方的行动算“先手行动”节点。日志里写明判定理由，例如“先制都是 0，反应 360 对 300”。

### 3.4 一次行动内部

```
被控制？→ 跳过次数 -1，用完则解除并获得「重连保护」2 回合 → 结束
使用普通或第五技能时重新检查 PP：已为 0 且不满足人设免扣条件 → 记录“PP 已耗尽，行动失败” → 结束
扣 PP（或人设免扣）
命中判定（命中率 < 100 时掷骰）→ 未命中 → 结束
命中前判定：按顺序执行技能里 at = "pre" 的效果
伤害结算（威力 > 0 时）
  → 受到对手直接技能伤害后的反弹（见 5.2）；行动方下播则停止其余效果
  → 被击中方的“被击中后”人设
命中后判定：按顺序执行技能里 at = "post" 的效果
技能结算中行动者下播 → 记录“下播，技能中断”，跳过余下伤害和全部未结算效果
```

行动前 PP 检查不会改变回合开始的 `Normalize`：技能在选择时合法、行动前被削到 0 时，本次行动失败，不改用硬撑、不扣 PP、不更新最后使用技能记录；「团魂」满足免扣条件时仍可使用 0 PP 技能。若回合开始已经全部无 PP，仍由 `Normalize` 改为硬撑。

自伤、反噬、命中前效果或反弹导致行动者在技能结算中下播时，都立即中断这次技能，不再执行后续伤害或效果。中断日志记在该行动节点；若没有一方全灭，照常完成其余回合流程并进入补位。若因此全灭，保留立即结束规则，结束节点在中断日志之后。

**命中前和命中后读到的数值不同。** 例：「高音破麦」（命中前）和「电流麦」（命中后）都写“若对手人气高于 50%，40% 使对手卡麦”。对手在 55% 时被打到 40%：前者判定通过，后者不通过。测试 `PreHitConditionReadsHpBeforeDamage` / `PostHitConditionReadsHpAfterDamage` 锁定了这一点。

### 3.5 伤害公式

```
基础 = 50 × 威力 × A / D / 50 + 2        （A、D 为含能力等级的数值）
互动类：A = 互动，D = 抗压；才艺类：A = 才艺，D = 定力
倍率 = 本赛道加成(同赛道 1.5) × 克制倍率 × 状态修正 × 人设(攻) × 直播间效果(攻) × 直播间效果(受) × 人设(受) × 暴击(1/16 概率 ×1.5)
伤害 = max(1, floor(基础 × 倍率 × 随机(0.85..1.0)))
威力 = 技能威力 × 命中前判定里的威力倍率（POWER_MUL、POWER_PER_MARK）
```

### 3.6 能力等级

五项能力（互动、抗压、才艺、定力、反应）各有等级 -6..+6。倍率：等级 n ≥ 0 时 (2+n)/2，n < 0 时 2/(2-n)。下场清零。

## 4. 赛道

8 条：歌回、游戏、杂谈、绘画、整活、助眠、恐怖、硬核。克制表在 `StreamDuelRules.json` 的 `chart`：`攻击方 → 防守方 → 倍率`，没写的为 1。每条赛道克制 2 条（×2），被 1 条克（自身 ×0.5），对同赛道 ×0.5。

主播可在内容包中通过可选的 `type2` 字段指定第二赛道；省略或为 `null` 时仍是单赛道。第二赛道必须存在于赛道表，且不能与主赛道 `type` 相同。界面和名单按主赛道/第二赛道显示，例如“歌回/杂谈”。现有主播不添加第二赛道。

对双赛道主播造成技能伤害时，克制倍率为该技能对两个防守赛道的倍率之积；例如两次克制为 ×4，两次被克为 ×0.25，一次克制和一次被克为 ×1。同赛道加成在技能赛道等于攻击方任一赛道时生效，仍为 ×1.5，且只计算一次。技能本身仍只有一个赛道；固定伤害不受赛道倍率影响。伤害预览和电脑对手的对位判断遵循同一规则。

## 5. 状态与直播间效果

### 5.1 状态

| 分类 | 例子 | 计数 | 效果 | 能否净化 |
|---|---|---|---|---|
| 控制类 `control` | 卡麦(1)、掉线(2)、挂机(3，受到伤害即解除) | 跳过几次**行动**，在被控制者自己的行动时扣减 | 不能用技能，可以换人 | 不能，只能等它结束 |
| 弱化类 `weak` | 炎上（每回合 -1/12，互动伤害 ×0.7）、黑粉缠身（-1/8）、被引流（-1/10，对手回复同量） | 回合数，在回合结束扣减 | 回合结束结算 | 能（CLEANSE、人设“纯净人设”） |

规则：
- 同时最多 1 个控制类状态；已有控制时再施加无效。
- 身上有「重连保护」时控制类无效。
- 同一弱化类状态再次施加时刷新回合数，不叠加。
- 身上有 `immuneWeak = true` 的直播间效果（如「防火墙」）时，施加或刷新弱化类状态会被挡下并写日志；不移除已有弱化，也不阻止控制类状态。
- 状态跟着主播走，下场不清除；后排主播的状态不结算。

### 5.2 直播间效果

挂在场上主播身上，下场时全部清除。每个效果有 `kind`：

| kind | 名称 | 消回合（DISPEL_TURNS） | 例子 |
|---|---|---|---|
| `turn` | 回合类 | **能**清除 | 房管护盘、美颜滤镜、抢先开播、网络延迟、舰长续费、憋大招、镜面回击、防火墙、锁麦 |
| `mark` | 印记 | 不能 | 热度（可叠层）、黑历史 |
| `protect` | 保护类 | 不能 | 重连保护 |

`dispel` 字段是最终依据（`turn` 的都为 true，其余为 false）。持续回合在回合结束扣减；`turns = -1` 表示直到下场。

| 效果 id | 名称 | 判定时机与作用 | 新技能施加回合 | 消除规则 |
|---|---|---|---|---|
| `mirror` | 镜面回击 | 只反弹对手技能的直接伤害（含固定伤害）：本次实际扣除人气 × 0.3，向下取整且至少 1，日志记在攻击方；持续伤害、反噬、自伤和状态结算伤害一律不反弹 | 3 | 回合类，可被消回合，下场清空 |
| `firewall` | 防火墙 | 被施加弱化类状态时，阻止施加或刷新；不净化已有弱化、不阻止控制 | 3 | 回合类，可被消回合，下场清空 |
| `lockin` | 锁麦 | 选择行动时禁止主动换人；该效果施加到对手，击倒后的补位不受影响 | 2 | 回合类，可被消回合，下场清空 |

这些能力由 `FieldDef` 的可选数据字段 `reflectDamage`（反弹比例，默认 0）、`immuneWeak`、`preventSwitch`（默认 false）决定，不依赖效果 id。施加时机仍由技能效果的 `at` 决定；持续时间采用该 `FIELD` 效果的 `turns`，并遵守当回合结束即扣减的通用规则。

反弹不会再次触发反弹，不受伤害倍率影响，不触发被反弹者的人设（包括因此下播时的人设）；其造成的伤害仍会解除挂机。反弹使行动方下播时，该行动余下的效果不再执行。原攻击先导致一方全灭时，依照 3.2 立即结束，不再反弹。没有攻击方的持续伤害、自身反噬和以自身为目标的固定伤害不进入反弹入口。

### 5.3 两种驱散

| 代码 | 名称 | 清除 | 不清除 |
|---|---|---|---|
| `DISPEL_TURNS` | 消回合 | 对手所有 `dispel = true` 的直播间效果 | 印记、保护类、能力等级 |
| `DISPEL_BOOST` | 消强化 | 对手所有 **> 0** 的能力等级归零 | 下降的等级、所有直播间效果 |

日志写清清掉了什么、保留了什么。

### 5.4 印记与层数

印记效果可带 `maxStacks`。`ADD_MARK` 加层（上限截断），`POWER_PER_MARK` 在命中前按层数加威力，`consume: true` 时用后清空。

## 6. 数据格式

### 6.1 技能 `skills.<id>`

```json
{
  "name": "高音破麦", "type": "song", "cat": "talent",
  "power": 80, "pp": 15, "acc": 100, "prio": 0,
  "effects": [
    { "at": "pre", "code": "STATUS", "chance": 40, "target": "foe", "status": "stall",
      "cond": { "kind": "foeHpAbove", "value": 0.5 } }
  ]
}
```

- `cat`：`interact` 互动 / `talent` 才艺 / `status` 状态（威力 0）。
- `acc` 默认 100，`prio` 默认 0。
- 效果按数组顺序执行。`chance` 默认 100。条件不满足时不再掷概率。

**效果码表**

| code | 参数 | 作用 |
|---|---|---|
| `STATUS` | target, status | 施加状态（遵守 5.1 的规则） |
| `STAGE` | target, changes{stat:n} | 改能力等级 |
| `HEAL` | frac | 自身回复最大人气 × frac |
| `RECOIL` | frac | 自身受到本次造成伤害 × frac（至少 1） |
| `DRAIN` | frac | 自身回复本次造成伤害 × frac |
| `PP_REDUCE` | n, target | 在指定 pre/post 时机使目标本次上场最后使用的技能 PP 减 n，最低为 0；还没有用过技能则无效。未命中、免扣 PP 的技能也计入；硬撑和受控跳过不计，下场清空记录。即时结算，不可驱散 |
| `FIXED_DAMAGE` | n, target | 在指定 pre/post 时机对目标造成固定 n 点伤害，人气最低为 0；不受能力、赛道、直播间效果、人设或暴击影响，可解除挂机并导致下播，但不触发被击中后人设。即时结算，不可驱散 |
| `FIELD` | target, field, turns | 获得/刷新直播间效果 |
| `ADD_MARK` | target, field, n | 印记加层 |
| `POWER_MUL` | mul | 本次威力 × mul（只能放在 pre） |
| `POWER_PER_MARK` | field, per, consume | 威力 × (1 + per × 层数)（只能放在 pre） |
| `DISPEL_TURNS` | target | 消回合 |
| `DISPEL_BOOST` | target | 消强化 |
| `STEAL_BOOST` | target | 在指定 pre/post 时机取走目标所有 > 0 的能力等级，加到自身对应等级（每项最高 +6），目标这些等级归零；目标负等级保留。转移后自身正等级可被消强化、下场清零；以自身为目标时无效。日志列明双方等级变化 |
| `CLEANSE` | — | 净化自身弱化类状态 |

**条件 `cond.kind`**：`foeHpAbove`(value)、`foeWeak`、`actedFirst`、`actedSecond`、`foeBuffed`。在效果自己的 `at` 时机读取当时的数值。

### 6.2 人设 `personas.<id>`

```json
{ "name": "准点开播", "code": "T_FIRST_TURN_PRIO", "node": "排行动顺序时", "params": { "prio": 1 }, "desc": "…" }
```

`node` 只给界面显示；真正的调用时机由 `code` 决定：

| code | 调用时机 | 参数 | 作用 |
|---|---|---|---|
| `T_LOWHP_POWER` | 本方造成伤害时 | below, mul | 自身人气低于 below 时伤害 × mul |
| `T_EXECUTE` | 本方造成伤害时 | below, mul | 对手人气低于 below 时伤害 × mul |
| `T_REGEN` | 回合结束 | frac | 回复最大人气 × frac |
| `T_BENCH_GUARD` | 受到伤害时 | per | 己方后排每有 1 位在播，受伤 -per |
| `T_INTERACT_REDUCE` | 受到伤害时 | mul | 受到互动伤害 × mul |
| `T_FIRST_TURN_PRIO` | 排先手时 | prio | 上场后第一个回合先制 + prio |
| `T_TURNSTART_CLEANSE` | 回合开始 | — | 移除自身 1 个弱化类状态 |
| `T_FREE_PP_SLOT6` | 使用技能时 | — | 己方 6 号位队友在播（且不是自己）时不扣 PP |
| `T_CONTACT_STATUS` | 被击中后 | chance；人设的 `status` 字段 | 被互动技能击中后按概率给攻击方施加状态 |
| `T_ENTER_FIELD` | 登场时 | turns；人设的 `field` 字段 | 登场获得直播间效果（按那个效果自己的驱散规则） |
| `T_FAINT_CURSE` | 下播时 | n | 对手场上主播五项能力各 + n（n 为负） |
| `T_SPEED_IF_FIRST` | 回合结束 | n | 本回合先手则反应 + n |
| `T_KO_HEAL` | 本方技能直接击倒对手后 | frac | 本方普通或固定技能伤害击倒对手后，自身回复 floor(最大人气 × frac)，不超过上限；对战已经结束则不再触发 |
| `T_FIRST_CONTROL_IMMUNE` | 被施加控制类状态时 | — | 每次登场后，第一次本来可施加的控制类状态无效；下场再登场时重新计算。重连保护或已有控制已经使施加无效时，不消耗本次免疫 |
| `T_ENDURE` | 受到伤害时 | — | 每场对战一次：受到会使人气归零的伤害时，保留 1 点人气；下场不重置，反弹伤害不触发 |
| `T_ALLY_PP_ON_ENTER` | 登场时 | n | 己方后排所有还在播的队友，每个技能 PP +n，不超过各技能上限；不回复自身或已下播队友 |
| `T_STAGE_ON_HIT` | 受到普通技能直接伤害后 | 能力名 → 提升等级，例如 `{"def": 1}` | 实际扣除人气且没有下播时，按参数中的正值提升自身能力等级（最高 +6），每次被击中均触发；固定伤害、持续伤害、反噬和反弹不触发 |

“上场后第一个回合”：开局上场 = 第 1 回合；回合中换人上场 = 下一回合；补位上场 = 补位后的那个回合。

人设本体永久生效、不可消除；`T_KO_HEAL` 的人气回复和 `T_ALLY_PP_ON_ENTER` 的 PP 回复即时结算；`T_STAGE_ON_HIT` 产生的能力提升仍可被消强化，下场清零。被击中后的人设遵守 3.4：反弹使行动方下播后，不再执行后续的被击中后人设。`T_ENDURE` 的一次性保命属于人气下限规则，不改变固定伤害的数值计算；它可以响应普通、固定、持续伤害和自身反噬，但依照 5.2 不响应反弹。`T_KO_HEAL` 不因持续伤害、自身反噬或反弹归因触发，且遵守 3.2 的全灭后立即结束规则。

界面可调用 `Describe.Persona(db, persona)` 获取触发时机、说明和消除规则。上述 5 个新人设按代码和参数生成说明；已有代码保留其 `node`、`desc`，兼容内容包中的自定义文案。

```json
{
  "id": "fan_holo_niji", "name": "同人包：…", "notice": "非官方同人作品…",
  "skills": {}, "personas": {}, "fields": {}, "statuses": {},
  "skillNames":  { "<skillId>": "新显示名" },
  "fieldNames":  { "<fieldId>": "新显示名" },
  "statusNames": { "<statusId>": "新显示名" },
  "streamers": [
    { "id": "suisei", "name": "星街彗星", "org": "hololive", "type": "song",
      "stats": { "hp": 340, "atk": 220, "def": 220, "spa": 340, "sdef": 230, "spd": 360 },
      "persona": "punctual", "personaName": "彗星登场", "personaDesc": "…", "personaStatus": null,
      "skills": ["warm_up", "full_volume", "go_live_early", "noise_cancel"], "fifth": "high_note",
      "blurb": "…" }

```

- 改名只改显示，不改机制。`personaName/personaDesc/personaStatus` 会复制出一份只属于这位主播的人设。
- 每包至少 6 位主播（不足 12 位时，电脑队伍先用玩家没选的，再从玩家选的里补，允许双方出现同一位主播）；每位正好 4 个普通技能 + 1 个第五技能。
- 读取时 `ContentDb.Validate()` 检查所有引用，错误信息要指出是哪一条。

内容包可选的 `skills`、`personas`、`fields`、`statuses` 对象用于新增本包定义；省略或写成 `{}` 时不增加定义。每个对象都以 id 为键，值的格式、默认值和含义与 `StreamDuelRules.json` 中的同名对象完全一致：技能见 6.1，人设见 6.2，状态和直播间效果见第 5 节。例如以下四个对象可放在内容包顶层：

```json
{
  "skills": {
    "pk_signature": {
      "name": "聚光开场", "type": "song", "cat": "talent", "power": 80, "pp": 5,
      "effects": [
        { "at": "post", "code": "FIELD", "target": "self", "field": "pk_glow", "turns": 2 },
        { "at": "post", "code": "STATUS", "target": "foe", "status": "pk_pause", "chance": 20 }
      ]
    }
  },
  "personas": {
    "pk_opening": {
      "name": "登场光环", "code": "T_ENTER_FIELD", "node": "登场时",
      "field": "pk_glow", "params": { "turns": 2 }, "desc": "登场时获得 2 回合聚光保护。"
    }
  },
  "fields": {
    "pk_glow": {
      "name": "聚光保护", "kind": "turn", "when": "受到伤害时", "dispel": true,
      "dmgTakenMul": 0.9, "desc": "受到的伤害乘以 0.9；可被消回合，下场清除。"
    }
  },
  "statuses": {
    "pk_pause": {
      "name": "短暂静音", "cat": "control", "skip": 1, "cleanse": false,
      "desc": "跳过下 1 次行动；不能净化。"
    }
  }
}
```

- 每次读取都先建立独立的 `ContentDb`，载入共用规则，再合并本包四类定义。同类别的 id 与共用规则已有 id 重复时抛出 `KeyError`，错误写明类别和重复 id；不会覆盖共用定义，也不会影响其他包的 `ContentDb`。
- 四类定义全部合并后，才处理 `skillNames/fieldNames/statusNames` 改名、主播的技能和人设绑定，以及 `personaName/personaDesc/personaStatus` 人设复制。因此包内技能和人设可以引用同包新增的状态或直播间效果，改名表也可以引用本包新增 id。
- 完成合并、改名和绑定后统一调用公开的 `ContentDb.Validate()`；所有技能引用的赛道、状态、直播间效果及人设引用的状态、直播间效果必须存在，每个技能效果必须有 `at: "pre"` 或 `at: "post"`。新增定义仍须使用引擎已支持的效果码和人设码。
- `Tools/PackCheck` 对合并后的全部技能检查未使用提醒；生成名单时，在本包定义的技能和人设名称旁标注 `〔本包独有〕`。复制本包人设保留该标记，仅改名或复制共用定义不添加标记。

内容包还可以提供可选的赛季规则；未提供时 `ContentDb.Seasons` 为空：

```json
"seasons": { "s1": { "name": "第一赛季", "banned": ["kei"], "limited": [ { "max": 1, "ids": ["bell", "bee"] } ] } }
```

- `banned` 是禁用主播 id 列表；`limited` 的每个池子各自限制其 `ids` 中最多选择 `max` 位主播。读取内容包时校验这些 id，引用不存在的主播会抛出 `KeyError`，指出赛季和 id。
- `TeamCheck.Validate(db, seasonId, team)` 返回中文错误列表：队伍必须正好 6 位、不重复、主播均存在，并遵守赛季的禁用池与所有限制池。已知主播用显示名报错，限制池错误说明池子成员和上限。
- `seasonId` 为 `null` 时只检查人数、重复和主播存在性；未知赛季返回一条错误。该检查供组队界面调用。

`BattleStage` 仅提供具名显示节点：双方 `fighter-0` / `fighter-1`，各含 `portrait`、`hp-bar`、`status-row`；覆盖层 `fx-layer` / `float-layer` 与 `field-banner`。动画、技能特效、状态图标、头像分别通过 `IBattleAnimator`、`IFxPlayer`、`IStatusIconProvider`、`IPortraitProvider` 替换；当前默认实现为空动画、空特效、文字图标及按赛道颜色生成的纯色头像，不推导战斗规则。Input System 使用编辑器推荐的 1.20.1，迁移期间以 Both 保留旧 IMGUI 的运行时输入，T-67 移除旧画面后再切为 New。

`BattleViewModel.From(battle, viewerSide)` 提供当前时点的独立显示快照，不持有战斗或内容定义对象，也不改变状态、日志、回放或随机数。双方顺序与 Battle 相同；技能和可换人下标取查看方的 `LegalFor`，伤害范围取 `PreviewDamage`，不在画面重复计算规则。`Pct` 沿用 Fighter 的整数百分比；禁用后的队伍保留实际五人。状态芯片同时列出状态与直播间效果的类别、剩余次数或回合、层数及消除规则。`NodeStrip` 按开场、换人、回合开始、先手行动、后手行动、回合结束、补位、结束排列，仅标记 `battle.Turn` 的日志内容；历史逐行回放继续使用日志中的快照。

画面通过只读的 `Battle.Events` 播放动画，每条结构化事件以 `LogIndex` 对应原日志，并保留相同的回合和节点；同一日志可以对应多个事件，事件按实际发生顺序排列。事件中的 `Side` 和从 0 开始的 `Slot` 定位主播，`Id` 标识技能、状态、直播间效果或能力，`Amount` 记录实际变化：伤害与回复为正值，PP 与能力等级增减带符号。状态、效果的添加与移除也由引擎直接发出事件，界面无需解析日志文字；事件列表随 `Battle.Clone()` 独立复制，不参与状态哈希，也不消耗随机数。

### 8.1 文本与语言

`Core/Loc.cs` 提供独立文本表，JSON 格式为 `{"language":"zh-CN","texts":{"key":"文本 {0}"}}`。键名使用小写英文和点分层；中文原表位于 `Resources/Locale/zh-CN.json`。`Loc.FromJson(json, fallback)` 要求非空语言标识与字符串文本对象，创建时可指定回退文本表；`T(key, args)` 先查本表，再查 fallback，均不存在时返回 `[key]`。命中文本以 `CultureInfo.InvariantCulture` 调用 `string.Format`；`Has(key)` 包含回退表。无效格式占位符会抛异常，不静默吞掉翻译错误。

`Loc.Current` 可由调用方注入。测试和命令行工具可用 `Loc.Current = Loc.FromJson(File.ReadAllText(path))`；Unity 可用 `Loc.Current = Loc.FromJson(Resources.Load<TextAsset>("Locale/zh-CN").text)`。Core 不引用 Unity，也不会自行查找文件或读取资源。未注入或把 Current 设为 null 时，首次使用按需解析编译进 `Loc.ZhCn.cs` 的同一份中文 JSON；资源表与编译常量有一致性测试，修改文本时需同步更新两处。

当前迁移范围为 `TeamCheck` 的全部错误、`Describe` 的代码说明文字和 `PackLoader` 自身的错误模板。调用统一写为 `Loc.T("xxx.yyy", ...)`，这三个类中的 Loc 属性指向当前文本表；`Loc` 类本身保留实例查询 API，允许同时持有多份语言及回退表。内容包中的技能名、人设名和文案仍使用内容数据；底层校验器返回的错误原因也保持原样。Battle 日志尚未迁移，中文表的现有展示输出保持不变。

语言切换由调用方在显示或读取前设置 Current；这是全局显示配置，不参与规则、随机数、内容指纹或对战状态哈希。本次不增加语言选择界面，也不引入其它语言译文。

`Glossary.Build(db)` 根据当前合并后的内容库建立规则说明快照，按赛道、状态、直播间效果、人设、通用规则分组。内容条目在组内按内部 id 稳定排列，通用规则采用固定顺序。条目的 `Id` 和 `Category` 供程序定位；界面展示 `Title`、`Text` 和已翻译的 `Tags`，不把内部代码直接展示给玩家。控制状态用行动次数，弱化状态用回合数；直播间效果的持续时间由赋予它的技能或人设决定，说明不替它虚构统一时长。人设复用 `Describe`，旧机制的参数和关联名称在说明条目中从当前定义生成，避免包内改名后沿用旧描述。通用规则描述默认对战，并区分已启用修饰器时的例外；它不是当前战斗的实时状态。

`Glossary.Search(all, keyword)` 仅查询标题和正文，忽略大小写并去掉关键词两端空白；空关键词返回全部条目的新列表，顺序不变。重建快照才能反映后续内容或语言变更，不修改内容定义、战斗或随机数。命令行 `--glossary [关键字]` 提供同一查询，只与内容包选择参数同用，不启动对局或写入存档。

### 8.2 本地设置与存档

`FileSaveStore` 在调用方指定的本机根目录保存设置、档案和回放，不上传数据。设置缺失或 JSON 损坏时使用默认值，旧版本补齐字段并升级为当前版本。命令行沿用 `--save-dir`，Unity 使用 `Application.persistentDataPath`，首次缺少设置文件时迁移原 PlayerPrefs；冒烟验收只使用内存设置，不读写玩家设置存档。正常设置读写失败时保留本次内存选择并显示提示；读取失败后不自动写回默认值覆盖原文件。

回放名称只允许 ASCII 字母、数字、下划线和连字符，并拒绝系统设备名。管理范围包括旧自动命名回放、可解析的自定义名称对战记录，以及通过 `SaveReplay` 保存并由隐藏索引登记内容摘要的其它载荷；未登记且不是对战记录的外来 JSON 不参与清理。所有管理的回放按修改时间倒序排列，合计最多保留 50 份；覆盖保存成为最新一份。索引损坏或内容摘要不匹配不能作为删除外来文件的依据。暂时不可读且无法确认的文件不列出或删除，已有摘要登记保留，解锁后的下次保存重新纳入清理。

写入采用独占锁和临时文件替换，累计档案持锁完成读改写。新回放已经写入但索引更新或旧回放清理失败时，报告 `ReplayRetentionException`，保留新文件并继续记录本局战绩。路径检查拒绝越界及重解析点；战报输出不能覆盖设置或回放管理索引及其临时路径。文件命名与保留顺序使用的时间不参与战斗结算。

### 8.3 画面动画时间线

`BattleTimeline.Build(events, from, to, speed)` 把 `Battle.Events` 的半开区间 `[from, to)` 转换为纯 C# 的 `AnimCue` 列表，子区间从 0 秒开始。`EventIndex` 保留事件在原列表中的绝对下标，`LogIndex` 保留原日志下标；`Side`、`Slot`、`Id`、`Amount` 用于定位提示及显示引擎已经结算的变化，不在画面重算规则。返回列表和每个提示都是独立对象，不持有输入事件引用。

以下时长以秒计，均为 1 倍速；同一事件内未注明先后的提示同时开始：

| 战斗事件 | 动画提示与时长 | 跳字或参数 |
|---|---|---|
| Act | Cast 0.35，结束后 Projectile 0.25 | 均定位施放者，Id 为技能 id |
| Damage | Hit 0.2、Flash 0.12、FloatText 0.8、HpBar 0.4 | `-数值`，Style 为 `damage`，定位实际受击者 |
| Crit | FloatText 0.8 | `暴击`，Style 为 `crit`；保留事件的施放者定位 |
| Miss | Miss 0.3、FloatText 0.8 | `未命中`，Style 为 `miss` |
| Heal | FloatText 0.8、HpBar 0.4 | `+数值`，Style 为 `heal` |
| Faint | Faint 0.5 | 定位下播者 |
| Switch | SwitchOut 0.3，结束后 SwitchIn 0.35 | 离场者与新登场者的定位见下文 |
| Enter | Enter 0.4 | 定位登场者 |
| StatusAdd / StatusRemove | StatusIcon 0.3 | Style 为 `status`；Amount 为剩余次数或回合，移除时为 0 |
| FieldAdd / FieldRemove | FieldBanner 0.6 | Style 为 `status`；添加保留原 Amount（回合、-1 或印记增量），移除时为 0 |
| StageChange | FloatText 0.8 | 如 `互动 +1`、`抗压 -1`；Style 为 `stage-up` / `stage-down` |
| End | End 0 | 保留胜方 Side，平局为 -1 |
| PpChange / Info | 无 | 不占用动画时间 |

同一事件的提示共用 EventIndex，下一事件在上一事件全部提示结束后开始；同 LogIndex 不代表同时播放。唯一并行例外是输入中紧邻的 Crit 和 Damage：二者同时开始，后一事件在两者全部提示结束后开始；各自保留独立的事件、日志与目标定位。独立 Crit 正常占用 0.8 秒。区间外的 Damage 不与区间内 Crit 配对。

Switch 事件只标识离场者。SwitchIn 在当前区间内跳过不生成提示的 Info/PpChange 后，如果下一条可见事件是同 Side、Turn、Node 的 Enter，采用该 Enter 的 Slot 和 Id；其 EventIndex 和 LogIndex 仍属于 Switch。找不到或范围已截断时，保留 Side，以 Slot=-1、Id=null 表示尚未确定新主播，播放器不可据此显示旧主播重新入场。后续 Enter 仍独立生成 Enter 提示，不吞并事件。

`speed` 是有限数值倍速：所有 Start、Duration 除以正倍速；小于等于 0 时保留全部提示与元数据，把 Start、Duration 全部置 0，以便直接呈现终态。NaN、无穷倍速、换算后开始时间或时长（含结束时间）溢出的极小正倍速、非法范围、范围内空事件及未知事件类型报参数错误。空区间或只有不生成提示的事件返回空列表。`TotalDuration(cues)` 返回全部 `Start + Duration` 的最大值，空列表为 0，不要求调用方列表已排序。

跳字、能力名和错误文字通过 `Loc` 的 `timeline.*` 键取得，中文原表与 Core 内置表同步。能力名为互动、抗压、才艺、定力、反应；未知能力显示“能力”。Build 在开始时读取一次当前文本表；相同事件、范围、倍速和文本表得到相同结果，不读取系统时间、不使用随机数，也不改写 Battle、事件或日志。Unity 播放器由后续画面任务实现。

### 8.4 战后关键回合

`BattleReview.KeyMoments(battle, viewerSide, max = 5)` 只读取日志、每行事后人气快照与结构化事件，不读取当前队伍或重新模拟规则，不消耗随机数。返回 `KeyMoment` 的回合、类别、经 `Loc` 格式化的文字及有符号 `Swing`；正数表示查看方人气差改善，负数表示恶化。非法查看方抛参数异常，非正的 `max` 返回空列表。

复盘采用以下展示口径，不改变对战规则：

- **人气差与评分**：将双方全队剩余人气分别求和，取查看方减对方。每回合净变化以该回合之前的最后快照为基线、该回合最后快照为终点；历史的首张快照只作基线。`ko`、`control`、`switch` 都使用所在回合的净变化作为 `Swing`。计和使用长整数，输出分数超出 int 时截到边界。
- **ko**：每次 `Faint` 提示谁下播及该时刻双方在播人数。事件没有伤害来源字段，因此不推断谁击倒谁，也不把反噬、反弹或持续伤害归因于最近出招者。
- **swing**：只选全局绝对净变化最大的非零回合，相等选最早回合；文字给出变化前后的人气差。
- **control**：同一方、同一号位曾有成功的控制类 `StatusAdd`，且行动节点实际记录“无法行动”或“刚回过神来，本回合来不及行动”，才记一次行动损失。免疫、仅施加状态、未轮到行动就下播或换下均不足以形成提示。
- **switch**：只跟踪主动换人的 `Switch`→`Enter`，不把补位当主动换人。观察新人这次在场期间的真实普通伤害：受到明确“赛道被克”的攻击，或作为出招者打出明确“赛道克制”。每次入场的每个方向最多提示一次，允许收益出现在后续回合；再次换人或下播立即停止该次跟踪。固定伤害、反弹、未命中和仅预览不算克制收益。
- **comeback**：从 `End` 确认查看方最终获胜后，取其首次在回合末全队剩余人气不超过对方一半（对方大于零）的回合作为落后记录的起点；`Swing` 为该起点到终局的人气差改善。此提示只说明历史落后后获胜，不声称某个操作造成逆转。未结束、平局及查看方落败不生成此类提示。

先按 `abs(Swing)` 降序选前 `max` 条，同分按回合、日志顺序稳定选择，再按回合与日志顺序输出。相同回合允许多种事实并列。控制行动损失和克制标记目前依赖引擎的既有中文日志格式；以后迁移这些日志时须同步此识别器，不能用当前属性补算历史。人名和状态名来自历史文本，其余复盘模板均在语言表。

命令行完成对战时打印复盘，联网客机使用自己的查看方；完整回放默认查看 0 方并标明视角。Markdown 战报末尾追加“关键回合”，默认 0 方，也可用 `Markdown(battle, viewerSide)` 指定视角；未结束的战报显示尚未结束，所有新增文字沿用 Markdown 转义。

### 8.5 对战解说

`Commentary.For(battle, fromEvent, toEvent)` 返回半开区间内的 `CommentLine`（绝对 `EventIndex`、`Text`、`Priority`）。它读取当前完整事件历史，按事件的 `Turn` 每回合先选优先级最高的两条，再过滤请求区间并按事件顺序返回；同分保留较早事件。因此对同一完整历史分段查询与一次查询一致，不会因切片重新获得两条额度。尚未结束的回合继续产生事件时，较高优先级事件可能替换先前候选；持续播放的调用方应在该回合结束后输出。CLI 的普通对战、联网与回放均采用此边界，回放还受当前展示页的回合上界约束。

优先级由高到低为：胜利/平局 120、开场 110、残血反杀 100、连续击倒 95、下播 90、最后一位上场 80、暴击 70、未命中 65、控制成功 60、解除控制 55、获得/刷新直播间效果 40、换人上场 30、赛道克制/被克制对位 20。开场仅在首次实际首发登场时提示，禁用或首发选择等待期间不提前提示。一次下播只产生反杀、连续击倒或普通下播中的一种候选。

解说中的残血指该次击倒快照中施放者仍存活且人气不超过本局上限的四分之一；连续击倒指同一主播本次在场直接技能击倒至少两位，下场或下播后重新计数。归因要求同回合、同节点的技能行动与伤害事件相符、受击方与施放方不同；持续伤害、反弹与自伤只提示普通下播。最后一位上场按登场日志快照中的实际存活人数判断，不读取终局状态推断历史。赛道对位在有威力技能的 `Act` 事件处读取当时目标与 `TypeMul`，文案只说明对位关系，不宣称命中或把固定伤害套入赛道倍率。以上均为展示分类，不改变战斗结算。

中文表的 `comment.*` 提供 15 类、每类 3 条原创模板，以绝对事件下标取模选择。参数依次为主播或胜方名、技能/状态/效果名、数值、目标名；当前文案不需要数值参数。同人包沿用相同模板，只替换内容定义的名称。资源表与 `Loc.ZhCn.cs` 同步；相同事件历史、快照、内容与语言产生相同结果，不读取时间、不调用随机数，也不改写状态、事件、日志、回放或内容。

## 9. 电脑对手（`Ai.cs`）

估算每个可用技能的价值：伤害技能按“估算伤害 / 对手当前人气”，能击倒加大权重，先手击倒再加；状态、能力、直播间效果、驱散、净化按局面给固定加分；加 0~0.08 随机扰动。威胁大且自己选项都差时，60% 概率换到对位更好的队友。补位选对位分最高的。

### 9.1 主播的出招风格

内容包的每条主播定义可选填 `aiStyle`，对应 `StreamerDef.AiStyle`；例如在该主播对象内添加 `"aiStyle": "aggressive"`。省略或设为 `null` 表示没有专属风格，沿用原有 AI 行为。风格名区分大小写，只接受下表三个名称；未知名称在 `ContentDb.Validate()` 时抛出 `KeyError`，不静默回退。

| `aiStyle` | 风格 | 偏好方向 |
|---|---|---|
| `aggressive` | 猛攻 | 提高伤害和击倒收益，减少主动换人倾向。 |
| `defensive` | 稳守 | 提高回复、护盾等防护效果和改善对位的换人收益。 |
| `tricky` | 花招 | 提高施加状态、驱散和削减 PP 的收益。 |

`AiStyles.Get(name)` 返回对应的独立 `AiWeights` 实例，修改返回值不会污染预设或其他主播；未知名称（包括 `null`）返回 `null`。预设改变的是电脑的选择偏好，不改变技能、人设、合法行动或实际结算规则。

普通难度每次选行动时读取当前场上主播的风格：有风格时使用其预设，优先于调用者传入的普通难度权重；无风格时继续使用传入权重或原默认值。换人、补位后，下一次选择按新场上主播重新读取，不沿用上一位的风格。困难和专家保留原有搜索流程，在候选评分中使用对应风格与默认普通估值的差额作为偏好；计算差额不额外消耗随机数。简单难度完全忽略风格，包括其调用普通估值的分支。

未配置风格时，选择结果和原有随机数消耗保持不变。本次不为任何现有主播添加 `aiStyle`；今后由内容任务决定谁采用哪种风格。内容指纹也保留兼容性：全包主播均无风格时，`ContentHash()` 不增加编码；只在存在配置时，于原编码末尾追加独立标记和按 ordinal 主播 id 排序的风格配置，使不同风格参与内容一致性检查。

## 10. 联网对战（进行中）

联网对战使用相同版本的引擎、规则数据、内容包和种子，双方只交换行动，每回合结算后在同一节点比对 `Battle.StateHash()`；哈希读取不推进随机数，也不改写状态或日志。

`ContentDb.ContentHash()` 对加载、合并和改名后的内容计算 FNV-1a 64 位指纹，返回 16 位小写十六进制。范围包括包 id/名称/声明、属性与类别名称、赛道与克制表、状态、直播间效果、人设、技能（含硬撑）、主播、赛季限制，以及这些定义的全部显示文字和数值。字典按 ordinal 键顺序、主播按 ordinal id 顺序写入；技能槽、效果和赛季列表保留原顺序。字符串采用 UTF-8 长度前缀，null 与空串区分；整数和 IEEE-754 双精度值固定小端序，布尔使用单字节，各集合包含数量。每次调用重新读取当前内容，不缓存可变定义。指纹用于内容一致性检查，不用于安全认证；`Tools/PackCheck` 在检查和列出内容包时显示它。

内容指纹编码以字符串 `StreamDuel.Content.v1` 为前缀，FNV 初值和质数与下述状态哈希相同。整数及长度为 4 字节，双精度值为 8 字节；null 字符串或集合长度为 -1，每个定义对象先写入存在标记。JSON 空白、对象键排列和等价的省略默认值不影响指纹；技能槽及效果顺序影响指纹。

行动编码为 `S0`～`S4`（技能）、`W0`～`W5`（换人）或 `P`（跳过），区分大小写且不允许空白或额外字符。硬撑和受控跳过仍由 `Normalize` 派生，不作为发送的行动编码。

### 10.1 同步会话与协议版本 3

`Core/Net/` 中的 `NetSession` 负责握手、收集双方承诺和公开选择、结算及哈希确认，并提供独立的固定快捷语；`INetTransport` 只传递字符串消息，要求每个方向先进先出、不丢不重。`LoopbackPair.Create` 提供线程安全的两端内存队列，不连接真实网络；`TcpTransport` 提供本机或可信局域网的 UTF-8 按行传输。会话的 `Poll`、`Submit`、`SubmitReplace`、`SendQuickChat` 和可选计时的 `Tick` 由同一调用线程依次执行；每次 `Poll` 最多取出 64 条消息（包含无效、超额和静音聊天），剩余消息按原 FIFO 留待下次调用，避免聊天洪泛阻塞调用方的计时或输入。

构造参数为内容库、传输端、是否主机、本方六人队伍、名字、可选种子。主机固定为 `MySide = 0`，客机为 `1`；两端的队伍和名字始终按 `[主机, 客机]` 排列。种子只由主机决定，传入 null 时主机在构造时用 `Environment.TickCount` 生成一次；客机传入的种子不参与对战。握手完成前 `Battle` 为 null。双方协议版本、内容包 id 和 `ContentDb.ContentHash()` 必须一致，两支队伍均须通过 `TeamCheck.Validate(db, null, team)`；本方参数非法时直接报错，不开始对战。hello 必须带 `contentHash`，按 ordinal 字符串比较；不一致在构造对战前报“内容不一致”并列出双方指纹，通知另一端。会话保存发出 hello 时的指纹，握手期间本地内容变化也会拒绝；开局后调用者不得改动共享内容库。版本 3 不启用禁用和首发阶段，拒绝版本 1、2 握手及旧版明文 action/replace 消息。旧版本收到未知的 `chat` 类型会报错，因此新增快捷语时按 T-62 的兼容规则将协议从 2 升到 3；承诺、公开选择及哈希流程沿用版本 2。

每条发送消息均为一行紧凑 JSON，不含尾部换行；行分隔由传输实现负责，字符串内的换行、引号和反斜杠均转义：

| type | 格式示例 | 含义 |
|---|---|---|
| `hello` | `{"type":"hello","version":3,"packId":"original","contentHash":"63a758a4fa663be9","seed":42,"name":"主机","team":["bell","enka","shiori","lumi","hane","momo"]}` | 两端各发一次；客机的 `seed` 必须为 null，主机为 uint 整数。检查版本、内容包与指纹、角色及队伍后开局 |
| `commit` | `{"type":"commit","turn":1,"kind":"action","digest":"<64位小写十六进制>"}` | 锁定当前选择，仅发送摘要；`kind` 为 `action` 或 `replace` |
| `reveal` | `{"type":"reveal","turn":1,"kind":"action","action":"S2","nonce":"<32位小写十六进制>"}` | 所有本阶段参与方的承诺齐备后公开编码和随机串；补位使用 `kind: "replace"` 与 `action: "W3"`（队伍下标从 0 开始） |
| `hash` | `{"type":"hash","turn":1,"hash":"0123456789abcdef"}` | 每次本地 `ResolveTurn` 或 `Replace` 后立即发送该操作结果的状态哈希 |
| `chat` | `{"type":"chat","index":0}` | 只发送固定短句编号 0～7；不发送文字、身份、回合或时间，不参与行动和哈希确认 |
| `error` | `{"type":"error","message":"中文原因"}` | 终止会话；对方收到后也进入 Error，不再回复 error |

`NetState` 与提交规则：`Handshake` 等握手；`Choose` 可提交一次行动；`Replace` 仅本方需要补位时可提交一次；`Waiting` 等承诺、公开选择或哈希；`Over` 表示最终哈希也已确认；`Desync` 表示双方哈希不同；`Error` 表示协议、队伍或传输错误。`HasSubmitted` 在本阶段本方提交后为 true，哈希确认并开放下一阶段时清零。错误阶段、重复提交、不可编码动作或非法补位的本地调用抛 `InvalidOperationException`，不发送消息；远端重复、过期、越阶段或格式错误则进入 Error 并发送原因。合法的 AI 派生硬撑/受控跳过由会话转换为 P，结算时仍交给 Core 的 Normalize 判断。

承诺摘要为 `SHA-256(UTF-8(行动编码 + "|" + nonce))`，输出 64 位小写十六进制。每次本方有效提交用 `System.Security.Cryptography.RandomNumberGenerator` 产生 16 字节，再编码为 32 位小写十六进制 nonce；不会从 `Battle.Rng` 取得或向其写入随机数。这是 T-32 唯一允许的额外随机源，用于使承诺无法按有限行动集合直接枚举；nonce 与摘要均不参与战斗、日志、回放或状态哈希，因此相同种子和选择仍产生相同对战结果。

双方行动或同时补位时，本端发送自己的 commit 且收到对方 commit 后，才发送自己的 reveal；每个方向先进先出的传输保证接收方先收到该方的 commit。只有一方需要补位时，仅该方发送 commit，紧接着发送 reveal，不等待无需补位的一方提交。收到 reveal 必须已有该方承诺，所有参与方承诺均齐备，且回合、kind、行动编码和 nonce 格式合法。重算摘要与已保存承诺不同则进入 Error，原因包含“承诺”。未经验证的公开选择不参与结算；重复 commit/reveal、提前公开、无需补位方的提交一律报错。每阶段哈希确认后清除全部承诺和公开记录，下一阶段重新提交。

版本 3 沿用版本 2 的承诺摘要，按任务约定只包含行动与 nonce，回合、kind 在消息外层校验，发送方和会话身份未纳入摘要。它能检测承诺后更换行动或 nonce，但不能阻止对端复制已收到的 digest，再复制其公开的相同行动编码和 nonce；也不解决故意断开连接。是否增加摘要上下文绑定属于后续协议决策。

快捷语编号固定为 0～7，对应“你好、打得好、好险、再来一局、我在想、抱歉手滑、谢谢、晚安”，通过 `Loc` 的 `quickchat.0`～`quickchat.7` 取文本。`QuickChat.Lines` 是首次访问时当前语言的快照；显示消息时调用 `QuickChat.Text(index)`，按当前 `Loc` 查询，因此切换语言不改变已收消息中的编号。不支持自由文字。

`SendQuickChat(index, now)` 只在握手完成且会话未处于 `Error` 或 `Desync` 时发送，`Over` 仍可聊天。编号越界、握手未完成、会话故障，以及非法时间或超出限频均返回 false 且不发送。`now` 由调用方提供秒数，须有限、非负且单调不减；引擎不读取系统时间。发送使用滚动 10 秒窗口，最多 3 条；已发送消息距当前时间达到 10 秒时退出窗口，边界时即可重新发送。

接收消息以本机收到时的 `Battle.Turn` 标记 `Turn`，并将 `Side` 固定为 `1 - MySide`。同一本机回合最多接受对方 6 条有效快捷语，多出的丢弃；静音期间的有效消息仍计入此上限。`MuteOpponent = true` 只阻止新收到的消息进入 `ReceivedChats`，不清除历史，也不在解除静音时补入此前的消息。`ReceivedChats` 是只读列表，其中的 `QuickChatMessage` 记录也不能被调用方修改；握手前或会话故障时不接收快捷语，`Over` 可继续接收。

快捷语消息只接受 `type` 和 `index` 两个字段，`index` 必须是 0～7 的整数，不接受 `text`、`side`、`turn` 等额外字段。合法 JSON 对象的顶层 `type` 为 `chat` 时，编号或消息结构无效就直接丢弃，不影响对战，也不视为掉线。JSON 解析失败时，局部扫描根对象字段；完整确认顶层 `type` 为 `chat`，且没有遇到非聊天或冲突的顶层类型时，按坏聊天消息丢弃。字段顺序、合法 JSON 空白和字符串转义不影响识别，载荷数值只跳过而不转换，因此前置的溢出 `index` 也不会把聊天当作掉线。字符串内或嵌套对象内的 `type` 不算路由头；已确认聊天头之后的截断载荷仍丢弃。无法确认聊天类型或明确非聊天的坏 JSON，以及其它协议错误，仍走原有 `Fault` 流程，进入 `Error` 并报告原因。此扫描仅用于失败的 JSON，不改变正常解析对象的既有重复键行为。

快捷语独立于行动、补位、承诺和哈希确认，不改变 `HasSubmitted` 或这些流程的先后顺序，不追加对战日志或回放记录，不改变 `StateHash`，也不读取或推进 `Battle.Rng`。聊天不会触发新回合或恢复已经结束的对局。

进入 Over 后继续调用 Poll 仍会接收远端 error 并转入 Error，避免只有一端最终哈希被篡改时，另一端忽略稍晚到达的错误通知；Over 允许快捷语，但不允许新的行动、补位或握手。

TCP 在后台线程接收完整 UTF-8 行，由调用线程通过不阻塞的 `TryReceive` 依次取出。连接断开前收到的完整消息优先交付；未完成会话在断开后进入 Error，提示“对方已断开”。本端已确认终局的 Over 状态仅忽略纯传输断开，仍处理断开前排队的 error 和非法协议消息，避免正常退出把已完成对局改成错误。CLI 进入 Over 后用 TCP 半关闭结束发送方向，并继续分批 Poll，直到 `TcpTransport.ReceiveDrained` 确认正常 EOF 与接收队列为空同时成立，确保关闭前的最终哈希错误仍会阻止保存；收尾超时或错误不保存。`PeerClosed` 仍只表示已收到正常 EOF，不能单独作为消息已经处理完的依据。传输收到正常 EOF 后保留发送方向，以便本端仍能报告已收到消息的校验错误。此收尾不增加 JSON 消息或改变协议版本。连接与会话均不提供加密或身份认证，只面向可信本机或局域网。

双方行动收齐后才按固定的 0、1 方参数调用 `ResolveTurn`。补位只收集需要补位的方；双方都需要时先收齐，再固定按主机、客机顺序分别调用 `Replace`，每次调用都单独发送哈希。哈希消息的 `turn` 是**该次操作调用前**的 `Battle.Turn`：第 N 回合结算的哈希标 N，随后补位通常标 N+1；同一补位阶段的两份哈希可以有相同回合号。接收端按操作发生顺序 FIFO 配对保存的哈希快照，不按回合号覆盖。对应快照以字符串精确比较，任一不同进入 Desync，Error 属性写明回合、本端和对端哈希，并发送 error；当前阶段全部哈希一致后才允许下一阶段，终局也必须等待最后一次确认。

会话在开局和每次结算后保存共享 RNG 检查点。界面或 AI 在本端选招、等待时可能消费 Battle.Rng，但这只用于本端决定提交什么行动；正式结算前以及哈希确认后恢复共享检查点，使两端只按相同行动推进同一随机流。哈希使用结算瞬间保存的值，不重新读取被本端建议计算影响后的状态。调用者通过会话提交选择，不直接调用其 Battle 的结算接口或修改战斗状态。

#### 局域网房间发现（SD-LAN-1）

发现数据独立于对战会话，使用 IPv4 UDP 47777 广播，不改变当前对战协议版本或对战随机数。`LanBeacon` 编码紧凑 UTF-8 JSON：`{"magic":"SD-LAN-1","name":"周末对战","port":7777,"protocol":3,"contentHash":"内容指纹","ruleset":"casual"}`。这六个字段均必需；端口为 1～65535，协议为正整数。房名按最多 24 个 UTF-16 单位截断，末尾不拆代理对。完整消息最多 512 字节，错误魔数、缺字段、错误类型、重复字段或非法 JSON/Unicode 返回 null；编码非法房间也返回 null。`Address` 与 `LastSeen` 不写入包，接收时忽略包内同名值，地址仅取实际 UDP 来源。

`LanRoomList.Receive(text, fromAddress, now)` 按规范化的来源 IP 与 TCP 端口更新房间，`Rooms(now)` 返回独立快照；距离最后收到广播恰好 3 秒仍保留，超过 3 秒移除。调用方提供有限、非负、单调的秒数。`LanBeaconSender.Tick(seconds)` 首次调用立即广播，之后每积累 1 秒广播一次，长时间未轮询不补发多份；`LanBeaconListener.Poll(now)` 非阻塞接收。两者都由调用方驱动，不启动后台时钟；通过 `Error` 提供中文套接字故障，关闭或构造失败均释放套接字。监听独占 UDP 47777，拒绝超长数据报和无效 UTF-8，每次轮询限制处理数量，避免持续数据流阻塞界面。

CLI 的 `--lan-host 房名` 默认自动分配 TCP 端口，也可配合 `--host` 指定；仅等待连接时广播，建立连接后停止。`--lan-list` 独立收集 5 秒内见过的房间，结束时把超过 3 秒未更新的条目标为失联，仅为仍可见且协议兼容的房间显示加入命令。列表中的房名、指纹和规则仅供发现与显示，不能代替实际 TCP 握手的内容一致性校验；当前房主广播 `casual` 基础规则，不宣称支持尚未接入网络的其他赛制。发现不保存数据，也不提供公网匹配或 NAT 穿透。

### 10.2 状态哈希

状态哈希采用 FNV-1a 64 位（初值 14695981039346656037、质数 1099511628211），每字节先异或再按无符号 64 位溢出乘法计算。整数固定为 4 字节小端序，布尔为 0/1 单字节，字符串为 UTF-8 字节数前缀加内容（null 长度为 -1），可变长度集合带数量。按回合数、阶段、双方场上位置、双方队伍顺序写入各主播的人气/下播/最后技能、各技能 id/PP、能力等级（`ContentDb.StatKeys` 顺序）、状态 id/剩余、直播间效果 id/回合/层数，再写入 RNG 内部状态和胜负。状态与效果保留列表顺序，因为结算顺序本身有意义。

随后写入内容包 id，再按 0 方、1 方的顺序，分别写入本方补位需求/先手标记/首发选择以及本方各主播 id/号位/所属方/最大人气/登场回合/首次控制免疫是否已用（`FirstControlImmunityUsed`）/本场保命是否已用（`EndureUsed`）和各技能最大 PP/第五技能标记，避免遗漏会影响后续结算的状态。这一尾段的队伍和技能数量复用前段，不重复写入。末尾按 0 方、1 方写入禁用选择（未选择为 -1），再写入禁用后是否进入首发选择（`leadPickAfterBan`）；禁用尚未全部确认时，这些选择也参与比较。显示名字、日志、回放历史及不影响后续结算的累计对战统计不参与哈希；此哈希用于同步检查，不用于安全认证。

### 10.3 对战计时

`TurnClock(turnSeconds, bankSeconds)` 为双方各保存一份基本时间和总时间余额。参数及 `Tick(side, seconds)` 的时间增量必须是有限非负数，side 只能为 0 或 1。构造即初始化首个阶段；`StartTurn()` 重置双方基本时间、清除已提交标记和上阶段超时状态，但不补充总时间。选择行动与需要补位都各自获得一次基本时间；总时间跨这些阶段累计扣除。零基本时间直接使用总时间，两者均为零立即超时。

`Tick` 先扣基本时间，再用超出的部分扣总时间，不出现负余额；两者恰好归零也算超时。`Submit(side)` 停止该方本阶段计时；已经超时后提交不取消超时标记。`TurnLeft/BankLeft/TimedOut` 仅查询，不推进时间。Core 不读取系统时钟，也不消耗对战随机数，调用方传入经过的秒数。

`TurnClock.TimeoutAction(b, side)` 返回原始 `BattleAction.Pass()`；受控时也返回 Pass。该默认选择仍经过 3.4 的既有 Normalize：受控时派生受控跳过，全部技能无 PP 时派生硬撑。`TimeoutReplacement` 返回不是当前场上者、仍在播且人气大于零的最小队伍下标；无候选时返回 −1。计时本身不改变 Battle，只有这些默认选择进入正常行动与补位接口，形成原有日志及回放事件。

`NetSession` 的构造末尾可传 `double? turnSeconds`、`double? bankSeconds`，须成对提供；不传时不启用计时。`Clock` 为启用后的计时器，未启用时为 null；`Tick(double seconds)` 推进会话计时，输入等待和已提交后的 Waiting 阶段均须继续调用。只有主机决定预算，客机采用主机 hello 声明的值。

`Tick` 不隐式调用 Poll。调用方先收取已到达的消息，再推进时间；只读 `TimerRevision` 在新决策阶段或新的公开/哈希等待窗口开始时变化。若本次 Poll 刚开启新窗口，调用方重置计时基线，不把旧窗口的经过时间扣到新窗口上。一次大 Tick 内刚自动发出的 commit/reveal/hash 同样不会倒算发送前的时间为对方响应迟延。

协议为版本 3。新版 hello 附带 `"timerVersion":1` 能力标记；启用计时的主机另附 `"timer":{"turnSeconds":10,"bankSeconds":30}`。主机启用计时时拒绝未声明支持的旧客机；无计时的会话仍接受省略计时能力字段的版本 3 hello；版本 1、2 握手仍会被拒绝。计时数值须为有限非负数。此扩展不更改承诺摘要、行动编码或哈希格式。

每次开放行动或补位阶段重置基本时间，不需要补位的一方停表。本方提交 commit 后停本方表，收到对方有效 commit 后停对方表；对方提前承诺不会压缩本方剩余选招时间。本方超时仅由本端通过正常 Submit/SubmitReplace 提交默认选择，仍须等待并校验双方承诺与公开。任何一端都不能替对方编造行动或 nonce。

启用计时时，若对方在基本时间与总时间均耗尽后再过 10 秒仍未提交 commit，则会话进入 Error，报告掉线。双方所需承诺齐全后，另等待对方 reveal 最多 10 秒；已经结算后，等待 hash 确认也最多 10 秒。三类等待使用独立计数，已提交方不再耗总时间。未启用计时不增加这些等待限制；TCP 终局半关闭与最终错误接收沿用 10.1。各端倒计时是本地经过时间的估计，不参与 Battle 状态哈希；最终行动通过已有同步协议结算。

CLI 的 `--timer 10,30` 启用每阶段 10 秒基本时间和每方全局 30 秒总时间。它以单调 Stopwatch 测量时间增量并显示剩余时间，超时自动提交；联网客机显示房主下发的预算。禁用与首发选择暂不计时，回放不接受此参数。相同选择序列的战斗结果仍可复现；有计时时，实时输入与计算耗时会影响最终提交的选择，倒计时输出本身不要求逐字相同。

## 11. 规则修饰器

规则修饰器用于对战房间的自定义规则和特殊赛制。构造对战时通过 `BattleOptions.Modifiers` 传入 id 列表，可同时启用多项；省略、`null` 或空列表均不启用，原有对战规则保持不变。`BattleModifiers.All` 提供可用修饰器的 id、中文名称和说明。

id 按 ordinal 比较，区分大小写；未知 id 在构造对战时抛出 `KeyError`。构造时将列表复制、去重并按 ordinal 排序，因此重复项只生效一次，输入顺序不影响结算、日志或哈希。对战持有独立的只读规则列表；之后修改调用方的列表或回放记录，不会改变正在进行的对战。完整克隆及 AI 的模拟副本都保留相同规则，不重复施加初始化效果。

修饰器从开局到结束持续有效，不能被消回合、消强化或净化移除。初始化只改变本局战斗实例，不修改共享技能、主播或内容包定义。实际开场时在“开场”节点列出全部启用项；禁用或首发选择尚未完成时不提前触发开场授予效果。

| id | 作用与时机 |
|---|---|
| `half_pp` | 在禁用、首发选择及登场人设之前，将双方全队所有普通和第五技能的 PP 上限减半，向上取整，当前 PP 同步设为新上限；例如 5 变为 3，1 仍为 1，0 仍为 0。后续回复 PP 不能超过新上限；人设免扣 PP 仍遵守原规则。整数计算使用 `原上限 / 2 + 原上限 % 2`，避免加 1 溢出。 |
| `stage_cap_3` | 将双方五项能力等级的上下限改为 -3～+3，适用于技能、人设及偷强化等所有能力变化。偷强化仍将目标正等级归零，获得方超出 +3 的部分舍去。能力倍率公式、消强化与下场清零不变。 |
| `sudden_death` | 从第 10 回合（含）起，在回合结束节点，按该节点原有的反应顺序，对每位仍在场且未下播的主播，在其自身弱化状态、直播间效果和回合结束人设全部结算后，扣除 `max(1, floor(本局最大人气 / 16))` 人气，并记录原因和实际扣除量。后排不受影响。 |
| `hype_start` | 禁用和首发选择完成、双方实际首发的登场人设全部结算后，在“开场”节点各授予 1 层「热度」。整局仅授予这一次，主动换人和补位不再授予。该层数遵守热度上限及消耗规则，不能被消回合，下场时清除；规则本身不会在下次登场时补回热度。 |
| `no_switch` | 禁止双方主动换人，合法行动列表不再提供换人；直接提交换人仍经过原有 `Normalize` 纠正规则。禁用、首发选择和下播后的补位不受影响。 |
| `hp_x2` | 在禁用、首发选择及登场人设之前，将双方全队主播的本局最大人气和初始人气乘以 2。按最大人气比例计算的回复、持续伤害及猝死均读取倍增后的最大人气；普通伤害公式和固定伤害数值不变。原始最大人气超过 `int.MaxValue / 2` 时，构造对战抛出 `KeyError`，避免整数溢出。 |

猝死沿用持续伤害处理：不受伤害倍率影响，不反弹，不解除挂机，不触发被击中后人设或击倒回复；一次性保命 `T_ENDURE` 和下播人设仍可响应。顺序遵守 3.2，任意一方全灭立即结束，另一方尚未执行的回合结束步骤（包括猝死扣除）不再执行；不会先同时扣除两边人气再判断胜负。同速时沿用对战 `Rng` 决定本节点顺序。提前因其他伤害下播的主播不会再承受猝死扣除。

显示层读取本局的能力上限、技能 PP 上限和最大人气。技能及人设的战斗说明按本局上限生成，组队时和无修饰器时仍保留原说明；不改写共享内容包的文案或数值。开场热度、骤降伤害和受限能力变化沿用结构化事件入口，事件中的变化量为实际生效值，完整克隆和回放保留一致的事件序列。

对战记录通过可选的 `modifiers` 字符串数组保存规范化后的列表，`Replay.Run` 将其还原为同一组构造选项。旧记录缺省该字段，或字段为空数组，均按无修饰器回放；无修饰器记录省略该字段，不改变原有记录格式。`StateHash()` 使用对战自身的规则快照：启用修饰器时，在 10.2 的既有编码末尾追加字符串 `StreamDuel.Modifiers.v1`、列表数量及各 id；未启用时不追加任何字节，保持旧哈希兼容。启用规则不同，即使当前人气等可见状态相同，也参与哈希比较。
