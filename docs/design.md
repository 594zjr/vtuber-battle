# 开播对决 设计文档（规则与数据格式的唯一标准）

版本 0.2 · 2026-10-15。现有代码（`UnityProject/Assets/StreamDuel/Core/`）已经实现了本文档第 1～6 节，测试见 `Engine.Tests/BattleTests.cs`。

## 0. 定位

**只做对战**：玩家对玩家（本机/局域网/以后的联网）和玩家对电脑。不做闯关、每日挑战、成就、教学关卡等单机养成内容（2026-10-15 用户确定）。

- 6 对 6 回合制对战，玩家对电脑（以后加联网对战）。玩法机制借鉴赛尔号的竞技对战，所有名字、文案、数值、美术为本项目自制。
- 非官方同人作品，免费、非商业、开源。主播名单是可替换的内容包（见第 7 节）。
- 设计核心：**每个效果都有明确的判定时机和驱散规则，并且显示给玩家看。** 同样的描述文字背后不允许藏着不同的时机。

## 1. 术语

| 术语 | 含义 | 代码里的名字 |
|---|---|---|
| 主播 | 一个战斗单位 | `StreamerDef` / 战斗中 `Fighter` |
| 人气 | 体力。降到 0 叫“下播” | `hp` |
| 互动 / 抗压 | 物攻 / 物防 | `atk` / `def` |
| 才艺 / 定力 | 特攻 / 特防 | `spa` / `sdef` |
| 反应 | 速度 | `spd` |
| 赛道 | 属性 | `type` |
| 人设 | 专属特质，每位主播 1 个，永久生效，不能被消除 | `PersonaDef` |
| 直播间效果 | 挂在主播身上的持续效果 | `FieldDef` / `FieldInst` |
| 第五技能 | 每位主播 4 个普通技能 + 1 个第五技能，规则上和普通技能相同，界面上单独标出 | `fifth` |

## 2. 一场对战

- 双方各 6 位主播，按 1～6 号位排列，开局各派 1 号位上场。
- 某方 6 位都下播即输；双方同时全灭为平局；打满 120 回合按剩余人气比例之和判定。
- 随机数只来自对战自带的 `Rng`（mulberry32，种子在开战时给定），同样的种子和同样的操作序列必须得到完全相同的日志。

**开局禁用**：用 `BattleOptions.BanOne = true` 启用时，先进入 `Phase.Ban`，双方看到对手原始六人阵容，各自调用 `ChooseBan(side, foeIndex)` 禁用对手一位。每方只能确认一次，双方都确认后才同时移除对应主播，其余顺序不变，重新编号为 1～5，改为五对五；原 1 号位被禁时原 2 号位成为首发。禁用不消耗回合，在“开场”节点写明双方禁用了谁；禁用期间不触发登场人设。若同时启用 `LeadPick`，禁用后进入 `Phase.Lead`，首发下标针对剩余五人；否则直接开场。后续人设按剩余号位判断，因此五人队伍没有 6 号位。电脑禁用对己方全队平均对位威胁最高的对手，同分时只使用对战的 `Rng`。

`BattleOptions` 还包含可选种子 `Seed` 和首发开关 `LeadPick`，旧构造函数保持默认不禁用的行为。命令行用 `--ban` 启用，支持手动选择及 `--auto` 自动禁用。回放保存禁用前的原始队伍、`banOne: true` 和按确认顺序的 `type: "ban"` 事件（`side`、原始对手下标 `to`、结算前 `rng` 状态）。可选 `names` 保存双方显示名以复现日志；旧记录缺省 `banOne` 时不禁用，缺省 `names` 时沿用“你/对手”。

**首发选择**：构造对战时可启用 `leadPick`，双方先看到彼此的完整阵容，在 `Phase.Lead` 各自调用 `ChooseLead(side, index)` 确认首发。两边确认后，将各自所选主播移到 1 号位，其余主播保持原有相对顺序，按剩余人数重新连续编号（未禁用时 1～6，禁用后 1～5）；按重排后的号位应用人设规则。随后在“开场”节点记录双方首发并触发登场人设，开始第 1 回合。选择首发不消耗回合，双方确认前不能结算行动或触发登场人设。电脑按对对手全队的平均对位分选择首发，同分时只用对战的 `Rng` 决定。`leadPick` 默认 false，保留原有直接派出 1 号位的行为。

回放记录保留禁用和重排前的原始队伍；启用首发时写入 `leadPick: true`，并按确认顺序保存 `type: "lead"` 的 `side`、`to`（首发阶段开始时的己方队伍下标；有禁用时为移除后的队伍）及结算前 `rng` 状态。回放先恢复相应禁用或首发阶段，再重放选择和后续行动；旧记录缺省 `leadPick` 时不选择首发。

新建对战的记录使用 `version: 2`，并在开局时将当前 `ContentDb.ContentHash()` 保存为 `contentHash`。读取缺省 `version` 的旧记录时按版本 1 处理；未提供指纹的旧记录仍可回放。提供了指纹的记录必须与当前内容指纹完全一致，否则 `Replay.Run` 在开始对战前抛出“内容不一致”错误，并显示记录和当前的指纹。内容包 id 仍须匹配。

`BattleRecord.CurrentVersion` 为兼容预检支持的最高版本，现为 3；`DefaultVersion=2` 保持普通新对局原有 v2 格式。只有发生投降、和局提议或回应时，记录提升到 `TerminationVersion=3`。旧记录的可选字段与显式尽力重放规则见 2.3。

### 2.1 回放分享码

`ShareCode.Encode(record)` 把对战记录转换为 `SD1-` 加无填充 base64url 文本。载荷先放 `BattleRecord.ToJson()` 的 UTF-8 字节经 Deflate 压缩后的数据，再放压缩数据的 32 位 FNV-1a 校验值（初值 2166136261、质数 16777619，按小端序追加 4 字节）。记录 JSON 的可读格式保持不变，版本、内容指纹、原始行动、禁用/首发、名字以及每个事件的随机流位置均保留。

`ShareCode.Decode(code)` 忽略 `char.IsWhiteSpace` 识别的全部空白，检查大小写敏感的 `SD1-` 前缀、无填充 base64url 字符与规范尾比特、载荷校验、Deflate、严格 UTF-8 和记录 JSON；无效输入统一抛出中文 `FormatException`。分享码只携带记录，接收方仍须有匹配的规则和内容包；回放继续经过 `Replay.Run` 的内容指纹与包 id 校验。FNV 校验用于发现复制或传输损坏，不提供身份认证。

为限制外部分享码的内存占用，原始 JSON 最多 1 MiB（1,048,576 个 UTF-8 字节），压缩数据最多 1,049,600 字节，去空白后的完整分享码最多 1,399,476 字符；编码与解码均检查上限。解压时逐块限制输出大小，并拒绝提前结束或尾随数据的压缩流。普通完整对局的目标长度小于 1,500 字符，不截断或丢弃事件来缩短分享码；自定义长名字或异常大的记录不保证这一短码长度。

命令行 `--share` 在完成对局后输出分享码，联网对局仍须先完成双方终局校验。分享导出失败单独报告并使退出码为 1，不阻止已完成对局保存原始回放和档案。`--replay-code <码>` 使用与文件回放相同的加载、播放和战报流程，不新增档案战绩或回放文件；与 `--replay`、联网选项及 `--hash` 互斥。回放完整播放后也可用 `--share` 导出原记录，提前退出不输出。回放的战报与分享分别导出；一项导出失败仍尝试另一项，最终退出码为 1。

### 2.2 同屏双人会话

`HotseatSession(db, teamA, teamB, nameA, nameB, opt)` 包装私有的 `Battle`，让同一台设备上的两位玩家轮流提交选择。会话 API 在同一线程顺序调用，结算同步完成。`WhoseTurn` 为当前操作方 0/1，结算中或终局为 -1；`NeedsHandover` 为 true 时，界面先遮挡并提示交接，接手者调用 `ConfirmHandover()` 后才能继续提交。首次由 0 方选择，无需交接。

行动、禁用、首发和双方补位都先在会话内部收齐双方选择，再按固定的 0、1 方顺序交给 `Battle`；先选内容不会提前写入战斗或录像。第一位提交后必须交接给另一位；第二位提交并完成结算后，由仍在设备前的这一位继续下一阶段的首次选择。只有一方需要补位时，直接由该方选择，无需交接确认，补位后仍由该方先选。这个顺序只安排界面输入，不改变行动先后、补位效果、随机流或其他战斗规则。

`Submit`、`SubmitReplace`、`SubmitBan`、`SubmitLead` 按当前操作方接收对应阶段的合法选择；交接未确认、阶段错误或无效选择均拒绝，保留已收取的选择。`ViewFor(side)` 返回脱离会话状态的视图快照，不含任何待结算选择；`Record` 和 `Log` 每次返回深拷贝，只包含已结算内容。会话不公开进行中的 `Battle`，仅在 `Phase.Over` 允许 `CloneCompletedBattle()` 供统计、保存和战报使用。录像不记录交接操作，仍按普通 `BattleRecord` 重放。

命令行用 `--hotseat` 启用；交接时清屏并要求接手者按回车，选项输入不回显。A 方沿用 `--team` 或 `--team-code`，B 方用 `--team-b`，`--name-a` / `--name-b` 默认“玩家 A” / “玩家 B”。完整对局仅按 A 方视角累计一次档案，并在旧回放目录与新录像库各保存一份；提前退出不保存。

### 2.3 旧录像兼容与版本维护

`BattleRecord.FromJson` 支持缺省版本的 v1、显式 v1、v2 和 v3。旧记录缺省 `contentHash` 时不检查内容指纹；缺省 `leadPick`、`banOne` 时均为 false，缺省或空 `modifiers` 表示无修饰器，缺省 `names` 时沿用“你/对手”，事件缺省 `rng` 时从原种子顺序推进随机流，不虚构历史 AI 的额外抽样。`seed`、`packId`、两支 `teams` 和 `events` 是历史格式也必须具备的字段，格式损坏不能靠默认值掩盖。读取不会把旧记录自动改写成当前版本。

版本必须为正整数。按任务表 2026-10-16 02:40 的决定，`FromJson` 保留 T-30 的行为，接受任意正整数版本并继续验证现有字段结构；可解析不等于已通过兼容检查。高于 `CurrentVersion` 的记录由 `Replay.Check` 返回 `CanReplay = false` 和含“录像来自更新的版本”的中文原因，不执行记录；格式损坏或未知事件仍由解析器报错。本地录像库在解析后调用兼容检查拒绝未来版本，沿用 `IsCorrupt` 的不可加载标记，并在 `Error` 保留明确的版本原因；未来录像不参与自动清理，也不允许修改备注重写未知字段，且不阻止其它条目列出。保存入口同样在序列化和文件操作前拒绝未来版本；回看游标先执行兼容检查，再沿用严格指纹校验，不能绕过版本门禁。

`Replay.Check(db, record)` 返回 `ReplayCompat`（`CanReplay`、`Reason`），只检查当前内容库能否支持记录的版本、包、原始阵容及构造选项，不执行历史事件、不改写记录或内容。缺失内容库、包 id 不符、版本不支持、无效阵容或修饰器等返回 false 和中文原因；内容指纹不同但其余条件满足时返回 true，并明确提示“结果可能不同”。兼容的记录返回 true 和空原因。这个预检不保证所有后续事件都能执行，损坏的事件或规则变化导致的不合法补位仍可能在重放时被拒绝。

`Replay.Run(db, record)` 保留 T-30 的低层接口行为，严格核对指纹但不新增版本门禁；应用播放前必须先调用 `Replay.Check`。`Replay.RunBestEffort(db, record)` 是调用方明确选择的尽力重放入口，执行兼容检查，仅允许内容指纹差异，不绕过版本、包、阵容或事件校验，也不清空原记录的指纹。输出是按当前内容重新计算的对战，不声称复原旧版规则。CLI 的严格与尽力回看均先通过兼容检查，`--replay-best-effort` 只可与文件、录像库编号或分享码回看同用；先显示兼容警告再重放，导出的战报也注明按当前内容重新计算，不修改来源录像，不增加战绩或新录像。重新导出的分享码保留原记录。未指定时仍执行严格指纹校验。

版本升级规则：新增必需字段或事件、改变已有字段/行动的含义、改变缺省值、随机流解释或导致同一内容与记录产生不同结果的结算规则时，须提升录像版本，保留旧版本的读取与可用迁移，并明确无法重放的原因。仅新增旧读取器可忽略的展示元数据、调整 JSON 排版、增加已有可选字段，不必升级；仅调整内容包数据由 `contentHash` 区分，严格回放拒绝，尽力回放提示差异。

`Engine.Tests/Golden/replays/` 冻结真实完整对局、预期终局 `StateHash` 和生成时的规则/内容快照，测试只读取、不自动重写。覆盖普通、首发、禁用、修饰器、多局中的单局、联网记录、同人包、第二期包和无版本 v1；多局关联只检验各局录像，完整赛制容器待 T-54 合并后补齐。每次升版本须保留旧样例、为新版本添加代表样例与期望哈希，并在 PR 解释迁移和任何历史回放结果变化；不能仅重生成旧哈希使回归变绿。

### 2.4 投降与和局

禁用前的提议、拒绝也会产生历史快照；双方确认禁用时，快照须删除同一主播的位置，后续首发重排继续按存活主播身份映射，避免逐行回看或复盘把人气对应到错误主播。录像中的投降只能使用独立 `surrender` 事件；拒绝把 `Surrender` 嵌入普通 `turn`，保证回合游标与统计都不虚增未发生的行动回合。

`BattleAction.Surrender()` 是显式投降行动，线路编码为 `Q`。`ResolveTurn(a0, a1)` 在普通行动、Normalize、随机排序和伤害之前同时检查双方；一方投降直接判负，双方在同次提交中投降则平局。`Battle.Surrender(side)` 与 `ResolveSurrenders(side0, side1)` 也适用于当前已有的选择行动、补位、首发、禁用阶段，终局后再次提交会拒绝。投降不花费 PP、不执行对手行动、不推进回合或随机数；只写投降记录及“结束”日志和 `BattleEventKind.End`，不伪造全员下播。尚未合并的选人流程可直接调用同一终止入口。同屏模式只允许当前已确认交接的操作者投降。

`Battle.OfferDraw(side)` 记录该方提议，`RespondDraw(side, accept)` 回应对方；`HasDrawOffer(side)` 查询该方提出的待答提议，`CanOfferDraw(side)` 查询是否可提出。双方各有独立冷却：第 N 回合提出后，最早第 N+5 回合再提，拒绝不重置冷却；同一方不能叠加未答提议。双方可以同时提出，拒绝只清除被回应的提议并继续对战，接受直接判平局并清除双方提议。所有入口不读取时钟或随机数。提议与拒绝日志写在当前选择对应的开场、回合开始或补位节点；接受和投降写在结束节点。首次发生提议后，状态哈希追加双方待答标志与上次提议回合；完整克隆及 AI 副本复制这些状态，未协商过的旧对局哈希输入不变。

录像 v3 增加 `surrender`（`side=-1` 表示双方同时投降，0/1 表示单方）、`drawOffer`（提出方 `side`）、`drawResponse`（回应方 `side`、布尔 `accept`）事件，均保存结算前的 RNG 检查点。新增事件标成 v1/v2 时序列化、解析及兼容预检均拒绝；保留普通 v1/v2 的原行为和黄金录像。`Replay.Run`、回看游标和本地录像库处理这些事件，不把未出招的终止操作算成一个行动回合。投降通过已有 `Winner=0/1` 表示负局，和局通过 `Winner=-1` 表示平局，玩家档案沿用原胜负口径；排位模块尚未合并，本任务不伪造排位接口。

电脑不会主动投降。收到和局提议时，`Ai.AcceptDraw(battle, side)` 比较全队当前人气总和：己方严格超过对方的 1.3 倍则拒绝，否则同意，恰好领先 30% 同意；双方为零时同意。这个判断不改变对战、不消耗随机数。CLI 的本地电脑对战用同一入口响应玩家的 `/draw`，联网由玩家用 `/draw accept` 或 `/draw reject` 回应；`/surrender` 与提前退出不同，会完成并保存真实胜负。

## 3. 一个回合

### 3.1 选择行动

双方同时选择，选项有：

| 行动 | 说明 |
|---|---|
| 使用技能 `Skill(i)` | i = 0..4，4 是第五技能。PP 为 0 的技能不能用（人设“团魂”例外，见 6.2） |
| 换人 `SwitchTo(j)` | 换成后排第 j 位（未下播、不是场上的）。换人占用这一回合 |
| 跳过 `Pass` | 只在被控制或无事可做时由界面提供 |
| 投降 `Surrender()` | 不执行普通行动，按 2.4 立即结算负局；同一窗口双方投降为平局 |

服务器（`Battle.Normalize`）会把非法选择纠正：被控制 → `PassControlled`；所有技能都没 PP → `Struggle`（硬撑：互动、威力 40、反噬造成伤害的 1/4）；其它非法 → `Pass`。**被控制时仍然可以换人，但「锁麦」等禁止主动换人的直播间效果仍然生效。**

### 3.2 结算顺序（节点）

每一回合严格按下面的顺序。日志每一行都带节点名。

| 顺序 | 节点 | 发生什么 |
|---|---|---|
| 1 | 换人 | 所有换人先执行（按双方当前反应高低排序）。下场者清空能力等级和所有直播间效果，状态保留；上场者触发“登场”类人设 |
| 2 | 回合开始 | 触发“回合开始”类人设 |
| 3 | 先手行动 | 先手方行动（见 3.3） |
| 4 | 后手行动 | 后手方行动；如果此时它已下播则不行动 |
| 5 | 回合结束 | 按反应顺序，对双方场上主播依次结算：弱化类状态 → 直播间效果 → 人设 |
| 6 | 补位 | 回合数 +1；场上主播已下播的一方选择补位，补位的主播触发“登场”类人设 |

任意时刻有一方全灭，立即结束，后面的步骤不再执行。

### 3.3 谁先手

1. 先制高者先手。实际先制 = 技能先制 + 身上直播间效果的先制修正 + 人设修正。
2. 先制相同，反应（含能力等级）高者先手。
3. 都相同，随机。
只有一方行动（另一方换人）时，那一方的行动算“先手行动”节点。日志里写明判定理由，例如“先制都是 0，反应 360 对 300”。

### 3.4 一次行动内部

```
被控制？→ 跳过次数 -1，用完则解除并获得「重连保护」2 回合 → 结束
使用普通或第五技能时重新检查 PP：已为 0 且不满足人设免扣条件 → 记录“PP 已耗尽，行动失败” → 结束
扣 PP（或人设免扣）
命中判定（命中率 < 100 时掷骰）→ 未命中 → 结束
命中前判定：按顺序执行技能里 at = "pre" 的效果
伤害结算（威力 > 0 时）
  → 受到对手直接技能伤害后的反弹（见 5.2）；行动方下播则停止其余效果
  → 被击中方的“被击中后”人设
命中后判定：按顺序执行技能里 at = "post" 的效果
技能结算中行动者下播 → 记录“下播，技能中断”，跳过余下伤害和全部未结算效果
```

行动前 PP 检查不会改变回合开始的 `Normalize`：技能在选择时合法、行动前被削到 0 时，本次行动失败，不改用硬撑、不扣 PP、不更新最后使用技能记录；「团魂」满足免扣条件时仍可使用 0 PP 技能。若回合开始已经全部无 PP，仍由 `Normalize` 改为硬撑。

自伤、反噬、命中前效果或反弹导致行动者在技能结算中下播时，都立即中断这次技能，不再执行后续伤害或效果。中断日志记在该行动节点；若没有一方全灭，照常完成其余回合流程并进入补位。若因此全灭，保留立即结束规则，结束节点在中断日志之后。

**命中前和命中后读到的数值不同。** 例：「高音破麦」（命中前）和「电流麦」（命中后）都写“若对手人气高于 50%，40% 使对手卡麦”。对手在 55% 时被打到 40%：前者判定通过，后者不通过。测试 `PreHitConditionReadsHpBeforeDamage` / `PostHitConditionReadsHpAfterDamage` 锁定了这一点。

### 3.5 伤害公式

```
基础 = 50 × 威力 × A / D / 50 + 2        （A、D 为含能力等级的数值）
互动类：A = 互动，D = 抗压；才艺类：A = 才艺，D = 定力
倍率 = 本赛道加成(同赛道 1.5) × 克制倍率 × 状态修正 × 人设(攻) × 直播间效果(攻) × 直播间效果(受) × 人设(受) × 暴击(1/16 概率 ×1.5)
伤害 = max(1, floor(基础 × 倍率 × 随机(0.85..1.0)))
威力 = 技能威力 × 命中前判定里的威力倍率（POWER_MUL、POWER_PER_MARK）
```

### 3.6 能力等级

五项能力（互动、抗压、才艺、定力、反应）各有等级 -6..+6。倍率：等级 n ≥ 0 时 (2+n)/2，n < 0 时 2/(2-n)。下场清零。

## 4. 赛道

8 条：歌回、游戏、杂谈、绘画、整活、助眠、恐怖、硬核。克制表在 `StreamDuelRules.json` 的 `chart`：`攻击方 → 防守方 → 倍率`，没写的为 1。每条赛道克制 2 条（×2），被 1 条克（自身 ×0.5），对同赛道 ×0.5。

主播可在内容包中通过可选的 `type2` 字段指定第二赛道；省略或为 `null` 时仍是单赛道。第二赛道必须存在于赛道表，且不能与主赛道 `type` 相同。界面和名单按主赛道/第二赛道显示，例如“歌回/杂谈”。现有主播不添加第二赛道。

对双赛道主播造成技能伤害时，克制倍率为该技能对两个防守赛道的倍率之积；例如两次克制为 ×4，两次被克为 ×0.25，一次克制和一次被克为 ×1。同赛道加成在技能赛道等于攻击方任一赛道时生效，仍为 ×1.5，且只计算一次。技能本身仍只有一个赛道；固定伤害不受赛道倍率影响。伤害预览和电脑对手的对位判断遵循同一规则。

### 4.1 赛道的无障碍展示

`types.<id>` 增加可选的 `symbol` 和 `colorAlt`，分别映射到 `TypeDef.Symbol` 与 `ColorAlt`。符号为简单字符，配色为 `#RRGGBB`；内置八赛道各有不同符号，界面应同时显示名称和符号，不只靠颜色区分。旧数据缺省、null、空白或非字符串值时，符号回退为 `●`、备用颜色回退为原 `Color`；手工创建 `TypeDef` 时也有相同回退。旧内容仅能保证可显示，不自动获得内置配色的色差保证。

| 赛道 id | 名称 | symbol | colorAlt |
|---|---|---|---|
| song | 歌回 | ♪ | `#ffb0ff` |
| game | 游戏 | ▲ | `#d09000` |
| talk | 杂谈 | ● | `#90f0b0` |
| art | 绘画 | ◆ | `#fff030` |
| meme | 整活 | ★ | `#c070ff` |
| asmr | 助眠 | ≈ | `#30a0a0` |
| horror | 恐怖 | × | `#90a080` |
| tech | 硬核 | ■ | `#f0ffff` |

配色回归先将 sRGB 用 0.04045 分段转成线性 RGB，再应用 Machado 的红色弱、绿色弱、蓝色弱 severity=1.0 矩阵，逐通道夹到 [0,1]，转为 D65 CIELAB，计算 CIEDE2000（kL=kC=kH=1）。矩阵固定为[作者 2010 学位论文附录 A、表 A.1](https://www.inf.ufrgs.br/~oliveira/students_dissertations/Masters/Gustavo_Machado_Masters_thesis_UFRGS_2010.pdf)的三位小数值，代码在 `T109_ColorblindPaletteTests.cs`；普通视力使用单位矩阵。色差实现用 [Sharma 等作者的 34 对参考值](https://hajim.rochester.edu/ece/sites/gsharma/ciede2000/dataNprograms/ciede2000testdata.txt)校准，正反向误差均不超过 0.00005。

选色前固定的项目门槛为每种模拟下全部 28 对赛道 **ΔE00 > 10**；普通视力也检查相同门槛。当前最小值分别为普通 18.675343、红色弱 17.006853、绿色弱 16.691924、蓝色弱 16.137005。测试辅助另用 [WCAG 相对亮度对比度公式](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)检查备用色相对主题背景 `#0c1124`、面板 `#151c38`、抬高面板 `#1c2549`：普通和三种模拟后均 **≥4.5:1**，全局最低为 4.509045。模拟时前景、背景都变换；颜色若作色块背景，应配深色文字（如 `#0c1124`），不能直接套用主题的浅色文字。

ΔE00 门槛是项目的工程回归约束，不是所有玩家、屏幕或字号都能辨识的保证，也不构成整个界面符合 WCAG 的结论。尤其蓝色弱矩阵采用光谱偏移近似，原模型不声称准确覆盖完全蓝色盲；名称与独特符号始终是必要的冗余标记。实际画面仍须检查符号字体覆盖、大小、间距和真实显示效果。

`GameSettings.ColorblindMode` 默认 false；true 时选用备用配色，false 时仍用完全不变的原配色。`BattleViewModel.From(battle, viewerSide, settings)` 在生成快照时读取一次模式；两参入口及 null 设置均按默认模式。`FighterView.TrackViews` 按主、副赛道顺序提供独立 `TrackView`（`Id`、`Name`、`Symbol`、当前 `Color`），单赛道只有一项；`SkillView.TrackSymbol`、`TrackColor` 提供相同语义。原有 `FighterView.Tracks` 与 `SkillView.Track` 中文文字保持不变。改设置后需重新生成快照，已经返回的快照不会随设置或内容对象改变。

同屏 `HotseatSession.ViewFor`、联网 `NetSession.ViewFor` 和回看 `ReplayCursor.View` 均提供 `(viewerSide, settings)` 重载，原单参数入口保留默认配色。此任务提供数据和视图接口；Unity 画面任务接入设置开关和这些字段后才能显示色弱模式，不把已有画面称为已完成无障碍验收。

`symbol`、`colorAlt` 和本地开关只影响展示，不参与伤害、先手、随机流、日志、状态哈希或录像格式。为兼容已有录像，新增两项展示元数据不进入 `ContentHash()`，原 `Color`、名称等既有指纹字段保持原编码。混合内容包复制这两项，并单独比较来源规则基线和当前定义中的值；不一致时按共用规则冲突拒绝合并，不能静默挑一个来源的符号或配色。

## 5. 状态与直播间效果

### 5.1 状态

| 分类 | 例子 | 计数 | 效果 | 能否净化 |
|---|---|---|---|---|
| 控制类 `control` | 卡麦(1)、掉线(2)、挂机(3，受到伤害即解除) | 跳过几次**行动**，在被控制者自己的行动时扣减 | 不能用技能，可以换人 | 不能，只能等它结束 |
| 弱化类 `weak` | 过热（每回合 -1/12，互动伤害 ×0.7）、黑粉缠身（-1/8）、被引流（-1/10，对手回复同量） | 回合数，在回合结束扣减 | 回合结束结算 | 能（CLEANSE、人设“纯净人设”） |

规则：
- 同时最多 1 个控制类状态；已有控制时再施加无效。
- 身上有「重连保护」时控制类无效。
- 同一弱化类状态再次施加时刷新回合数，不叠加。
- 身上有 `immuneWeak = true` 的直播间效果（如「防火墙」）时，施加或刷新弱化类状态会被挡下并写日志；不移除已有弱化，也不阻止控制类状态。
- 状态跟着主播走，下场不清除；后排主播的状态不结算。

### 5.2 直播间效果

挂在场上主播身上，下场时全部清除。每个效果有 `kind`：

| kind | 名称 | 消回合（DISPEL_TURNS） | 例子 |
|---|---|---|---|
| `turn` | 回合类 | **能**清除 | 房管护盘、美颜滤镜、抢先开播、网络延迟、舰长续费、憋大招、镜面回击、防火墙、锁麦 |
| `mark` | 印记 | 不能 | 热度（可叠层）、循环回放 |
| `protect` | 保护类 | 不能 | 重连保护 |

`dispel` 字段是最终依据（`turn` 的都为 true，其余为 false）。持续回合在回合结束扣减；`turns = -1` 表示直到下场。

| 效果 id | 名称 | 判定时机与作用 | 新技能施加回合 | 消除规则 |
|---|---|---|---|---|
| `mirror` | 镜面回击 | 只反弹对手技能的直接伤害（含固定伤害）：本次实际扣除人气 × 0.3，向下取整且至少 1，日志记在攻击方；持续伤害、反噬、自伤和状态结算伤害一律不反弹 | 3 | 回合类，可被消回合，下场清空 |
| `firewall` | 防火墙 | 被施加弱化类状态时，阻止施加或刷新；不净化已有弱化、不阻止控制 | 3 | 回合类，可被消回合，下场清空 |
| `lockin` | 锁麦 | 选择行动时禁止主动换人；该效果施加到对手，击倒后的补位不受影响 | 2 | 回合类，可被消回合，下场清空 |

这些能力由 `FieldDef` 的可选数据字段 `reflectDamage`（反弹比例，默认 0）、`immuneWeak`、`preventSwitch`（默认 false）决定，不依赖效果 id。施加时机仍由技能效果的 `at` 决定；持续时间采用该 `FIELD` 效果的 `turns`，并遵守当回合结束即扣减的通用规则。

反弹不会再次触发反弹，不受伤害倍率影响，不触发被反弹者的人设（包括因此下播时的人设）；其造成的伤害仍会解除挂机。反弹使行动方下播时，该行动余下的效果不再执行。原攻击先导致一方全灭时，依照 3.2 立即结束，不再反弹。没有攻击方的持续伤害、自身反噬和以自身为目标的固定伤害不进入反弹入口。

### 5.3 两种驱散

| 代码 | 名称 | 清除 | 不清除 |
|---|---|---|---|
| `DISPEL_TURNS` | 消回合 | 对手所有 `dispel = true` 的直播间效果 | 印记、保护类、能力等级 |
| `DISPEL_BOOST` | 消强化 | 对手所有 **> 0** 的能力等级归零 | 下降的等级、所有直播间效果 |

日志写清清掉了什么、保留了什么。

### 5.4 印记与层数

印记效果可带 `maxStacks`。`ADD_MARK` 加层（上限截断），`POWER_PER_MARK` 在命中前按层数加威力，`consume: true` 时用后清空。

## 6. 数据格式

### 6.1 技能 `skills.<id>`

```json
{
  "name": "高音破麦", "type": "song", "cat": "talent",
  "power": 80, "pp": 15, "acc": 100, "prio": 0,
  "effects": [
    { "at": "pre", "code": "STATUS", "chance": 40, "target": "foe", "status": "stall",
      "cond": { "kind": "foeHpAbove", "value": 0.5 } }
  ]
}
```

- `cat`：`interact` 互动 / `talent` 才艺 / `status` 状态（威力 0）。
- `acc` 默认 100，`prio` 默认 0。
- 效果按数组顺序执行。`chance` 默认 100。条件不满足时不再掷概率。

**效果码表**

| code | 参数 | 作用 |
|---|---|---|
| `STATUS` | target, status | 施加状态（遵守 5.1 的规则） |
| `STAGE` | target, changes{stat:n} | 改能力等级 |
| `HEAL` | frac | 自身回复最大人气 × frac |
| `RECOIL` | frac | 自身受到本次造成伤害 × frac（至少 1） |
| `DRAIN` | frac | 自身回复本次造成伤害 × frac |
| `PP_REDUCE` | n, target | 在指定 pre/post 时机使目标本次上场最后使用的技能 PP 减 n，最低为 0；还没有用过技能则无效。未命中、免扣 PP 的技能也计入；硬撑和受控跳过不计，下场清空记录。即时结算，不可驱散 |
| `FIXED_DAMAGE` | n, target | 在指定 pre/post 时机对目标造成固定 n 点伤害，人气最低为 0；不受能力、赛道、直播间效果、人设或暴击影响，可解除挂机并导致下播，但不触发被击中后人设。即时结算，不可驱散 |
| `FIELD` | target, field, turns | 获得/刷新直播间效果 |
| `ADD_MARK` | target, field, n | 印记加层 |
| `POWER_MUL` | mul | 本次威力 × mul（只能放在 pre） |
| `POWER_PER_MARK` | field, per, consume | 威力 × (1 + per × 层数)（只能放在 pre） |
| `DISPEL_TURNS` | target | 消回合 |
| `DISPEL_BOOST` | target | 消强化 |
| `STEAL_BOOST` | target | 在指定 pre/post 时机取走目标所有 > 0 的能力等级，加到自身对应等级（每项最高 +6），目标这些等级归零；目标负等级保留。转移后自身正等级可被消强化、下场清零；以自身为目标时无效。日志列明双方等级变化 |
| `CLEANSE` | — | 净化自身弱化类状态 |

**条件 `cond.kind`**：`foeHpAbove`(value)、`foeWeak`、`actedFirst`、`actedSecond`、`foeBuffed`。在效果自己的 `at` 时机读取当时的数值。

### 6.2 人设 `personas.<id>`

```json
{ "name": "准点开播", "code": "T_FIRST_TURN_PRIO", "node": "排行动顺序时", "params": { "prio": 1 }, "desc": "…" }
```

`node` 只给界面显示；真正的调用时机由 `code` 决定：

| code | 调用时机 | 参数 | 作用 |
|---|---|---|---|
| `T_LOWHP_POWER` | 本方造成伤害时 | below, mul | 自身人气低于 below 时伤害 × mul |
| `T_EXECUTE` | 本方造成伤害时 | below, mul | 对手人气低于 below 时伤害 × mul |
| `T_REGEN` | 回合结束 | frac | 回复最大人气 × frac |
| `T_BENCH_GUARD` | 受到伤害时 | per | 己方后排每有 1 位在播，受伤 -per |
| `T_INTERACT_REDUCE` | 受到伤害时 | mul | 受到互动伤害 × mul |
| `T_FIRST_TURN_PRIO` | 排先手时 | prio | 上场后第一个回合先制 + prio |
| `T_TURNSTART_CLEANSE` | 回合开始 | — | 移除自身 1 个弱化类状态 |
| `T_FREE_PP_SLOT6` | 使用技能时 | — | 己方 6 号位队友在播（且不是自己）时不扣 PP |
| `T_CONTACT_STATUS` | 被击中后 | chance；人设的 `status` 字段 | 被互动技能击中后按概率给攻击方施加状态 |
| `T_ENTER_FIELD` | 登场时 | turns；人设的 `field` 字段 | 登场获得直播间效果（按那个效果自己的驱散规则） |
| `T_FAINT_CURSE` | 下播时 | n | 对手场上主播五项能力各 + n（n 为负） |
| `T_SPEED_IF_FIRST` | 回合结束 | n | 本回合先手则反应 + n |
| `T_KO_HEAL` | 本方技能直接击倒对手后 | frac | 本方普通或固定技能伤害击倒对手后，自身回复 floor(最大人气 × frac)，不超过上限；对战已经结束则不再触发 |
| `T_FIRST_CONTROL_IMMUNE` | 被施加控制类状态时 | — | 每次登场后，第一次本来可施加的控制类状态无效；下场再登场时重新计算。重连保护或已有控制已经使施加无效时，不消耗本次免疫 |
| `T_ENDURE` | 受到伤害时 | — | 每场对战一次：受到会使人气归零的伤害时，保留 1 点人气；下场不重置，反弹伤害不触发 |
| `T_ALLY_PP_ON_ENTER` | 登场时 | n | 己方后排所有还在播的队友，每个技能 PP +n，不超过各技能上限；不回复自身或已下播队友 |
| `T_STAGE_ON_HIT` | 受到普通技能直接伤害后 | 能力名 → 提升等级，例如 `{"def": 1}` | 实际扣除人气且没有下播时，按参数中的正值提升自身能力等级（最高 +6），每次被击中均触发；固定伤害、持续伤害、反噬和反弹不触发 |

“上场后第一个回合”：开局上场 = 第 1 回合；回合中换人上场 = 下一回合；补位上场 = 补位后的那个回合。

人设本体永久生效、不可消除；`T_KO_HEAL` 的人气回复和 `T_ALLY_PP_ON_ENTER` 的 PP 回复即时结算；`T_STAGE_ON_HIT` 产生的能力提升仍可被消强化，下场清零。被击中后的人设遵守 3.4：反弹使行动方下播后，不再执行后续的被击中后人设。`T_ENDURE` 的一次性保命属于人气下限规则，不改变固定伤害的数值计算；它可以响应普通、固定、持续伤害和自身反噬，但依照 5.2 不响应反弹。`T_KO_HEAL` 不因持续伤害、自身反噬或反弹归因触发，且遵守 3.2 的全灭后立即结束规则。

界面可调用 `Describe.Persona(db, persona)` 获取触发时机、说明和消除规则。上述 5 个新人设按代码和参数生成说明；已有代码保留其 `node`、`desc`，兼容内容包中的自定义文案。

```json
  "skills": {}, "personas": {}, "fields": {}, "statuses": {},
```

- 改名只改显示，不改机制。`personaName/personaDesc/personaStatus` 会复制出一份只属于这位主播的人设。
- 每包至少 6 位主播（不足 12 位时，电脑队伍先用玩家没选的，再从玩家选的里补，允许双方出现同一位主播）；每位正好 4 个普通技能 + 1 个第五技能。
- 读取时 `ContentDb.Validate()` 检查所有引用，错误信息要指出是哪一条。

内容包可选的 `skills`、`personas`、`fields`、`statuses` 对象用于新增本包定义；省略或写成 `{}` 时不增加定义。每个对象都以 id 为键，值的格式、默认值和含义与 `StreamDuelRules.json` 中的同名对象完全一致：技能见 6.1，人设见 6.2，状态和直播间效果见第 5 节。例如以下四个对象可放在内容包顶层：

```json
{
  "skills": {
    "pk_signature": {
      "name": "聚光开场", "type": "song", "cat": "talent", "power": 80, "pp": 5,
      "effects": [
        { "at": "post", "code": "FIELD", "target": "self", "field": "pk_glow", "turns": 2 },

    "pk_opening": {
      "name": "登场光环", "code": "T_ENTER_FIELD", "node": "登场时",
```

- 每次读取都先建立独立的 `ContentDb`，载入共用规则，再合并本包四类定义。同类别的 id 与共用规则已有 id 重复时抛出 `KeyError`，错误写明类别和重复 id；不会覆盖共用定义，也不会影响其他包的 `ContentDb`。
- 四类定义全部合并后，才处理 `skillNames/fieldNames/statusNames` 改名、主播的技能和人设绑定，以及 `personaName/personaDesc/personaStatus` 人设复制。因此包内技能和人设可以引用同包新增的状态或直播间效果，改名表也可以引用本包新增 id。
- 完成合并、改名和绑定后统一调用公开的 `ContentDb.Validate()`；所有技能引用的赛道、状态、直播间效果及人设引用的状态、直播间效果必须存在，每个技能效果必须有 `at: "pre"` 或 `at: "post"`。新增定义仍须使用引擎已支持的效果码和人设码。
- `Tools/PackCheck` 对合并后的全部技能检查未使用提醒；生成名单时，在本包定义的技能和人设名称旁标注 `〔本包独有〕`。复制本包人设保留该标记，仅改名或复制共用定义不添加标记。

```json

```

- `banned` 是禁用主播 id 列表；`limited` 的每个池子各自限制其 `ids` 中最多选择 `max` 位主播。读取内容包时校验这些 id，引用不存在的主播会抛出 `KeyError`，指出赛季和 id。
- `TeamCheck.Validate(db, seasonId, team)` 返回中文错误列表：队伍必须正好 6 位、不重复、主播均存在，并遵守赛季的禁用池与所有限制池。已知主播用显示名报错，限制池错误说明池子成员和上限。
- `seasonId` 为 `null` 时只检查人数、重复和主播存在性；未知赛季返回一条错误。该检查供组队界面调用。

#### 内容包下架策略

`Resources/PackPolicy.json` 是部署方控制的下架配置，默认值为 `{"disabledPacks":[],"disabledStreamers":[],"reason":{}}`。`disabledPacks` 使用内容包内部 `id`，不是文件名；`disabledStreamers` 使用主播 `id`，在所有包中生效。编号按 ordinal 区分大小写，不能重复、为空、带首尾空白或控制字符。`reason` 是编号到中文原因的可选映射；包和主播使用同一个编号时共享原因。省略字段等同空集合，未知字段、显式 null、错误类型或重复 JSON 键均拒绝，不会默默解除下架。空白文件不是空策略。

`PackPolicy` 是不可变快照，没有进程级可变开关。`PackLoader.LoadDirectory` 默认读取运行目录下的 `Content/PackPolicy.json`；调用方也可以显式传入一个快照，内置包和外部包必须使用同一份，外部包不能自带配置覆盖部署方政策。文件确实缺失时兼容旧部署并使用空策略；存在但不可读或损坏时阻止加载并显示错误。`LoadJson` 为内置资源提供同一个加载入口；被禁用结果的 `IsDisabled` 为 true 并携带中文原因，目录包列表省略这些结果。真正损坏的包仍按原规则逐项报错，不阻止其他正常包。

禁用整包时不载入其定义。仅禁用主播时，先验证源包，再在新建的内容库中删除对应主播，并清理赛季禁用池和限制池的相应引用，限制上限保持不变；可用主播不足 6 位时隐藏整包。不会改写源包、自动替换玩家队伍成员或删除保存的数据。空策略保持原内容指纹、规则、选择顺序和随机流；非空策略的过滤结果正常参与内容指纹。`ContentDb.FromJson(rules, pack)` 保留纯解析入口供历史数据和制作工具使用；实际游戏加载必须经 `PackLoader` 或带政策的三参入口。

组队、保存队伍的 `TeamPreset.Check` 和实际对战的主播查询都再次检查政策。含下架成员时显示“该主播已下架”及编号、可选原因；整个包下架时显示“该内容包已下架”。`TeamCode.Decode(code, db)` 在解码后执行同一门禁；原单参解码只读出数据，使用前仍须验证预设。共享的 `PackPolicy.CheckTeam(packId, ids)` 可用于电脑陪练名单，不能因队伍已保存或来自分享码就绕过。T-78 的专用陪练模块尚未合并，本任务不复制它的数据格式；该模块接入时须在列出和使用队伍时复用此门禁。

`Replay.Check` 在指纹差异和尽力重放之前检查记录的包及原始两队名单，已下架内容不能重放；显式提供的政策只能增加限制，不能覆盖内容库自己的政策。录像库以 `IsUnavailable` / `UnavailableReason` 独立标记下架条目，保留时间、队伍、备注等元数据，与 `IsCorrupt` 区别；读取、保存和改备注均拒绝。自动清理不计入、也不删除这些条目；用户仍可显式删除。恢复可用政策后重新打开录像库，条目可恢复使用，不需要改写原录像。未来版本及损坏记录仍遵守 2.3，不因下架标记绕过原有格式检查。

下架流程为：修改 `PackPolicy.json` → 按仓库流程提交 PR、由审查窗口合入 main → 发布策略配置文件。命令行工具的可替换文件位于发布目录的 `Content/PackPolicy.json`；Unity 优先读取 `StreamingAssets/PackPolicy.json`，缺失时回退内置 Resources 配置。部署方可以只替换这些外置文件，不重新编译游戏；已经加载的对局和内容库使用原快照，更新后须重启客户端再载入。离线程序不会仅因 GitHub 上更新了文件而自动收到策略，也不会自行联网下载。`Tools/PackCheck` 读取仓库资源根的真实配置，显示当前下架项及隐藏原因，正常下架不是内容损坏错误。

历史引擎回归在测试输出目录使用固定空政策样例，避免运营下架改动使历史规则样本失去对象；T101 专项测试以显式政策覆盖禁用、错误配置、队伍与录像门禁，发布入口另用独立输出目录验证实际可替换文件。空政策只用于测试样例，不复制到工具或游戏部署目录。

#### 文本检查

`TextLint.Check(ContentDb db)` 对载入、合并和改名后的显示文字返回 `List<LintIssue>`；每条问题包含 `Level`（`error` 或 `warn`）、`Where`（载入后字段路径）、`Id` 和中文 `Message`。检查不改动内容库，不消耗随机数。默认入口使用与 `Resources/Lint/banned.txt` 一致的内置词表快照，不读取工作目录；需要自定义词表时调用 `Check(db, bannedWords)`，由调用方负责读入文本。

长度按 Unicode 字符计数，UTF-16 代理对算一个字符；下面的建议上限同时作为 `TextLint` 的公开常量。超过上限记 `warn`，严格超过上限的 1.5 倍记 `error`；例如技能名 7～9 字为提醒，10 字起为错误。

| 显示字段 | 常量 | 建议上限 |
|---|---|---|
| 主播名 | `StreamerNameLimit` | 10 字 |
| 技能名（含硬撑） | `SkillNameLimit` | 6 字 |
| 人设名 | `PersonaNameLimit` | 8 字 |
| 状态名 | `StatusNameLimit` | 6 字 |
| 直播间效果名 | `FieldNameLimit` | 6 字 |
| 主播简介 | `BlurbLimit` | 40 字 |

扫描范围包括包名与声明、属性及技能类别显示名、赛道名、全部技能与硬撑名称、状态名称与说明、直播间效果名称/说明/时机、人设名称/说明/节点、主播名称/简介/组织，以及赛季名称。基础定义及复制后的人设都检查，不以当前是否被主播使用为豁免条件。组织、说明、节点等可选字段缺省为 `null` 时不检查；一旦提供，空串或只有空白均为 `error`。主播名称、简介等必填显示文字不能缺失。同人包必须有声明，原创包声明可省略。`personaDesc` 省略时检查继承后的说明，显式写空不能避开检查。内部 id、效果代码、颜色及引用键不是显示文字，JSON 中未进入 `ContentDb` 的 `_readme` 不属于此接口的扫描输入。

禁词表一行一词，去除两端空白并忽略空行及以 `#` 开头的注释；重复词合并，按 ordinal 顺序检查。总词表中的任一词在显示文字出现即记 `error`，每个字段每个词报告一次。id 以 `fan_` 开头的同人包另外禁止“官方”“授权”；只有 `notice` 对这两个附加词豁免，声明仍检查总词表。过滤词典仅用于拒绝不合要求的内容，不作为技能或角色文案。共用规则的显示名称为 `flame` →“过热”、`blackhist` →“循环回放”、`dig_history` →“回放追击”；同人包仍可把后者改名为“回放轰炸”，id、数值、效果与引用结构保持不变。

一致性问题记 `warn`：含中文的文字混用对应于“，。：；！？”的半角标点；数字与单位之间有多余空格；说明里的明确技能引用与当前名称不一致。标点检查排除网址及小数点；数字与单位检查覆盖回合、次、点、层、秒、分钟、小时、人气、人、位、个、倍、PP 和百分号。技能引用采用 `技能「名称」` 或 `技能[id]「名称」`（也接受中文双引号）：带 id 时对照该技能当前 `Name`，不带 id 时检查名称是否存在。当前技能模型没有独立 `desc` 字段，此项检查现有显示文字及全部技能（含硬撑）的 `Describe.Effect(...).Text` 生成说明中的明确技能引用；生成说明的问题定位到对应效果的 `generatedText` 路径。生成说明不套用技能名长度限制，也不把状态或效果的普通引号内容当成技能；不新增技能说明字段。

`Tools/PackCheck` 读取资源词表并调用文本检查，输出全部问题及错误、提醒数量；存在 `error` 时返回非零，`warn` 不阻止通过。CI 在引擎测试后运行 PackCheck。文案修正也会改变 `ContentHash()`，旧的带指纹回放仍按内容一致性规则拒绝与新文案混用；不能通过忽略显示文字的哈希或放宽旧断言来掩盖改动。有意更名时，同步相应显示文案断言与黄金日志的文字，并保持原检查强度、全部非文字日志字段和战斗规则不变。

### 6.4 混合内容包与随机阵容（T-104）

`ContentDb.Merge(params ContentDb[] packs)` 将已加载内容包合成独立的内容库，供手动混合组队或随机阵容对战使用，也允许单个来源生成 `mix:original` 这样的组合标识。输入必须是非空数组，每个元素非 null、有非空且互不重复的包 id，并具备 FromJson 保存的规则来源。合并来源 id 不得含控制字符或无效 UTF-16 代理项；有效代理对、中文和标点仍可使用，这项限制不改变普通单包加载。没有加载来源的手工 ContentDb、已有混合结果或 id 以 `mix:` 开头的源包均抛中文 KeyError；不隐式展开嵌套 Merge，也不丢弃重复来源。包 id 按 ordinal 比较，大小写不同视为不同 id。

共用规则只保留一份。FromJson 在加入包定义和改名之前深复制规则基线，并记录包内显式声明的共用技能、状态及直播间效果名称覆盖。合并要求各源包的原始规则基线相同；还会从各包的当前公开定义提取共用规则，暂时还原已声明的名称覆盖后逐项比较。非名称的公开修改只有所有源包完全一致时才能保留；差异报“规则不一致”，不会只挑第一个包的数值。没有声明来源的名称改动不能借用改名豁免。属性名称、类别、赛道、克制表、硬撑及共用定义的嵌套效果、条件、参数均属于规则比较范围。

合并输出的共用名称采用各包显式声明的唯一一致别名；未声明覆盖的包所保留的基础名不参与别名冲突。没有任何显式覆盖时保留规则名称；存在多个不同的显式别名则中文报错，避免随输入顺序选名或恢复同人包已特意替换的名称。人设的主播专属副本属于包私有定义，不是共享名称覆盖。共用定义按规则基线中的成员识别，不能仅依赖技能或人设的 PackDefined 标记。

主播、包新增技能/人设/状态/直播间效果、主播人设副本，以及 Seasons 均保留；不同源包在同一类别的私有 id 重复时一律抛中文 KeyError，写明类别与 id，即使内容完全相同也不去重。各类别仍有独立命名空间。合并结果对所有定义及嵌套字典、列表、效果、条件、人设参数、赛季限制池做深复制，合并过程不改源包；之后修改任一源包或结果均不会改变另一方。合并后重新 Validate，不能通过其它包的定义掩盖源包中原本无效的引用。

混合来源必须使用内容一致的下架策略：按 ordinal 比较 DisabledPacks、DisabledStreamers 集合及 Reasons 的全部键值，不要求是同一个对象；不一致时抛中文 KeyError，要求以同一策略重新加载全部来源。合并结果保留该不可变 Policy 快照，不能退回空策略。实际游戏入口先通过政策加载各源包，只合并过滤后的名单；因下架而不足六位、已隐藏的源包不能靠混合其它包补足。Merge 重新检查各来源包、当前名单及生成的组合 id，被下架的包或被重新加入公开名单的下架主播均抛 PackDisabledException。政策本身不额外写入 ContentHash；过滤后的定义和来源内容指纹正常参与哈希，空政策保留既有行为。

结果 PackId 为 `mix:` 加排序后的来源包 id：先按未编码原 id 的 ordinal 顺序排序，再逐个使用 Uri.EscapeDataString 编码，以逗号连接。例如 `original` 与 `fan_asoul_vr` 得到 `mix:fan_asoul_vr,original`；原 id 中的逗号、冒号、百分号等会转义，避免组合标识歧义。结果名称和聚合声明也按同一来源顺序生成。ContentHash 继续读取合并结果当前的全部内容，另仅对混合库追加独立尾段，按 ordinal 键顺序写入合并时冻结的“源包 id → 源包 ContentHash”及“主播 id → 来源 notice”映射。因此源包名称、声明或被统一名称遮盖的原别名仍影响混合指纹；交换传入包顺序不影响结果。普通单包不增加该尾段，原有指纹保持兼容。

`db.NoticeFor(streamerId)` 按主播返回来源包声明，不因跨包组队而丢失同人 notice。混合内容库保留各包聚合声明供整体展示；BattleViewModel 的 Notice 提供混合声明，FighterView.Notice 提供该主播的来源声明。画面和工具通过这些公开字段显示来源，不能根据混合 PackId 不以 `fan_` 开头便省略同人声明。

`MixedBattle.RandomTeams(ContentDb merged, uint seed)` 返回两组独立的六人 id 数组，双方合计十二位互不重复。先按 ordinal id 排序全名单，再用该 seed 构造 Core.Rng 做 Fisher–Yates 洗牌，取前六位给 0 方、随后六位给 1 方；不修改内容库或已存在对战的随机流。相同名单和种子得到相同分配，不受包传入顺序或主播列表顺序影响；少于十二位、空 id 或重复 id 的名单拒绝随机分配。随机入口在消耗随机数之前复查 Policy：整包下架或当前名单中含下架主播时直接抛 PackDisabledException，不静默过滤调用方重新加入的成员，也不等抽中后才拒绝。正常候选来自加载时已经过滤的名单。此入口只分配阵容，不加入额外赛季筛选或修改对战规则；手动队伍仍使用 TeamCheck 校验。

混合库直接用于 Battle、Replay.Run 和 NetSession。录像仍记录混合 PackId 与完整 ContentHash；回看时必须重建相同包组合和内容，联网双方也必须通过现有包 id 与内容指纹检查。不为混合玩法新增回放或网络消息格式，也不把源包对象写入录像。

`PackPolicy.PackReason` 先检查整个包 id 的精确禁用项，再识别规范的 `mix:` 标识：逐项仅解码一层，要求编码规范、原 id 按 ordinal 严格递增、无空项或嵌套组合，并检查每个来源包的下架状态。这样即使尚未加载 ContentDb，录像库和 `Replay.Check(null, record, policy)` 也能识别混合录像中的已下架来源；不可重放原因仍优先于缺包或指纹差异。普通包 id 不解码，非规范混合标识不会按猜测拆出来源，URI 解析失败不会使政策预检崩溃。显式传给回放检查的策略仍只能增加限制，不能解除内容库自身的下架策略；尽力重放也不能绕过。

CLI 用 `--packs original,fan_asoul_vr` 选择至少两个原始包 id，与 `--pack` 互斥；也可用 `--pack mix:fan_asoul_vr,original` 加载规范 URI 编码后的组合，特殊分隔符 id 使用这个编码入口。`mix:` 重建允许单个来源，与 Core 产生的组合标识一致。外部来源仍通过 `--pack-dir` 查找。回放、分享码和队伍码携带混合 PackId 时按该标识重建；普通单包 id 中的百分号不按混合编码解码。回看不接受额外 `--packs` 覆盖记录来源，队伍码与显式来源组合必须匹配。

`--random-teams` 用于新的本地、同屏或联网对局，与 `--team`、`--team-b`、`--team-code` 互斥，不用于回看、列表、分析、图鉴或赛事。联网随机阵容要求双方加载相同组合、均启用该选项并显式提供相同 `--seed`；主机取 0 方队伍，客机取 1 方队伍，握手后按房主公布的 Battle.Seed 重新生成并核对双方实际阵容，不一致则失败且不保存。混合包本地电脑对局也允许用 `--team-b` 手动指定对手；单包原有选项语义保持不变。CLI 在开局或回看头部按所选主播显示来源 notice，并保留包的聚合声明。

## 7. 内容包与同人规则

- `original`：全部原创。`fan_*`：同人包，只用公开艺名和公开人设，形象自制，**不得**含官方素材、现实事件、中之人、负面或擦边内容。
- 可能被误读成影射真人的技能/状态名，在同人包里用 `skillNames/statusNames` 改成中性名字。
- 收录一家公司之前必须查到它公开的二创规范并写进 `FANWORK.md`。
- 下架某位主播 = 删掉内容包里那一条。

`BattleStage` 仅提供具名显示节点：双方 `fighter-0` / `fighter-1`，各含 `portrait`、`hp-bar`、`status-row`；覆盖层 `fx-layer` / `float-layer` 与 `field-banner`。动画、技能特效、状态图标、头像分别通过 `IBattleAnimator`、`IFxPlayer`、`IStatusIconProvider`、`IPortraitProvider` 替换；当前默认实现为空动画、空特效、文字图标及按赛道颜色生成的纯色头像，不推导战斗规则。Input System 使用编辑器推荐的 1.20.1，迁移期间以 Both 保留旧 IMGUI 的运行时输入，T-67 移除旧画面后再切为 New。

`BattleViewModel.From(battle, viewerSide)` 提供当前时点的独立显示快照，不持有战斗或内容定义对象，也不改变状态、日志、回放或随机数。双方顺序与 Battle 相同；技能和可换人下标取查看方的 `LegalFor`，伤害范围取 `PreviewDamage`，不在画面重复计算规则。`Pct` 沿用 Fighter 的整数百分比；禁用后的队伍保留实际五人。状态芯片同时列出状态与直播间效果的类别、剩余次数或回合、层数及消除规则。`NodeStrip` 按开场、换人、回合开始、先手行动、后手行动、回合结束、补位、结束排列，仅标记 `battle.Turn` 的日志内容；历史逐行回放继续使用日志中的快照。

画面通过只读的 `Battle.Events` 播放动画，每条结构化事件以 `LogIndex` 对应原日志，并保留相同的回合和节点；同一日志可以对应多个事件，事件按实际发生顺序排列。事件中的 `Side` 和从 0 开始的 `Slot` 定位主播，`Id` 标识技能、状态、直播间效果或能力，`Amount` 记录实际变化：伤害与回复为正值，PP 与能力等级增减带符号。状态、效果的添加与移除也由引擎直接发出事件，界面无需解析日志文字；事件列表随 `Battle.Clone()` 独立复制，不参与状态哈希，也不消耗随机数。

### 8.1 文本与语言

`Core/Loc.cs` 提供独立文本表，JSON 格式为 `{"language":"zh-CN","texts":{"key":"文本 {0}"}}`。键名使用小写英文和点分层；中文原表位于 `Resources/Locale/zh-CN.json`。`Loc.FromJson(json, fallback)` 要求非空语言标识与字符串文本对象，创建时可指定回退文本表；`T(key, args)` 先查本表，再查 fallback，均不存在时返回 `[key]`。命中文本以 `CultureInfo.InvariantCulture` 调用 `string.Format`；`Has(key)` 包含回退表。无效格式占位符会抛异常，不静默吞掉翻译错误。

`Loc.Current` 可由调用方注入。测试和命令行工具可用 `Loc.Current = Loc.FromJson(File.ReadAllText(path))`；Unity 可用 `Loc.Current = Loc.FromJson(Resources.Load<TextAsset>("Locale/zh-CN").text)`。Core 不引用 Unity，也不会自行查找文件或读取资源。未注入或把 Current 设为 null 时，首次使用按需解析编译进 `Loc.ZhCn.cs` 的同一份中文 JSON；资源表与编译常量有一致性测试，修改文本时需同步更新两处。

当前迁移范围为 `TeamCheck` 的全部错误、`Describe` 的代码说明文字和 `PackLoader` 自身的错误模板。调用统一写为 `Loc.T("xxx.yyy", ...)`，这三个类中的 Loc 属性指向当前文本表；`Loc` 类本身保留实例查询 API，允许同时持有多份语言及回退表。内容包中的技能名、人设名和文案仍使用内容数据；底层校验器返回的错误原因也保持原样。Battle 日志尚未迁移，中文表的现有展示输出保持不变。

语言切换由调用方在显示或读取前设置 Current；这是全局显示配置，不参与规则、随机数、内容指纹或对战状态哈希。本次不增加语言选择界面，也不引入其它语言译文。

`Glossary.Build(db)` 根据当前合并后的内容库建立规则说明快照，按赛道、状态、直播间效果、人设、通用规则分组。内容条目在组内按内部 id 稳定排列，通用规则采用固定顺序。条目的 `Id` 和 `Category` 供程序定位；界面展示 `Title`、`Text` 和已翻译的 `Tags`，不把内部代码直接展示给玩家。控制状态用行动次数，弱化状态用回合数；直播间效果的持续时间由赋予它的技能或人设决定，说明不替它虚构统一时长。人设复用 `Describe`，旧机制的参数和关联名称在说明条目中从当前定义生成，避免包内改名后沿用旧描述。通用规则描述默认对战，并区分已启用修饰器时的例外；它不是当前战斗的实时状态。

`Glossary.Search(all, keyword)` 仅查询标题和正文，忽略大小写并去掉关键词两端空白；空关键词返回全部条目的新列表，顺序不变。重建快照才能反映后续内容或语言变更，不修改内容定义、战斗或随机数。命令行 `--glossary [关键字]` 提供同一查询，只与内容包选择参数同用，不启动对局或写入存档。

`StreamerCard.Build(db, streamerId)` 从当前内容库生成独立的组队前资料卡，包含名字、主副赛道及符号、六维基础数值、人设和四个普通技能加第五技能。六维按人气、互动、抗压、才艺、定力、反应排列；排名只比较当前库内主播的同项基础数值，降序使用并列竞争名次（如 1、1、3），同时给出总人数。正常加载后的下架主播不在排名范围内；混合库以合并后的名单作为比较范围。不施加能力等级、对局修饰器或临时效果，也不创建对战。

人设正文直接复用 `Glossary.Build` 的对应条目，技能效果逐项复用 `Describe.Effect`，保留判定时机和已有驱散说明；名称与技能数值都取当前内容定义。`Notice` 通过 `db.NoticeFor(streamerId)` 保留主播来源包的声明，混合库也不丢失原声明。资料卡的弱点是对方一个赛道攻击自身主副赛道时，合算倍率严格大于 1 的赛道。攻击优势以自身主副赛道分别攻击一个防守赛道的较大倍率为准，严格大于 1 才列入，并记录提供该倍率的自身赛道（相同时优先主赛道）；它只说明赛道关系，不表示实际技能覆盖、伤害预估或对双赛道目标的最终倍率。对位条目按赛道 id 稳定排列，倍率沿用第 4 节。

`card.ToText()`（或 `StreamerCard.ToText(card)`）把该快照输出为中文纯文本，无附加效果或无对应克制时明确写出“无”。CLI 的 `--card <主播id>` 输出一张卡，可用 `--pack`、`--packs`、`--pack-dir` 选择来源；`--cards <包id>` 输出所选整包，可配合 `--pack-dir`。两种入口互斥，不与对战、回放、列表、其它分析或导出选项混用，沿用内容加载和下架检查，只输出资料、不写存档。修改内容后须重新生成资料卡才能更新已有快照。

### 8.2 本地设置与存档

`FileSaveStore` 在调用方指定的本机根目录保存设置、档案和回放，不上传数据。设置缺失或 JSON 损坏时使用默认值，旧版本补齐字段并升级为当前版本。命令行沿用 `--save-dir`，Unity 使用 `Application.persistentDataPath`，首次缺少设置文件时迁移原 PlayerPrefs；冒烟验收只使用内存设置，不读写玩家设置存档。正常设置读写失败时保留本次内存选择并显示提示；读取失败后不自动写回默认值覆盖原文件。

设置的可选布尔字段 `colorblindMode` 对应色弱配色开关。缺省、null 或错误类型均为 false；true 序列化为 `"colorblindMode":true`，false 省略此可选字段，保持旧默认设置 JSON 和版本 1 兼容。显式 false 也可读取，开关可通过 `FileSaveStore` 保存和恢复。

回放名称只允许 ASCII 字母、数字、下划线和连字符，并拒绝系统设备名。管理范围包括旧自动命名回放、可解析的自定义名称对战记录，以及通过 `SaveReplay` 保存并由隐藏索引登记内容摘要的其它载荷；未登记且不是对战记录的外来 JSON 不参与清理。所有管理的回放按修改时间倒序排列，合计最多保留 50 份；覆盖保存成为最新一份。索引损坏或内容摘要不匹配不能作为删除外来文件的依据。暂时不可读且无法确认的文件不列出或删除，已有摘要登记保留，解锁后的下次保存重新纳入清理。

写入采用独占锁和临时文件替换，累计档案持锁完成读改写。新回放已经写入但索引更新或旧回放清理失败时，报告 `ReplayRetentionException`，保留新文件并继续记录本局战绩。路径检查拒绝越界及重解析点；战报输出不能覆盖设置或回放管理索引及其临时路径。文件命名与保留顺序使用的时间不参与战斗结算。

### 8.3 画面动画时间线

`BattleTimeline.Build(events, from, to, speed)` 把 `Battle.Events` 的半开区间 `[from, to)` 转换为纯 C# 的 `AnimCue` 列表，子区间从 0 秒开始。`EventIndex` 保留事件在原列表中的绝对下标，`LogIndex` 保留原日志下标；`Side`、`Slot`、`Id`、`Amount` 用于定位提示及显示引擎已经结算的变化，不在画面重算规则。返回列表和每个提示都是独立对象，不持有输入事件引用。

以下时长以秒计，均为 1 倍速；同一事件内未注明先后的提示同时开始：

| 战斗事件 | 动画提示与时长 | 跳字或参数 |
|---|---|---|
| Act | Cast 0.35，结束后 Projectile 0.25 | 均定位施放者，Id 为技能 id |
| Damage | Hit 0.2、Flash 0.12、FloatText 0.8、HpBar 0.4 | `-数值`，Style 为 `damage`，定位实际受击者 |
| Crit | FloatText 0.8 | `暴击`，Style 为 `crit`；保留事件的施放者定位 |
| Miss | Miss 0.3、FloatText 0.8 | `未命中`，Style 为 `miss` |
| Heal | FloatText 0.8、HpBar 0.4 | `+数值`，Style 为 `heal` |
| Faint | Faint 0.5 | 定位下播者 |
| Switch | SwitchOut 0.3，结束后 SwitchIn 0.35 | 离场者与新登场者的定位见下文 |
| Enter | Enter 0.4 | 定位登场者 |
| StatusAdd / StatusRemove | StatusIcon 0.3 | Style 为 `status`；Amount 为剩余次数或回合，移除时为 0 |
| FieldAdd / FieldRemove | FieldBanner 0.6 | Style 为 `status`；添加保留原 Amount（回合、-1 或印记增量），移除时为 0 |
| StageChange | FloatText 0.8 | 如 `互动 +1`、`抗压 -1`；Style 为 `stage-up` / `stage-down` |
| End | End 0 | 保留胜方 Side，平局为 -1 |
| PpChange / Info | 无 | 不占用动画时间 |

同一事件的提示共用 EventIndex，下一事件在上一事件全部提示结束后开始；同 LogIndex 不代表同时播放。唯一并行例外是输入中紧邻的 Crit 和 Damage：二者同时开始，后一事件在两者全部提示结束后开始；各自保留独立的事件、日志与目标定位。独立 Crit 正常占用 0.8 秒。区间外的 Damage 不与区间内 Crit 配对。

Switch 事件只标识离场者。SwitchIn 在当前区间内跳过不生成提示的 Info/PpChange 后，如果下一条可见事件是同 Side、Turn、Node 的 Enter，采用该 Enter 的 Slot 和 Id；其 EventIndex 和 LogIndex 仍属于 Switch。找不到或范围已截断时，保留 Side，以 Slot=-1、Id=null 表示尚未确定新主播，播放器不可据此显示旧主播重新入场。后续 Enter 仍独立生成 Enter 提示，不吞并事件。

`speed` 是有限数值倍速：所有 Start、Duration 除以正倍速；小于等于 0 时保留全部提示与元数据，把 Start、Duration 全部置 0，以便直接呈现终态。NaN、无穷倍速、换算后开始时间或时长（含结束时间）溢出的极小正倍速、非法范围、范围内空事件及未知事件类型报参数错误。空区间或只有不生成提示的事件返回空列表。`TotalDuration(cues)` 返回全部 `Start + Duration` 的最大值，空列表为 0，不要求调用方列表已排序。

跳字、能力名和错误文字通过 `Loc` 的 `timeline.*` 键取得，中文原表与 Core 内置表同步。能力名为互动、抗压、才艺、定力、反应；未知能力显示“能力”。Build 在开始时读取一次当前文本表；相同事件、范围、倍速和文本表得到相同结果，不读取系统时间、不使用随机数，也不改写 Battle、事件或日志。Unity 播放器由后续画面任务实现。

### 8.4 战后关键回合

`BattleReview.KeyMoments(battle, viewerSide, max = 5)` 只读取日志、每行事后人气快照与结构化事件，不读取当前队伍或重新模拟规则，不消耗随机数。返回 `KeyMoment` 的回合、类别、经 `Loc` 格式化的文字及有符号 `Swing`；正数表示查看方人气差改善，负数表示恶化。非法查看方抛参数异常，非正的 `max` 返回空列表。

复盘采用以下展示口径，不改变对战规则：

- **人气差与评分**：将双方全队剩余人气分别求和，取查看方减对方。每回合净变化以该回合之前的最后快照为基线、该回合最后快照为终点；历史的首张快照只作基线。`ko`、`control`、`switch` 都使用所在回合的净变化作为 `Swing`。计和使用长整数，输出分数超出 int 时截到边界。
- **ko**：每次 `Faint` 提示谁下播及该时刻双方在播人数。事件没有伤害来源字段，因此不推断谁击倒谁，也不把反噬、反弹或持续伤害归因于最近出招者。
- **swing**：只选全局绝对净变化最大的非零回合，相等选最早回合；文字给出变化前后的人气差。
- **control**：同一方、同一号位曾有成功的控制类 `StatusAdd`，且行动节点实际记录“无法行动”或“刚回过神来，本回合来不及行动”，才记一次行动损失。免疫、仅施加状态、未轮到行动就下播或换下均不足以形成提示。
- **switch**：只跟踪主动换人的 `Switch`→`Enter`，不把补位当主动换人。观察新人这次在场期间的真实普通伤害：受到明确“赛道被克”的攻击，或作为出招者打出明确“赛道克制”。每次入场的每个方向最多提示一次，允许收益出现在后续回合；再次换人或下播立即停止该次跟踪。固定伤害、反弹、未命中和仅预览不算克制收益。
- **comeback**：从 `End` 确认查看方最终获胜后，取其首次在回合末全队剩余人气不超过对方一半（对方大于零）的回合作为落后记录的起点；`Swing` 为该起点到终局的人气差改善。此提示只说明历史落后后获胜，不声称某个操作造成逆转。未结束、平局及查看方落败不生成此类提示。

先按 `abs(Swing)` 降序选前 `max` 条，同分按回合、日志顺序稳定选择，再按回合与日志顺序输出。相同回合允许多种事实并列。控制行动损失和克制标记目前依赖引擎的既有中文日志格式；以后迁移这些日志时须同步此识别器，不能用当前属性补算历史。人名和状态名来自历史文本，其余复盘模板均在语言表。

命令行完成对战时打印复盘，联网客机使用自己的查看方；完整回放默认查看 0 方并标明视角。Markdown 战报末尾追加“关键回合”，默认 0 方，也可用 `Markdown(battle, viewerSide)` 指定视角；未结束的战报显示尚未结束，所有新增文字沿用 Markdown 转义。

### 8.5 本地录像库

`ReplayLibrary(string directory, int maxCount = 200, Func<DateTimeOffset> clock = null)` 管理调用方指定目录内的录像，`maxCount` 必须至少为 1。可注入时钟以便测试；未注入时使用当前时间，保存日期统一为 UTC。时间只用于本地命名、筛选和保留顺序，不参与 `Battle.Rng`、对战记录的随机检查点或战斗结算，也不保存账号及设备信息。

公开接口为 `string Save(BattleRecord r, BattleSummary s, string note = null)`、`List<ReplayEntry> List(ReplayFilter f = null)`、`BattleRecord Load(string id)`、`void Delete(string id)` 和 `void SetNote(string id, string note)`。`Save` 使用时间戳与种子生成 id，同名时追加碰撞序号。`ReplayEntry` 包含 `Id`、`Date`、`PackId`、`Names`、`Teams`、`Winner`、`Turns`、`Note`、`IsCorrupt` 和 `Error`；双方名字与阵容按 0 方、1 方排列，阵容来自记录中的禁用及首发重排前原始队伍。旧记录未保存名字时，沿用回放的“你/对手”。`BattleSummary.From` 将真实对战的 `Winner` 及记录中 `Turn` 事件数量分别保存为 `Winner`、`Turns`；这两个字段不改变原有 `ToText()` 输出。正常录像的胜方为 0 或 1，-1 表示平局。

每份录像保存为 `<id>.json`，保留完整的对战记录字段，并在同一 JSON 根对象的 `library` 字段中附加 `date`、`winner`、`turns`、`note` 元数据。`BattleRecord.FromJson` 及回放仍可直接读取此文件。`index.json` 单独保存列表缓存，每次 `List` 扫描录像文件重建；索引丢失或损坏不影响从录像恢复信息，也不能以索引中的路径或条目作为删除文件的依据。单个文件或元数据损坏时，该条目以 `IsCorrupt = true` 和 `Error` 标记，不能加载，也不自动删除；其它录像仍可列出和读取。

`ReplayFilter` 支持 `StreamerId`、`PackId`、可空的 `Winner` 及可空的 `From`、`To`。多个条件同时满足才匹配；主播 id 匹配任意一方的原始阵容，包 id 按记录值匹配，胜方按 0、1 或平局 -1 匹配，日期范围包含两个端点。列表按日期及 id 稳定排序。损坏条目在任何筛选条件下仍返回并显示错误，避免被筛选条件隐藏。

容量计算包含全部正常录像；非空白备注视为收藏，收藏计入总数但不自动删除。超出 `maxCount` 时，从最旧且没有备注的正常录像开始清理，直到满足上限或只剩收藏；全部收藏时允许超出上限。收藏已经占满容量时，新保存的无备注录像也可能立即被清理。`SetNote` 清空备注或改为空白时同样触发整理。损坏条目不计入容量且始终保留，只有调用方显式 `Delete` 才删除。

所有读写和删除限制在给定目录内；id 仅允许 ASCII 字母、数字、下划线和连字符，拒绝 `..`、路径分隔符、系统设备名和索引等管理文件名。根路径及访问的文件不允许经过重解析点。写入持有独占锁，并通过临时文件原子替换，避免并发保存覆盖或留下半份 JSON。新录像文件已经写入后，索引或清理维护失败时抛出带 `ReplayId` 的 `ReplayLibraryMaintenanceException`，调用方报告维护失败，并继续保存本局档案及其它独立产物。

CLI 在 `--save-dir` 指定目录下的 `replay-library` 子目录自动保存完成对局，同时兼容原有回放存储；8.2 的 `FileSaveStore` 及旧 `replays` 目录最多 50 份的规则保持不变，两者独立管理。`--replays` 列出新库，`--replay <id>` 从新库回看，也继续接受原有回放文件路径。回看不新增录像或累计档案战绩。联网对局须完成终局哈希校验及连接收尾后才保存；新库、旧回放、战报及档案分别处理保存失败，任一项失败不阻止其它项。战报输出不能覆盖录像库、其索引、锁或临时路径。

### 8.6 组队阶段的对位建议

`TeamAdvice.For(db, mine, theirs)` 接受双方公开的原始六人阵容，沿用 `TeamCheck` 的人数、重复及成员检查。返回只读的 `TeamAdviceResult`：`BanSuggestion` 为一位建议禁用的对手；`LeadSuggestions` 为我方前两位首发候选；`Threats` 为对方前两位主要威胁；`Answers` 按威胁顺序给出我方相对最佳应对人选。条目的 `Index`、`Id` 用于程序定位原阵容，显示使用 `Name`、`Reason`；应对条目分别保留威胁和应对者的原阵容下标、编号、名字及理由。

建议复用 `DamageCalc.Matchup` 分别计算我方对敌方与敌方对我方的开场伤害百分比矩阵，保留该预览对完整后排、首发重排和可用技能的处理。首发与威胁优先按对全队的双向伤害百分比净差总和排序，再比净差为正的对位数量及技能赛道克制覆盖人数，最后按原阵容顺序稳定决胜；建议禁用排名第一的威胁。每个威胁的应对者优先按该单格净差排序，再比承伤较低、技能赛道倍率较高，最后按我方原阵容顺序。

用于辅助决胜的赛道覆盖只读取技能表：普通及第五技能中，威力和初始 PP 都大于 0 者，按技能赛道对目标主、副赛道的倍率乘积取最高值；超过 1 计为覆盖该目标。不含同赛道加成，也不把它当作实际行动合法性判断；技能能否使用及实际预览伤害仍以 `DamageCalc.Matchup` 为准。

结果只说明开场伤害预览与赛道关系，不等于胜率，也不保证某位应对者能击败威胁。`Scope` 和理由模板通过 `Loc` 生成，显示主播名与中文说明，不把内部编号当作文案。建议接口不接收 Battle 或对方的秘密选择，不改变输入、内容库或实际对战随机流；排序不用随机数。

CLI 的 `--advice` 仅用于带 `--ban` 或 `--lead` 的新本地对局，在首次禁用/首发选择前显示一次双方原始六人阵容的建议。两阶段同时开启时在禁用前显示，禁用后不将五人阵容送入六人对位表，也不读取尚未公开的首发选择。同屏双人、赛事、回放、联网、独立分析和列表模式不接受此选项。是否显示建议不改变电脑选择和战斗结果。

### 8.7 玩家输入的显示文字

`TextInput.Clean(raw, kind)` 返回只读的 `TextInputResult`：`Text` 为清理结果，`Message` 为中文调整原因（未调整时为空），`Changed` 表示与原值不同，`UsedDefault` 表示使用了默认文字。昵称、队伍名、房间名、录像备注分别使用 `PlayerName` / `TeamName` / `RoomName` / `Note`，上限为 12 / 16 / 24 / 60 个 Unicode 标量；补充平面字符计一个，组合标记各计一个，不截断代理对。

依次移除控制字符、Unicode Format 字符（含零宽连接符和双向控制符）、行/段分隔符、组合字素连接符 U+034F 及孤立代理项；其余 Unicode 空白统一为半角空格、连续空格合并并去除两端空格。变体选择符及普通组合标记保留，不折叠全角字母、数字或标点。清理后按 6.3“文本检查”共用的 `TextLint.DefaultBannedWords` 词表进行 ordinal 子串匹配，以等标量数量的 `*` 替换，再截断至该类型上限。空值分别使用“玩家”“我的队伍”“对战房间”“无备注”；提示说明调整类别，不回显被移除的原文。

网络会话的 `NameInputs` / `DisplayNames`、`ViewFor`，同屏会话的 `ViewFor` / `DisplayLog`，局域网 `LanRoom.NameInput` / `DisplayName`，队伍预设 `NameInput` / `DisplayName`，录像条目 `NameInputs` / `DisplayNames` 和 `NoteInput` / `DisplayNote` 是接收数据后的显示入口。`BattleViewModel.From` 清理双方昵称。`TextInput.ForDisplay` 克隆对战后清理昵称和当前日志模板中的玩家位置（登场、禁用、首发、胜利、投降、和局提议及拒绝或接受），不对整段日志做截断或全局子串替换；源对战、随机流、结构化事件和战斗数值保持不变。此副本仅供呈现，不替代原始记录保存或联网结算。CLI 的联网、同屏开场与交接、局域网、回看、结算、计时提示、录像列表、赛事报名/续赛/排名和 Markdown 导出均使用这些入口；尚未合入的画面或观战入口也应采用相同接口。

兼容边界：现有握手、`BattleRecord`、分享码/队伍码、队伍预设存储及录像库保存/备注修改仍保留原文字，现有验收要求它们逐字往返。录像库原始空备注仍表示未收藏，不能用显示默认值反写存储。Core 的原始日志、统计和 `BattleReport.Markdown` 继续保真，CLI 在呈现前传入显示副本。SD-LAN-1 仍按既有 24 个 UTF-16 代码单元截断，CLI 仍拒绝原来的空白或控制字符房名与同屏昵称；合法新房名在广播前清理，额外的协议截断给出提示。是否迁移底层保存/同步语义及广播长度，须在 PR 的“需要决定”确认后另行统一版本与验收。

### 8.8 战斗记录筛选与搜索

`Core/View/LogFilter.cs` 提供 `LogQuery`，公开字段为 `int? Turn`、`int? Side`、`HashSet<string> Kinds`、`string Text` 和 `bool OnlyImportant`。`LogFilter.Apply(battle, query)` 返回匹配的 `Battle.Log` 原始下标，按下标升序排列；空查询或所有条件为空时返回全部非 null 日志，不压缩或改写源列表。各维度同时满足才匹配；`Kinds` 内任一成员匹配即可，null 或空集合不限制类型。

`Turn` 精确匹配 `LogEntry.Turn`；`Side` 精确匹配 `LogEntry.Side`，包括表示全局记录的 -1。伤害行标记受击方，结束行标记全局，不能用结构化事件的 `Side` 替换日志归属。`Kinds` 匹配日志的 `Kind` 字符串，采用区分大小写的 ordinal 比较，不沿用调用方传入集合的 comparer，也不把事件类型当成日志类型。

文字搜索对查询和日志正文做 Unicode NFKC 规范化，再用 `OrdinalIgnoreCase` 作子串匹配，因此忽略全角半角和大小写，但不去掉重音或空格。null 或空串不限制文字；孤立代理项仅在搜索副本中替换为 U+FFFD，再进行规范化，不修改原文。每次查询只规范化查询文字一次。

`OnlyImportant` 只保留已有记录能确认的重要结果，优先通过结构化事件的 `LogIndex` 对应日志：

| 重要结果 | 判定依据 |
|---|---|
| 下播、暴击、换人、对战结束 | `Faint`、`Crit`、`Switch`、`End`；不据此猜测击倒者。 |
| 换人或补位登场 | 对应换人、补位节点的 `Enter`，开场登场不计入。 |
| 控制生效、解除或损失行动 | 控制类状态的 `StatusAdd` / `StatusRemove`，以及日志明确记录的实际受控跳过行动。 |
| 直播间效果生效 | `FieldAdd` 记录获得、刷新或非零印记变化；效果造成的回血、伤害、反弹、免疫、倍率变化及印记增威，只有现有日志明确记录来源和结果时计入。 |
| 人设触发 | 成功触发的 `trait` 日志、带人设来源前缀的 `Heal`，以及明确的人设伤害倍率提示。 |
| 赛道克制或被克制 | 实际伤害行尾注中明确记录的赛道克制结果，不根据当前赛道或数值重新计算。 |

未触发提示、弱化类状态、普通伤害、单纯消强化或效果到期，不因此自动成为重要记录。未记录来源的先制修正不能从当前状态倒推。部分来源和结果尚无独立结构字段，需识别少量现有中文日志模板；日志格式变化时须同步维护这些识别，不能靠任意关键词命中或重新执行规则补齐历史。模板识别先按事件槽位或该条日志的 `Side` / `SnapActive` 剥离完整主播名，再识别完整内容名称和固定正文；名称中合法的逗号、引号或模板片段不能制造重要事件，也不能使真实效果漏选。缺失或无效的历史槽位不回退到当前首发。

`LogFilter.GroupByTurn(battle)` 返回按回合数升序排列的 `LogGroup`，每组含 `Turn`、`Indices` 和 `Summary`；`Indices` 保留该回合所有非 null 日志的原始顺序。摘要以“第N回合：”开头，接最多三条重要日志原文，按原顺序用“；”分隔；没有重要记录时，取第一条非空且不是回合标题的原文；仍无可用正文时使用“第N回合：共M条记录”。摘要不改写成未经日志证实的“谁击倒谁”。

筛选与重要性标记对给定内容库按日志和事件线性扫描；模板匹配还检查内容库中的完整来源名称，文字规范化成本随正文长度增加。不跨调用持久缓存可变日志，也不修改战斗、日志、事件或随机数。显示界面可先取得 `TextInput.ForDisplay(battle)` 副本，再在同一副本上筛选、分组和显示摘要，使搜索结果对应玩家实际看到的文字。

## 9. 电脑对手（`Ai.cs`）

估算每个可用技能的价值：伤害技能按“估算伤害 / 对手当前人气”，能击倒加大权重，先手击倒再加；状态、能力、直播间效果、驱散、净化按局面加分。普通难度的随机扰动上限、换人概率及其它策略系数由 `AiWeights.Default` 提供，困难难度使用 `AiWeights.HardDefault`。T-95 的自我对弈协议、完整参数与强度验证见 `ai-tuning.md`；这些参数只影响选择偏好，不改变合法行动和战斗结算。简单难度继续使用 `AiWeights.Legacy` 的历史策略（普通估值分支随机扰动上限 0.08、换人概率 60%，简单难度自身仍不主动换人）。补位选对位分最高的；简单难度补位使用旧权重，普通难度使用当前权重。

专家保留三次采样、第一层前三名及分数并列者的向前搜索，默认每次行动或补位最多模拟 **128 个节点**。一个节点是副本中一次实际执行的 `ResolveTurn` 或 `Replace`，调用前扣除；双方补位分别计数。克隆、评分、困难难度启发式和已经结束的分支不计节点。预算限制确定性的模拟工作量，不读取系统时间；具体机器上的耗时由 `Tools/Bench` 测量，不承诺任意硬件下的墙钟时限。

`Ai.ChooseExpert(battle, side, budget)` 与 `Ai.ChooseExpertReplacement(battle, side, budget)` 返回 `ExpertDecision`：`Action`、`SimulatedNodes`、`BudgetExhausted`。补位的 `Action` 是 `SwitchTo`。`Ai.Choose` / `ChooseReplacement` 的专家入口使用 `ExpertBudget.Default`；显式 `new ExpertBudget(maxNodes)` 可调节上限，0 合法，负数拒绝，null 预算拒绝。预算对象不可变，每次决策重新计数，可安全复用。`ExpertBudget.Unlimited` 用 `int.MaxValue` 保留旧专家的完整搜索顺序、估值与平局随机数处理，供强度对照。

预算耗尽时只使用已完成的结果：第一层优先比较完成全部三次采样的候选；若没有，则比较已有完整样本的均值，忽略未完成补位的分支。第二层只在某个候选的全部样本扩展完成后更新评分；中断时从已完整扩展者中选择，尚无完整扩展者则使用第一层评分，避免混用不同搜索深度。补位须完成自身及对方必要补位与后续采样才计为一个完整样本。没有任何完整样本（含零预算）时返回顺序中的首个合法行动或可补位成员。仅当仍需模拟而无法取得下一节点时 `BudgetExhausted=true`，恰好用完并完成搜索不算截断。所有模拟在独立副本上执行，真实战斗只可能因最终并列选择消耗自身随机数。

### 9.1 主播的出招风格

内容包的每条主播定义可选填 `aiStyle`，对应 `StreamerDef.AiStyle`；例如在该主播对象内添加 `"aiStyle": "aggressive"`。省略或设为 `null` 表示没有专属风格，使用该难度的默认策略。风格名区分大小写，只接受下表三个名称；未知名称在 `ContentDb.Validate()` 时抛出 `KeyError`，不静默回退。

| `aiStyle` | 风格 | 偏好方向 |
|---|---|---|
| `aggressive` | 猛攻 | 提高伤害和击倒收益，减少主动换人倾向。 |
| `defensive` | 稳守 | 提高回复、护盾等防护效果和改善对位的换人收益。 |
| `tricky` | 花招 | 提高施加状态、驱散和削减 PP 的收益。 |

`AiStyles.Get(name)` 返回对应的独立 `AiWeights` 实例，修改返回值不会污染预设或其他主播；未知名称（包括 `null`）返回 `null`。预设改变的是电脑的选择偏好，不改变技能、人设、合法行动或实际结算规则。

普通难度每次选行动时读取当前场上主播的风格：有风格时使用其预设，优先于调用者传入的普通难度权重；无风格时继续使用传入权重或默认值。换人、补位后，下一次选择按新场上主播重新读取，不沿用上一位的风格。困难和专家保留原有搜索流程，在候选评分中使用对应风格与历史普通估值（`AiWeights.Legacy`）的差额作为偏好；计算差额不额外消耗随机数。T-95 不调整风格预设：有风格演员的 Hard 选择保留 Legacy 基底；专家模拟中的每个演员按自身当前风格选择基底，无风格者跟随新 Hard 权重。简单难度完全忽略风格，包括其调用普通估值的分支。

T-53 引入风格配置时保留了未配置风格者的原有选择和随机数消耗；T-95 随后按上一节更新其默认策略权重。两项任务均不为现有主播添加 `aiStyle`，今后由内容任务决定谁采用哪种风格。内容指纹仍保留兼容性：全包主播均无风格时，`ContentHash()` 不增加编码；只在存在配置时，于原编码末尾追加独立标记和按 ordinal 主播 id 排序的风格配置，使不同风格参与内容一致性检查。

## 10. 联网对战（进行中）

联网对战使用相同版本的引擎、规则数据、内容包和种子，双方只交换行动，每回合结算后在同一节点比对 `Battle.StateHash()`；哈希读取不推进随机数，也不改写状态或日志。

`ContentDb.ContentHash()` 对加载、合并和改名后的内容计算 FNV-1a 64 位指纹，返回 16 位小写十六进制。范围包括包 id/名称/声明、属性与类别名称、赛道与克制表、状态、直播间效果、人设、技能（含硬撑）、主播、赛季限制，以及这些定义的全部显示文字和数值。字典按 ordinal 键顺序、主播按 ordinal id 顺序写入；技能槽、效果和赛季列表保留原顺序。字符串采用 UTF-8 长度前缀，null 与空串区分；整数和 IEEE-754 双精度值固定小端序，布尔使用单字节，各集合包含数量。每次调用重新读取当前内容，不缓存可变定义。指纹用于内容一致性检查，不用于安全认证；`Tools/PackCheck` 在检查和列出内容包时显示它。

内容指纹编码以字符串 `StreamDuel.Content.v1` 为前缀，FNV 初值和质数与下述状态哈希相同。整数及长度为 4 字节，双精度值为 8 字节；null 字符串或集合长度为 -1，每个定义对象先写入存在标记。JSON 空白、对象键排列和等价的省略默认值不影响指纹；技能槽及效果顺序影响指纹。

T-109 新增的赛道 `symbol`、`colorAlt` 是上述显示字段范围的明确例外，采用 4.1 的展示兼容约定；不改变已经纳入指纹的原赛道颜色、名称或其它字段，也不放宽录像的内容一致性检查。

行动编码为 `S0`～`S4`（技能）、`W0`～`W5`（换人）、`P`（跳过）或 `Q`（投降），区分大小写且不允许空白或额外字符。硬撑和受控跳过仍由 `Normalize` 派生，不作为发送的行动编码。`Q` 仅用于已启用终止功能的公开输入接口，网络会话将它转为 10.4 的控制请求，不接受把 `Q` 塞入旧承诺/公开消息。

### 10.1 同步会话与协议版本 3

`Core/Net/` 中的 `NetSession` 负责握手、收集双方承诺和公开选择、结算及哈希确认，并提供独立的固定快捷语；`INetTransport` 只传递字符串消息，要求每个方向先进先出、不丢不重。`LoopbackPair.Create` 提供线程安全的两端内存队列，不连接真实网络；`TcpTransport` 提供本机或可信局域网的 UTF-8 按行传输。会话的 `Poll`、`Submit`、`SubmitReplace`、`SendQuickChat` 和可选计时的 `Tick` 由同一调用线程依次执行；每次 `Poll` 最多取出 64 条消息（包含无效、超额和静音聊天），剩余消息按原 FIFO 留待下次调用，避免聊天洪泛阻塞调用方的计时或输入。

构造参数为内容库、传输端、是否主机、本方六人队伍、名字、可选种子。主机固定为 `MySide = 0`，客机为 `1`；两端的队伍和名字始终按 `[主机, 客机]` 排列。种子只由主机决定，传入 null 时主机在构造时用 `Environment.TickCount` 生成一次；客机传入的种子不参与对战。握手完成前 `Battle` 为 null。双方协议版本、内容包 id 和 `ContentDb.ContentHash()` 必须一致，两支队伍均须通过 `TeamCheck.Validate(db, null, team)`；本方参数非法时直接报错，不开始对战。hello 必须带 `contentHash`，按 ordinal 字符串比较；不一致在构造对战前报“内容不一致”并列出双方指纹，通知另一端。会话保存发出 hello 时的指纹，握手期间本地内容变化也会拒绝；开局后调用者不得改动共享内容库。版本 3 不启用禁用和首发阶段，拒绝版本 1、2 握手及旧版明文 action/replace 消息。旧版本收到未知的 `chat` 类型会报错，因此新增快捷语时按 T-62 的兼容规则将协议从 2 升到 3；承诺、公开选择及哈希流程沿用版本 2。

每条发送消息均为一行紧凑 JSON，不含尾部换行；行分隔由传输实现负责，字符串内的换行、引号和反斜杠均转义：

| type | 格式示例 | 含义 |
|---|---|---|
| `hello` | `{"type":"hello","version":3,"packId":"original","contentHash":"63a758a4fa663be9","seed":42,"name":"主机","team":["bell","enka","shiori","lumi","hane","momo"]}` | 两端各发一次；客机的 `seed` 必须为 null，主机为 uint 整数。检查版本、内容包与指纹、角色及队伍后开局 |
| `commit` | `{"type":"commit","turn":1,"kind":"action","digest":"<64位小写十六进制>"}` | 锁定当前选择，仅发送摘要；`kind` 为 `action` 或 `replace` |
| `reveal` | `{"type":"reveal","turn":1,"kind":"action","action":"S2","nonce":"<32位小写十六进制>"}` | 所有本阶段参与方的承诺齐备后公开编码和随机串；补位使用 `kind: "replace"` 与 `action: "W3"`（队伍下标从 0 开始） |
| `hash` | `{"type":"hash","turn":1,"hash":"0123456789abcdef"}` | 每次本地 `ResolveTurn` 或 `Replace` 后立即发送该操作结果的状态哈希 |
| `chat` | `{"type":"chat","index":0}` | 只发送固定短句编号 0～7；不发送文字、身份、回合或时间，不参与行动和哈希确认 |
| `error` | `{"type":"error","message":"中文原因"}` | 终止会话；对方收到后也进入 Error，不再回复 error |

`NetState` 与提交规则：`Handshake` 等握手；`Choose` 可提交一次行动；`Replace` 仅本方需要补位时可提交一次；`Waiting` 等承诺、公开选择或哈希；`Over` 表示最终哈希也已确认；`Desync` 表示双方哈希不同；`Error` 表示协议、队伍或传输错误。`HasSubmitted` 在本阶段本方提交后为 true，哈希确认并开放下一阶段时清零。错误阶段、重复提交、不可编码动作或非法补位的本地调用抛 `InvalidOperationException`，不发送消息；远端重复、过期、越阶段或格式错误则进入 Error 并发送原因。合法的 AI 派生硬撑/受控跳过由会话转换为 P，结算时仍交给 Core 的 Normalize 判断。

承诺摘要为 `SHA-256(UTF-8(行动编码 + "|" + nonce))`，输出 64 位小写十六进制。每次本方有效提交用 `System.Security.Cryptography.RandomNumberGenerator` 产生 16 字节，再编码为 32 位小写十六进制 nonce；不会从 `Battle.Rng` 取得或向其写入随机数。这是 T-32 唯一允许的额外随机源，用于使承诺无法按有限行动集合直接枚举；nonce 与摘要均不参与战斗、日志、回放或状态哈希，因此相同种子和选择仍产生相同对战结果。

双方行动或同时补位时，本端发送自己的 commit 且收到对方 commit 后，才发送自己的 reveal；每个方向先进先出的传输保证接收方先收到该方的 commit。只有一方需要补位时，仅该方发送 commit，紧接着发送 reveal，不等待无需补位的一方提交。收到 reveal 必须已有该方承诺，所有参与方承诺均齐备，且回合、kind、行动编码和 nonce 格式合法。重算摘要与已保存承诺不同则进入 Error，原因包含“承诺”。未经验证的公开选择不参与结算；重复 commit/reveal、提前公开、无需补位方的提交一律报错。每阶段哈希确认后清除全部承诺和公开记录，下一阶段重新提交。

版本 3 沿用版本 2 的承诺摘要，按任务约定只包含行动与 nonce，回合、kind 在消息外层校验，发送方和会话身份未纳入摘要。它能检测承诺后更换行动或 nonce，但不能阻止对端复制已收到的 digest，再复制其公开的相同行动编码和 nonce；也不解决故意断开连接。是否增加摘要上下文绑定属于后续协议决策。

快捷语编号固定为 0～7，对应“你好、打得好、好险、再来一局、我在想、抱歉手滑、谢谢、晚安”，通过 `Loc` 的 `quickchat.0`～`quickchat.7` 取文本。`QuickChat.Lines` 是首次访问时当前语言的快照；显示消息时调用 `QuickChat.Text(index)`，按当前 `Loc` 查询，因此切换语言不改变已收消息中的编号。不支持自由文字。

`SendQuickChat(index, now)` 只在握手完成且会话未处于 `Error` 或 `Desync` 时发送，`Over` 仍可聊天。编号越界、握手未完成、会话故障，以及非法时间或超出限频均返回 false 且不发送。`now` 由调用方提供秒数，须有限、非负且单调不减；引擎不读取系统时间。发送使用滚动 10 秒窗口，最多 3 条；已发送消息距当前时间达到 10 秒时退出窗口，边界时即可重新发送。

接收消息以本机收到时的 `Battle.Turn` 标记 `Turn`，并将 `Side` 固定为 `1 - MySide`。同一本机回合最多接受对方 6 条有效快捷语，多出的丢弃；静音期间的有效消息仍计入此上限。`MuteOpponent = true` 只阻止新收到的消息进入 `ReceivedChats`，不清除历史，也不在解除静音时补入此前的消息。`ReceivedChats` 是只读列表，其中的 `QuickChatMessage` 记录也不能被调用方修改；握手前或会话故障时不接收快捷语，`Over` 可继续接收。

快捷语消息只接受 `type` 和 `index` 两个字段，`index` 必须是 0～7 的整数，不接受 `text`、`side`、`turn` 等额外字段。合法 JSON 对象的顶层 `type` 为 `chat` 时，编号或消息结构无效就直接丢弃，不影响对战，也不视为掉线。JSON 解析失败时，局部扫描根对象字段；完整确认顶层 `type` 为 `chat`，且没有遇到非聊天或冲突的顶层类型时，按坏聊天消息丢弃。字段顺序、合法 JSON 空白和字符串转义不影响识别，载荷数值只跳过而不转换，因此前置的溢出 `index` 也不会把聊天当作掉线。字符串内或嵌套对象内的 `type` 不算路由头；已确认聊天头之后的截断载荷仍丢弃。无法确认聊天类型或明确非聊天的坏 JSON，以及其它协议错误，仍走原有 `Fault` 流程，进入 `Error` 并报告原因。此扫描仅用于失败的 JSON，不改变正常解析对象的既有重复键行为。

快捷语独立于行动、补位、承诺和哈希确认，不改变 `HasSubmitted` 或这些流程的先后顺序，不追加对战日志或回放记录，不改变 `StateHash`，也不读取或推进 `Battle.Rng`。聊天不会触发新回合或恢复已经结束的对局。

进入 Over 后继续调用 Poll 仍会接收远端 error 并转入 Error，避免只有一端最终哈希被篡改时，另一端忽略稍晚到达的错误通知；Over 允许快捷语，但不允许新的行动、补位或握手。

TCP 在后台线程接收完整 UTF-8 行，由调用线程通过不阻塞的 `TryReceive` 依次取出。连接断开前收到的完整消息优先交付；未完成会话在断开后进入 Error，提示“对方已断开”。本端已确认终局的 Over 状态仅忽略纯传输断开，仍处理断开前排队的 error 和非法协议消息，避免正常退出把已完成对局改成错误。CLI 进入 Over 后用 TCP 半关闭结束发送方向，并继续分批 Poll，直到 `TcpTransport.ReceiveDrained` 确认正常 EOF 与接收队列为空同时成立，确保关闭前的最终哈希错误仍会阻止保存；收尾超时或错误不保存。`PeerClosed` 仍只表示已收到正常 EOF，不能单独作为消息已经处理完的依据。传输收到正常 EOF 后保留发送方向，以便本端仍能报告已收到消息的校验错误。此收尾不增加 JSON 消息或改变协议版本。连接与会话均不提供加密或身份认证，只面向可信本机或局域网。

双方行动收齐后才按固定的 0、1 方参数调用 `ResolveTurn`。补位只收集需要补位的方；双方都需要时先收齐，再固定按主机、客机顺序分别调用 `Replace`，每次调用都单独发送哈希。哈希消息的 `turn` 是**该次操作调用前**的 `Battle.Turn`：第 N 回合结算的哈希标 N，随后补位通常标 N+1；同一补位阶段的两份哈希可以有相同回合号。接收端按操作发生顺序 FIFO 配对保存的哈希快照，不按回合号覆盖。对应快照以字符串精确比较，任一不同进入 Desync，Error 属性写明回合、本端和对端哈希，并发送 error；当前阶段全部哈希一致后才允许下一阶段，终局也必须等待最后一次确认。

会话在开局和每次结算后保存共享 RNG 检查点。界面或 AI 在本端选招、等待时可能消费 Battle.Rng，但这只用于本端决定提交什么行动；正式结算前以及哈希确认后恢复共享检查点，使两端只按相同行动推进同一随机流。哈希使用结算瞬间保存的值，不重新读取被本端建议计算影响后的状态。调用者通过会话提交选择，不直接调用其 Battle 的结算接口或修改战斗状态。

#### 局域网房间发现（SD-LAN-1）

发现数据独立于对战会话，使用 IPv4 UDP 47777 广播，不改变当前对战协议版本或对战随机数。`LanBeacon` 编码紧凑 UTF-8 JSON：`{"magic":"SD-LAN-1","name":"周末对战","port":7777,"protocol":3,"contentHash":"内容指纹","ruleset":"casual"}`。这六个字段均必需；端口为 1～65535，协议为正整数。房名按最多 24 个 UTF-16 单位截断，末尾不拆代理对。完整消息最多 512 字节，错误魔数、缺字段、错误类型、重复字段或非法 JSON/Unicode 返回 null；编码非法房间也返回 null。`Address` 与 `LastSeen` 不写入包，接收时忽略包内同名值，地址仅取实际 UDP 来源。

`LanRoomList.Receive(text, fromAddress, now)` 按规范化的来源 IP 与 TCP 端口更新房间，`Rooms(now)` 返回独立快照；距离最后收到广播恰好 3 秒仍保留，超过 3 秒移除。调用方提供有限、非负、单调的秒数。`LanBeaconSender.Tick(seconds)` 首次调用立即广播，之后每积累 1 秒广播一次，长时间未轮询不补发多份；`LanBeaconListener.Poll(now)` 非阻塞接收。两者都由调用方驱动，不启动后台时钟；通过 `Error` 提供中文套接字故障，关闭或构造失败均释放套接字。监听独占 UDP 47777，拒绝超长数据报和无效 UTF-8，每次轮询限制处理数量，避免持续数据流阻塞界面。

CLI 的 `--lan-host 房名` 默认自动分配 TCP 端口，也可配合 `--host` 指定；仅等待连接时广播，建立连接后停止。`--lan-list` 独立收集 5 秒内见过的房间，结束时把超过 3 秒未更新的条目标为失联，仅为仍可见且协议兼容的房间显示加入命令。列表中的房名、指纹和规则仅供发现与显示，不能代替实际 TCP 握手的内容一致性校验；当前房主广播 `casual` 基础规则，不宣称支持尚未接入网络的其他赛制。发现不保存数据，也不提供公网匹配或 NAT 穿透。

### 10.2 状态哈希

状态哈希采用 FNV-1a 64 位（初值 14695981039346656037、质数 1099511628211），每字节先异或再按无符号 64 位溢出乘法计算。整数固定为 4 字节小端序，布尔为 0/1 单字节，字符串为 UTF-8 字节数前缀加内容（null 长度为 -1），可变长度集合带数量。按回合数、阶段、双方场上位置、双方队伍顺序写入各主播的人气/下播/最后技能、各技能 id/PP、能力等级（`ContentDb.StatKeys` 顺序）、状态 id/剩余、直播间效果 id/回合/层数，再写入 RNG 内部状态和胜负。状态与效果保留列表顺序，因为结算顺序本身有意义。

随后写入内容包 id，再按 0 方、1 方的顺序，分别写入本方补位需求/先手标记/首发选择以及本方各主播 id/号位/所属方/最大人气/登场回合/首次控制免疫是否已用（`FirstControlImmunityUsed`）/本场保命是否已用（`EndureUsed`）和各技能最大 PP/第五技能标记，避免遗漏会影响后续结算的状态。这一尾段的队伍和技能数量复用前段，不重复写入。末尾按 0 方、1 方写入禁用选择（未选择为 -1），再写入禁用后是否进入首发选择（`leadPickAfterBan`）；禁用尚未全部确认时，这些选择也参与比较。显示名字、日志、回放历史及不影响后续结算的累计对战统计不参与哈希；此哈希用于同步检查，不用于安全认证。

### 10.3 对战计时

`TurnClock(turnSeconds, bankSeconds)` 为双方各保存一份基本时间和总时间余额。参数及 `Tick(side, seconds)` 的时间增量必须是有限非负数，side 只能为 0 或 1。构造即初始化首个阶段；`StartTurn()` 重置双方基本时间、清除已提交标记和上阶段超时状态，但不补充总时间。选择行动与需要补位都各自获得一次基本时间；总时间跨这些阶段累计扣除。零基本时间直接使用总时间，两者均为零立即超时。

`Tick` 先扣基本时间，再用超出的部分扣总时间，不出现负余额；两者恰好归零也算超时。`Submit(side)` 停止该方本阶段计时；已经超时后提交不取消超时标记。`TurnLeft/BankLeft/TimedOut` 仅查询，不推进时间。Core 不读取系统时钟，也不消耗对战随机数，调用方传入经过的秒数。

`TurnClock.TimeoutAction(b, side)` 返回原始 `BattleAction.Pass()`；受控时也返回 Pass。该默认选择仍经过 3.4 的既有 Normalize：受控时派生受控跳过，全部技能无 PP 时派生硬撑。`TimeoutReplacement` 返回不是当前场上者、仍在播且人气大于零的最小队伍下标；无候选时返回 −1。计时本身不改变 Battle，只有这些默认选择进入正常行动与补位接口，形成原有日志及回放事件。

`NetSession` 的构造末尾可传 `double? turnSeconds`、`double? bankSeconds`，须成对提供；不传时不启用计时。`Clock` 为启用后的计时器，未启用时为 null；`Tick(double seconds)` 推进会话计时，输入等待和已提交后的 Waiting 阶段均须继续调用。只有主机决定预算，客机采用主机 hello 声明的值。

`Tick` 不隐式调用 Poll。调用方先收取已到达的消息，再推进时间；只读 `TimerRevision` 在新决策阶段或新的公开/哈希等待窗口开始时变化。若本次 Poll 刚开启新窗口，调用方重置计时基线，不把旧窗口的经过时间扣到新窗口上。一次大 Tick 内刚自动发出的 commit/reveal/hash 同样不会倒算发送前的时间为对方响应迟延。

协议为版本 3。新版 hello 附带 `"timerVersion":1` 能力标记；启用计时的主机另附 `"timer":{"turnSeconds":10,"bankSeconds":30}`。主机启用计时时拒绝未声明支持的旧客机；无计时的会话仍接受省略计时能力字段的版本 3 hello；版本 1、2 握手仍会被拒绝。计时数值须为有限非负数。此扩展不更改承诺摘要、行动编码或哈希格式。

每次开放行动或补位阶段重置基本时间，不需要补位的一方停表。本方提交 commit 后停本方表，收到对方有效 commit 后停对方表；对方提前承诺不会压缩本方剩余选招时间。本方超时仅由本端通过正常 Submit/SubmitReplace 提交默认选择，仍须等待并校验双方承诺与公开。任何一端都不能替对方编造行动或 nonce。

启用计时时，若对方在基本时间与总时间均耗尽后再过 10 秒仍未提交 commit，则会话进入 Error，报告掉线。双方所需承诺齐全后，另等待对方 reveal 最多 10 秒；已经结算后，等待 hash 确认也最多 10 秒。三类等待使用独立计数，已提交方不再耗总时间。未启用计时不增加这些等待限制；TCP 终局半关闭与最终错误接收沿用 10.1。各端倒计时是本地经过时间的估计，不参与 Battle 状态哈希；最终行动通过已有同步协议结算。

CLI 的 `--timer 10,30` 启用每阶段 10 秒基本时间和每方全局 30 秒总时间。它以单调 Stopwatch 测量时间增量并显示剩余时间，超时自动提交；联网客机显示房主下发的预算。禁用与首发选择暂不计时，回放不接受此参数。相同选择序列的战斗结果仍可复现；有计时时，实时输入与计算耗时会影响最终提交的选择，倒计时输出本身不要求逐字相同。

### 10.4 可选终止协议版本 4

`NetSession` 构造末尾增加 `enableTermination=false`；默认仍完整保留 10.1 的 v3 握手和普通消息序列。双方显式启用时，`SessionProtocolVersion` 为 `TerminationProtocolVersion=4`，hello 同时带 `terminationVersion:1`，版本或能力不符即拒绝，没有静默降级。CLI 联网入口启用 v4，局域网发现同步声明 v4。投降与求和仅在握手完成、当前选择/补位阶段的输入窗口可用，包括本方已提交而等待对方的窗口；短暂同步或哈希确认期间 `CanSurrender`、`CanOfferDraw`、`CanRespondDraw` 返回 false，调用方等待后重试。原联网会话尚不支持禁用、首发和选人。

`Surrender()` 或 `Submit(BattleAction.Surrender())` 提交投降；`OfferDraw()` 提议，`RespondDraw(bool)` 回应，`DrawOffered` 表示对方提议待答。为避免两端在不同时间收到控制消息、行动和公开选择而形成不同录像，新协议在普通结算及控制操作前使用同一确认窗口：主机 freeze、客机 ready、主机 apply，之后双方比较原有 hash。客机可先发 wake 请求窗口。每个消息携带阶段编号和回合，freeze/ready/apply 还携带递增序号，双方以相同顺序应用已确认的请求。

同一确认窗口的双方投降判平局；单方投降优先于本窗口的和局或普通行动，直接判该方负。已经发送 ready 的请求不能再改；后来的输入属于下一次可输入窗口。无投降时按 0、1 方顺序记录提议或回应，接受即平局；仍未结束且双方行动已公开齐全时再执行原行动。拒绝或仅提出和局不会撤回已承诺行动、重置该阶段计时预算。终局必须等双方哈希确认，错误或不同步仍不保存胜负。详细字段与状态约束见 `docs/netplay-protocol.md` 第 10 节。

## 11. 规则修饰器

规则修饰器用于对战房间的自定义规则和特殊赛制。构造对战时通过 `BattleOptions.Modifiers` 传入 id 列表，可同时启用多项；省略、`null` 或空列表均不启用，原有对战规则保持不变。`BattleModifiers.All` 提供可用修饰器的 id、中文名称和说明。

id 按 ordinal 比较，区分大小写；未知 id 在构造对战时抛出 `KeyError`。构造时将列表复制、去重并按 ordinal 排序，因此重复项只生效一次，输入顺序不影响结算、日志或哈希。对战持有独立的只读规则列表；之后修改调用方的列表或回放记录，不会改变正在进行的对战。完整克隆及 AI 的模拟副本都保留相同规则，不重复施加初始化效果。

修饰器从开局到结束持续有效，不能被消回合、消强化或净化移除。初始化只改变本局战斗实例，不修改共享技能、主播或内容包定义。实际开场时在“开场”节点列出全部启用项；禁用或首发选择尚未完成时不提前触发开场授予效果。

| id | 作用与时机 |
|---|---|
| `half_pp` | 在禁用、首发选择及登场人设之前，将双方全队所有普通和第五技能的 PP 上限减半，向上取整，当前 PP 同步设为新上限；例如 5 变为 3，1 仍为 1，0 仍为 0。后续回复 PP 不能超过新上限；人设免扣 PP 仍遵守原规则。整数计算使用 `原上限 / 2 + 原上限 % 2`，避免加 1 溢出。 |
| `stage_cap_3` | 将双方五项能力等级的上下限改为 -3～+3，适用于技能、人设及偷强化等所有能力变化。偷强化仍将目标正等级归零，获得方超出 +3 的部分舍去。能力倍率公式、消强化与下场清零不变。 |
| `sudden_death` | 从第 10 回合（含）起，在回合结束节点，按该节点原有的反应顺序，对每位仍在场且未下播的主播，在其自身弱化状态、直播间效果和回合结束人设全部结算后，扣除 `max(1, floor(本局最大人气 / 16))` 人气，并记录原因和实际扣除量。后排不受影响。 |
| `hype_start` | 禁用和首发选择完成、双方实际首发的登场人设全部结算后，在“开场”节点各授予 1 层「热度」。整局仅授予这一次，主动换人和补位不再授予。该层数遵守热度上限及消耗规则，不能被消回合，下场时清除；规则本身不会在下次登场时补回热度。 |
| `no_switch` | 禁止双方主动换人，合法行动列表不再提供换人；直接提交换人仍经过原有 `Normalize` 纠正规则。禁用、首发选择和下播后的补位不受影响。 |
| `hp_x2` | 在禁用、首发选择及登场人设之前，将双方全队主播的本局最大人气和初始人气乘以 2。按最大人气比例计算的回复、持续伤害及猝死均读取倍增后的最大人气；普通伤害公式和固定伤害数值不变。原始最大人气超过 `int.MaxValue / 2` 时，构造对战抛出 `KeyError`，避免整数溢出。 |

猝死沿用持续伤害处理：不受伤害倍率影响，不反弹，不解除挂机，不触发被击中后人设或击倒回复；一次性保命 `T_ENDURE` 和下播人设仍可响应。顺序遵守 3.2，任意一方全灭立即结束，另一方尚未执行的回合结束步骤（包括猝死扣除）不再执行；不会先同时扣除两边人气再判断胜负。同速时沿用对战 `Rng` 决定本节点顺序。提前因其他伤害下播的主播不会再承受猝死扣除。

显示层读取本局的能力上限、技能 PP 上限和最大人气。技能及人设的战斗说明按本局上限生成，组队时和无修饰器时仍保留原说明；不改写共享内容包的文案或数值。开场热度、骤降伤害和受限能力变化沿用结构化事件入口，事件中的变化量为实际生效值，完整克隆和回放保留一致的事件序列。

对战记录通过可选的 `modifiers` 字符串数组保存规范化后的列表，`Replay.Run` 将其还原为同一组构造选项。旧记录缺省该字段，或字段为空数组，均按无修饰器回放；无修饰器记录省略该字段，不改变原有记录格式。`StateHash()` 使用对战自身的规则快照：启用修饰器时，在 10.2 的既有编码末尾追加字符串 `StreamDuel.Modifiers.v1`、列表数量及各 id；未启用时不追加任何字节，保持旧哈希兼容。启用规则不同，即使当前人气等可见状态相同，也参与哈希比较。

## 12. 本地小型赛事

`Tournament(db, format, rounds, options)` 管理朋友间的报名、对阵和结果，原有 `roundrobin`（循环赛）与 `swiss`（瑞士轮）保持既有行为；`single`（单败）与 `double`（双败）见 12.2。报名通过 `AddPlayer(name, teamCode)` 读取 T-56 的队伍码，按当前内容包检查六人队伍是否合法；报名编号从 0 开始，同名玩家仍由编号区分。至少两人才能排第一轮，开始后不再接受报名。

循环赛每两人交手一次，使用固定报名顺序的轮转排表；偶数人数进行人数减一轮，奇数人数进行人数轮，每人恰好轮空一次。循环赛的 `rounds` 必须为 0，不能用它截短赛程。瑞士轮的 `rounds=0` 表示默认 `ceil(log2(人数))` 轮，也可指定正整数轮数；奇数人数的轮数不得超过人数，以保证每人最多轮空一次。

瑞士轮按当前排名优先安排分数接近的对手，优先寻找没有重复对阵的整轮配对，无法全部避开时减少重复对阵。奇数人数从未轮空者中优先选择低排名玩家轮空，必要时调整轮空人选以避免重复对阵。配对采用确定性顺序，不使用额外随机数。每轮对阵在报告任何本轮结果前固定；`NextRound()` 在本轮仍有未报结果时返回当前轮，全部完成后才生成下一轮，赛事结束后返回空列表。

`Pairing` 的双方编号为 `Player0`、`Player1`；轮空时 `Player1=-1`，自动记 `Player0` 获胜。普通对阵通过 `ReportResult(pairing, winnerSide)` 报分，`winnerSide` 为 0、1 或 -1（平局）。只接受当前赛事生成的未报结果对阵，不能覆盖已报结果或手工改写轮空。

每胜得 3 分、平局得 1 分、负得 0 分，轮空记一胜得 3 分。排名先比总积分，再比对手分：对手分为每场已完成的实际对局中，对手当前总积分的总和；重复交手逐场计入，轮空无对手贡献，未报结果对局不计入。前两项仍相同者组成同分组，以组内已完成直接对局获得的积分比较，避免多人互胜时使用两两比较产生循环；最后按报名先后排序。排名和对手分由完整结果重新计算，随着后续报分更新。

`ToJson()` / `Tournament.FromJson(db, json)` 保存并恢复版本 1 的赛事，记录内容包 id、内容指纹、赛制、配置轮数、报名队伍码、已排出的轮次与各场结果（未报结果为 null）。读取时校验内容一致性、队伍和赛程，按历史顺序重建配对并核对存档，不信任外部提供的积分或排名缓存；损坏存档拒绝载入，未完成轮可继续报分。

CLI 的 `--tournament <文件>` 创建或继续赛事，手动录入已完成的对局结果；`--auto` 用普通难度电脑完成未报结果的对阵。自动对局种子由稳定的对阵编号派生，AI 选择和对战结算只使用该 Battle 的随机流。赛事保存与玩家战绩、普通对战录像分别管理。

### 12.1 完整赛事战报与录像关联

`Tournament.Pairings` 只读列出已排出的全部对阵；读取历史不调用会推进赛程的 `NextRound()`。`TournamentReport.Build(t, lib)` 建立不可变报告，`ToText()` 输出中文纯文本，`ToJson()` 输出版本 1 的 JSON。积分榜直接采用 `Tournament.Standings()` 的排序与数值；已排轮次中的待赛、轮空和已完成结果全部列出。尚未生成的轮次不虚构配对。玩家姓名用 8.7 的 `PlayerName` 入口清理，报名编号保留，源赛事的原始姓名不变。

CLI 的 `--tournament-report <赛事文件> [--json]` 是独立只读查询，可额外使用 `--pack`、`--pack-dir`，省略 `--pack` 时读取赛事内保存的包。输出只写标准输出，不包含账号、设备、网络信息、文件路径或导出时间。缺少赛事文件时失败，不创建空赛事。内容包和内容指纹须与赛事相符；下架策略继续生效。

自动赛事将每场实际完成的 `Battle` 通过 `ReplayLibrary.SaveTournament(t, pairing, battle)` 保存到 `<赛事文件完整路径>.replay-library`，先归档再保存比分。手动录入比分不凭空生成录像。归档失败时仍保存已完成比分，CLI 提示失败并返回非零退出码。赛事录像不更新普通玩家档案；转移完整赛事时同时复制 JSON 文件和同名旁库目录。报告读取使用 `ReplayLibrary.OpenReadOnly()`，不会创建目录、锁、索引，也不修复索引或裁剪录像；缺库等同无归档。读取遇到真实权限或路径错误时失败，不把它冒充为缺失录像。

录像库版本 1 的 `library` 元数据可增加 `tournament: {version: 1, key: string, pairingId: int}`。普通录像不增加此字段，赛事 JSON 仍为原版本 1 的确定性格式，不加入时间或随机标识。`key` 是域前缀 `StreamDuel.TournamentArchive.v1\n` 加规范配置 JSON 的 UTF-8 字节的 SHA-256 小写十六进制：配置依次含 `version`、`format`、配置的 `rounds`、`packId`、`contentHash`、按报名顺序的 `players`（`id`、原始 `name`、`teamCode`）。不含比分或已排轮数，因此续赛关联不变；它是库内配置关联键，不是全球唯一赛事编号，相同配置的独立赛事应使用独立旁库。

归档验证对阵归属、已完成状态、包与指纹、原始双方姓名和队伍顺序、已报结果的一致性。写锁内相同关联和相同记录重试返回原 id，不重复保存；不同或不可用的既有记录拒绝覆盖。自动添加赛事备注，沿用有备注录像不被普通容量裁剪的规则。修改备注保留关联。报告只接受显式关联，不按种子、姓名或文件时间猜测；重复关联标为不明确，不任选一份；归档重试发现多份关联也拒绝返回成功，不改写任何一份录像。可识别关联但损坏的记录保留 id 和失败状态；关联标签或 JSON 本身无法识别时，不能归入某场对阵。

数据之最只取已报比分、关联唯一、内容兼容且完整重放后的胜负一致的录像。缺失、损坏、下架、内容不符或重放失败的对局均不补零，并公布统计覆盖范围；`lib=null` 等同无录像库。最高单次伤害是所有正 `Damage.Amount` 的最大值，即实际扣血，包含固定伤害、持续伤害、反弹和自伤。其 `side`、`slot` 与主播指向**受击者**，不推断施伤者；同值按对阵编号、日志顺序取首。最多击倒沿用 `BattleSummary` 的既有归属，跨双方、跨局按主播 id 累加；出场按每局每方实际 `Enter` 的主播去重，未登场替补不计，同一主播在镜像双方都登场计两局次。这两项同值按主播 id 的 Ordinal 顺序取首。没有有效录像或某指标没有正值时，该指标为 null。

战报 JSON 字段如下；列表按积分榜顺序、轮次/对阵编号顺序输出，固定字段顺序和不依赖区域设置的数值格式保证相同输入逐字节相同：

| 字段 | 含义 |
|---|---|
| `version`, `packId`, `format` | 战报版本 1、内容包 id、`roundrobin`、`swiss`、`single` 或 `double`。 |
| `roundCount`, `playedRounds`, `isFinished` | 配置对应的总轮数、已排轮数（可能仍有待赛）、是否结束。淘汰赛未结束时前者为上限，结束后为实际轮数。 |
| `standings[]` | 每项含 `rank`（从 1 开始）、`player`（报名编号）、过滤后的 `name`、`points`、`opponentPoints`、`headToHeadPoints`、`wins`、`draws`、`losses`、`byes`。 |
| `rounds[]` | 每项含 `number`（从 1 开始）和 `matches[]`。 |
| `matches[]` | 每项含 `pairingId`、`player0`、`player1`、`name0`、`name1`、`winnerSide`、中文 `result`、`replay`；轮空的 `player1/name1` 为 null，待赛的 `winnerSide` 为 null，平局为 -1。其余玩家、对阵编号从 0 开始。 |
| `replay` | `status`、`id`、中文 `message`。状态为 `saved`、`not_saved`、`unavailable`、`corrupt`、`mismatch`、`ambiguous`、`not_applicable` 或 `pending`；有唯一可识别关联时保留库 id，即使不可复算，否则 id 为 null。`not_saved` 提示“未保存”。 |
| `coverage` | `completedGames` 为已报非轮空局数，`archivedGames` 为可严格复算局数，`missingGames` 为未保存局数，`invalidGames` 为其余不能用于统计的已报局数；后三项之和等于第一项。 |
| `maxDamage` | null 或含 `amount`、`pairingId`、`round`、`turn`、`logIndex`、`side`、`slot`、`streamerId`、`streamerName`、`replayId` 的对象；日志、方、号位从 0 开始。 |
| `mostKos`, `mostAppearances` | null 或含 `streamerId`、`streamerName`、`count` 的对象；count 为累计击倒次数或出场局次。 |

### 12.2 单败与双败淘汰赛

赛制字符串为 `single`、`double`，也可使用常量 `Tournament.SingleElimination` / `DoubleElimination`。两者的构造参数 `rounds` 必须为 0；赛程由人数和比赛结果决定。`TournamentOptions` 仅用于淘汰赛，字段为可空 `Seed`（uint）、可空 `SeedOrder`（报名编号列表）、`ResetFinal`（默认 true）。`Seed` 和显式顺序互斥；构造时复制选项与列表，调用方之后修改原对象不改变赛事。第一轮排程前，显式顺序必须恰好包含全部报名编号一次；不完整或越界时拒绝且不生成赛程。未指定种子或顺序时，以报名顺序作为种子顺序。指定 `Seed` 时，在报名编号自然顺序上用与 Battle 相同的 Core `Rng` 做 Fisher–Yates 确定性洗牌，独立于各场对战的随机流；不读取时钟或使用系统随机数。

设人数为 N，补到最小的二次幂 M。固定种子槽从 `[1,2]` 逐层把每个 s 展开为 `[s, 2m+1-s]`（m 为展开前槽数），8 槽为 `[1,8,4,5,2,7,3,6]`。大于 N 的种子为空位，所以首轮 M−N 个轮空恰好属于排名最高的 M−N 位种子；5 人时前三种子轮空，第四对第五。单败每轮相邻胜者晋级，一次实际失利即淘汰，直到一名冠军；4/5/8 人分别进行 2/3/3 轮，实战场数始终为 N−1。

双败采用固定胜者组、败者组依赖图，避免按当前输场数临时重新配对。胜者组首轮相邻两场的败者进入败者组首轮；以后每个胜者组轮次的败者注入败者组相应轮，与前一败者组轮的胜者交叉配对（多场时相邻交换注入位置，只有一场时直接配对），随后败者组相邻胜者再合并。胜者组首败只进入败者组一次；败者组失利为第二败并出局。依赖图的零人节点直接传播空位，不制造一场无人比赛；单人节点显示轮空，自动晋级，不制造败者或失败次数。2 人双败没有单独败者组比赛，胜者组败者直接成为总决赛的败者组选手。

总决赛固定由 0 方胜者组冠军对 1 方败者组冠军。0 方获胜即夺冠；1 方获胜且 `ResetFinal=true` 时，双方各有一败，按相同方位再打一场重置总决赛，胜者夺冠。`ResetFinal=false` 时总决赛一场结束，败者组选手不需要再赢第二场；此时原胜者组冠军可能仅一败便获得亚军，是关闭重置的明确例外。默认重置开启的 8 人双败共有 14 或 15 场实战，除冠军外每人恰有两败。

全赛事的 `Round` 是排程批次：在一批全部报分后，把固定拓扑顺序中前置结果已确定的对阵一起排入下一批，所以同批可能同时有胜者组和败者组比赛。`Pairing.Bracket` 为 `single`、`winners`、`losers`、`final`、`reset`，`BracketRound` 为组内从 1 开始的轮次；旧两赛制保持 null/0。`NextRound()` 在当前批仍有待赛时返回原对阵，不推进。`Rounds` 在未结束时表示批次数上限（k=ceil(log2 N)，单败 k，双败 2k 加可选重置的一批），结束后等于实际 `Round`；`IsFinished` 根据最终节点结果判断，不靠固定轮数猜测，`Champion` 是冠军报名编号或 null。

当前 T-54 尚未合并，因此 `BestOf` 固定为 1，未提供三局两胜配置。淘汰赛 `ReportResult` 只接受 0/1；-1 平局中文拒绝且保持待赛，不按种子或积分任意判晋级。`SaveTournament` 也在任何写入前拒绝淘汰赛平局，避免错误关联占用该对阵的决胜录像位置；旧两赛制仍可保存平局。CLI 手动录入遇平局时提示完成有胜负的重赛后报分；自动对局平局则保持待赛、返回非零，保留已完成场次，不把平局归档为该对阵的决胜录像，也不使用相同种子无限重赛。本次不规定自动加赛次数或新种子规则。

淘汰赛的 `Standings()` 按最终冠军、仍在赛者、淘汰批次从晚到早排列；同阶段按初始有效种子顺序。原有胜/平/负/轮空/积分字段仍由真实历史计算，但积分不决定淘汰赛排名；轮空仍单列，不算实际失利。战报使用此排名并显示组别、组内轮次、冠军和总决赛重置状态，不把败者组累计胜场更多误当成冠军。

淘汰赛事保存为版本 2，根字段在原版基础上增加 `seed`（uint 或 null）、`seedOrder`（原始显式顺序或 null）、`resetFinal`（bool）；每个对阵增加 `bracket`、`bracketRound`。恢复时根据配置与此前结果重新构造依赖图，逐项核对实际对阵、组别、轮次和结果，不信任外部缓存的晋级者；部分报分、待赛、总决赛与重置阶段均可继续。循环赛/瑞士轮仍输出原版本 1 的相同字段与字节，版本与赛制不匹配时拒绝。

淘汰赛的录像关联键使用域 `StreamDuel.TournamentArchive.v2\n`，规范配置的 version 为 2，并在 format 后加入 seed、seedOrder、resetFinal，其他配置与 12.1 相同；不同种子或重置配置不串档。旧赛制的 v1 关联键保持不变，录像元数据标签仍为版本 1。淘汰战报 JSON 在原战报字段外增加根 `resetFinal`、`bestOf: 1`、`champion`（报名编号或 null）；每个 match 增加 `bracket`、`bracketRound`。旧两赛制不输出这些附加字段。

CLI 使用 `--tournament <文件> --format single|double` 创建相应赛事；也可在交互菜单选择。省略 format 继续已有赛事时使用存档赛制；显式指定不符时拒绝，不能借续赛转换赛制。CLI 新建采用报名顺序和开启重置，Core 创建者可通过 options 指定种子、顺序或关闭重置。`--format` 不用于战报查询，查询直接读取存档。
