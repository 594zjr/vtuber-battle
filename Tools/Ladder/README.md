# 天梯模拟

从仓库根目录运行（.NET 8）：

```powershell
dotnet run --project Tools/Ladder -- --pack original --teams 64 --rounds 10 --seed 1 --out ./ladder_out
dotnet run --project Tools/Ladder -- --pack original --teams 16 --rounds 3 --seed 1 --season s1 --level hard --out ./ladder_out
```

默认 64 支队伍、10 轮、种子 1、普通难度，输出目录为当前工作目录的 `ladder_out`。`--pack` 选择内置包 id，也兼容内置文件名；`--season` 可省略。`--help` 查看参数范围。`--level` 同时控制行动和补位策略。

## 阵容与配对

- 每队 6 位且不重复，最终通过 `TeamCheck.Validate`。前 `floor(teams / 2)` 队由 `TeamBuilder.Suggest` 自动组队，第 `i` 队（从 0 开始）的组队种子为 `unchecked(seed + i)`；其余队伍从按 id 排序的名单开始，用指定种子的独立 `System.Random` 打乱候选，再有限回溯满足赛季禁用和所有限制池。奇数队伍时随机阵容多一队。无合法六人阵容时报告中文错误。两种阵容随机数均与每场对战的 `Battle.Rng` 分离。
- 阵容是有序的六个号位，首发和第六位会影响对战。不同参赛队允许抽到同一阵容，仍保留独立的 `team_id`；不要求内容包提供足够多种不同组合。
- 每局胜 1 分、平 0.5 分、负 0 分。每轮开始按积分降序、队号升序排列；先为最高分未配对队伍选择交手次数最少、积分最接近的对手，同分按队号。整轮配对先冻结，再依次比赛。重复对局无法避免时仍可继续任意轮数。
- 奇数队伍时，优先让轮空次数最少、积分最低的队伍轮空，同分取队号较大的。轮空获得 2 分，但不计胜场、对局、出场或 Elo。
- 每对打两局，第二局交换双方位置，不改变队内号位，也不覆盖 Core 的先手规则。全赛事第 `g` 局（从 0 开始）的种子为 `unchecked(seed + g)`，两局使用不同种子。每场都通过 Core 结算至结束。

## Elo 和出场口径

初始 Elo 为 1500。每对两局共用赛前期望 `E = 1 / (1 + 10^((对手 Elo - 本方 Elo) / 400))`；每局 K=24，两局合计变化为 `24 × (两局总得分 - 2E)`。双方增减互为相反数；同实力各赢一局或两局均平不会因先处理哪局而产生净变化。全体参赛队的 Elo 总和保持 `1500 × 队伍数`。

主播的出场加权 Elo 为 `Σ(参赛阵容最终 Elo × 该主播在此阵容实际上场局数) / 总上场局数`。一局内多次换入只算一次；开场、主动换人和补位均算上场，立即被击倒也算。未上场的后排只记 `roster_games`，不参与加权；从未上场者的 `weighted_elo` 为空。该值反映抽样阵容及所选 AI 下的结果，不等同于主播单独贡献。

## 输出

输出为 UTF-8、无 BOM、LF 换行，数值用固定小数点。每次成功运行覆盖输出目录中的以下两个文件；不会修改规则或内容包。

- `teams.csv`：按 Elo 降序、积分降序、队号升序排序。`slot1`～`slot6` 为有序主播 id；`games/wins/draws/losses` 为真实对局统计，`byes` 为轮空次数。
- `streamers.csv`：按出场加权 Elo 降序、id 升序排序，未上场者在最后。`appearances` 是实际上场局数，`roster_games` 是入选阵容局数，`wins/draws/losses` 只统计实际上场对局。`damage_dealt/kos/turns_active` 累加自 `BattleSummary`；`turns_active` 仅统计到达回合结束节点时的在场次数，可能不包含提前终局的最后一回合。

控制台打印两份榜单的前十名。同一引擎与内容版本、同一组参数的两份 CSV 和控制台输出完全一致；输出不包含时间或绝对路径。CSV 排名使用未舍入值，展示的 Elo 保留六位小数。

验收规模为 `--teams 16 --rounds 3`，共 48 局；可将输出写入 `Tools/Ladder/obj/` 下以免生成文件混入提交。

自动验收：`pwsh -NoProfile -File Tools/Ladder/verify.ps1`（PowerShell 7）。脚本构建 Release，检查两次 CSV 与控制台字节一致、耗时、赛季合法性、积分和 Elo 守恒、登场统计、奇数轮空、困难模式和无效参数，并将日志及报告保存在 `Tools/Ladder/obj/verification/` 的独立子目录，不删除已有结果。

## 禁用与首发策略配对比较

```powershell
dotnet run --project Tools/Ladder -c Release -- --compare-openers --blocks 250 --pack original --seed 1 --out Tools/Ladder/obj/t90-comparison
```

`--compare-openers` 只改变禁用和首发策略：新策略调用带 `Hard` 的 `Ai.ChooseBan/ChooseLead`，旧策略调用 `Normal`；双方每回合出招与补位始终使用 `Hard`。每场同时开启禁用和首发。可设置 `--pack`、`--season`、`--seed`、`--out`，不能混用普通赛事的 `--teams`、`--rounds`、`--level`；`--blocks` 只用于比较模式，默认 250，范围 1..536870911。该模式与 `--ai-regression`、`--compare-expert`、`--compare-styles` 互斥，也不接受回归专用的 `--games`、`--baseline`、`--write-baseline`。

先用原有 `TeamGenerator.Generate(db, season, 2 * blocks, seed)` 生成阵容。第 `i` 组从前半取得建议阵容 A，从后半取得随机阵容 B。每组依次运行四局：

| 局内顺序 | 0 方 | 1 方 |
|---|---|---|
| 1 | A / 新策略 | B / 旧策略 |
| 2 | B / 旧策略 | A / 新策略 |
| 3 | A / 旧策略 | B / 新策略 |
| 4 | B / 新策略 | A / 旧策略 |

第 `i` 组（从 0 开始）的四场共用 `unchecked(seed + i)`，不改变队内原始顺序。两种策略都使用两套阵容、都处于两侧；默认 1000 局中新策略在 0 方、1 方各 500 局。每个阶段按 0 方、1 方顺序调用 AI；禁用/首发先收集双方决定再提交，不向第二方泄露第一方选择。不新增随机源、不回退或重置 `Battle.Rng`，阵容随机性只来自原有生成器。默认预先固定 `seed=1`，不能按结果挑选种子或删除失败场次。

输出 UTF-8、无 BOM，不含时间：

- `opener-games.csv`：每场的组号、方向、种子、新策略所在方、双方原始有序阵容、双方禁用的对手 id、双方首发 id、胜方、新策略结果、已结算回合数和终局哈希。`turns` 按录像里的 `Turn` 事件计数，与 `BattleSummary.Turns` 一致，补位阶段本身不增加回合数。
- `opener-records.jsonl`：与 CSV 数据行顺序一致，每行是一场完整 `BattleRecord`，含原始阵容、种子和全部决定。每场写入前经过 JSON 往返与 `Replay.Run`，核对终局、哈希及逐行日志。
- `opener-summary.json`：完整配置、内容指纹、计划/已完成局数、回放验证数，以及新策略处于 0 方、1 方和总体的胜平负、胜率及目标是否达到。

严格胜率为 `胜 / 总局数`，平局仍计入分母；同时单列 `(胜 + 0.5 × 平) / 总局数`，不把两者混用。目标为总体严格胜率至少 50%，结果不足照实输出，不改变战斗规则，不把低胜率当作工具运行异常。Core 按 120 回合上限正常裁决的终局计入结果；超出安全上限但仍未终局则报 `unfinished`、退出失败并保存 `status=failed` 的已完成汇总，未完成对局不算平局或完成场次。

自动验收：`pwsh -NoProfile -File Tools/Ladder/check-openers.ps1`；已有 Release 构建时可加 `-SkipBuild`。脚本用独立程序副本运行两次八局，核对配对、种子环回、赛季阵容、禁用/首发、真实 JSON 回放、回合与胜率统计、文件字节一致性、参数互斥及下架门禁；证据保存在 `Tools/Ladder/obj/opener-verification/`，不会替代完整 1000 局的强度验收。

## 电脑强度回归

```powershell
dotnet run --project Tools/Ladder -c Release -- --ai-regression
dotnet run --project Tools/Ladder -c Release -- --ai-regression --pack original --games 100 --seed 1 --baseline docs/ai-baseline.json
dotnet run --project Tools/Ladder -c Release -- --ai-regression --games 20 --seed 1 --write-baseline Tools/Ladder/obj/ai-baseline-candidate.json
```

`--ai-regression` 调用 Core 的 `AiRegression.Run`，比较简单、普通、困难、专家四档难度的全部六种配对。默认原创包、每对 100 局、种子 1；`--games` 必须为大于零的偶数。每组先从按 id 排序的名单随机抽取两支六人阵容，保持队内号位与对战种子不变，再交换双方难度打第二局；六种难度配对使用相同的阵容样本。随机数来自 `Battle.Rng`，技能先手顺序仍由 Core 正常结算，换边不会强制某档难度先行动。无赛季限制、禁用或选首发流程；每局使用引擎现有回合上限，达到上限也按 Core 的既有规则结算胜负。

控制台输出行对列的胜率矩阵与每对难度的胜、负、平、未完成数量。胜率为胜场除以总局数，平局不折算半胜；同档难度没有实际对战，以 `—` 显示。未完成指保护性步数上限结束时仍未终局的异常情况，数量包含在平局中；任何未完成对局均判回归失败。

默认基准由 `docs/ai-baseline.json` 复制到构建输出目录，运行时与当前工作目录无关；也可用 `--baseline` 指定已有文件。基准记录内容包、内容指纹、局数、种子、回合上限、采样版本、六组实测计数以及允许下降幅度。比较要求内容包、局数、种子、回合上限、采样版本一致；内容指纹变化时提示后继续比较，以便发现修改规则或内容后的退步。参数或文件错误、任一高难度对低难度胜率不大于 50%、任一高难度胜率比基准下降超过允许幅度（默认 5 个百分点）、任一未完成对局，均返回退出码 `1`。全部通过才返回 `0`，所有失败项逐条输出，不因其中一项失败而隐藏其余结果。

`--write-baseline` 明确指定并覆盖一个输出文件，创建其父目录，写入本次实际测得的数据；不读取旧基准，也不比较历史下降。难度顺序或完整对局要求未达标时仍保存实际结果并返回 `1`，避免把测得的失败改成成功。建议先写到 `obj/` 下作为候选，审查测量结果后再决定是否替换仓库基准；生成命令本身不代表接受这套难度强度。该选项与 `--baseline` 互斥。

回归模式只接受 `--pack`、`--games`、`--seed`、`--baseline` 或 `--write-baseline`，不能混用普通天梯的 `--teams`、`--rounds`、`--level`、`--season`、`--out`。回归专用参数也不能单独用于普通天梯。完整每对 100 局检查较慢，不在 CI 中运行；单元测试使用每对 20 局的小样本。

`pwsh -NoProfile -File Tools/Ladder/verify-ai-regression.ps1` 检查帮助、参数互斥、损坏或不匹配的基准、默认基准加载、每对两局的真实计数与退出码，以及旧天梯模式仍可输出 CSV。真实样本按其计数核对判定，不要求 AI 必须输；另外使用确定的统计夹具检查全胜通过、难度顺序失败、历史下降失败和未完成失败。它不会重复执行完整强度测量。已经构建 Release 时可加 `-SkipBuild`，日志保存在 `Tools/Ladder/obj/ai-regression-verification/` 的独立子目录。

## 专家预算比较（T-108）

`--compare-expert` 是独立模式，不修改前述天梯默认行为。使用 Release 构建，计时期间不要并行运行其它实验：

```powershell
dotnet run -c Release --project Tools/Ladder -- --compare-expert --compare-mode paired --games 300 --seed 1 --out Tools/Ladder/bin/expert-paired
dotnet run -c Release --project Tools/Ladder -- --compare-expert --compare-mode hard --games 300 --seed 1 --out Tools/Ladder/bin/expert-hard
dotnet run -c Release --project Tools/Ladder -- --compare-expert --compare-mode both --games 300 --budget 128 --workers 4 --seed 1 --out Tools/Ladder/bin/expert-both
```

默认模式为 `paired`、`games=300`、种子 1、预算为 Core 的 `ExpertBudget.DefaultMaxNodes`（当前 128），输出目录默认 `ladder_expert_out`。`--budget` 可取 0～2147483647；无限专家使用 `ExpertBudget.Unlimited`。比较固定使用原创包，显式 `--pack original` 也可；不接受 `--teams`、`--rounds`、`--level`、`--season`。双方均无禁用、首发选择或规则修饰器。

`--workers` 可取 1～16，默认 1。样本之间可以并行，每个样本内仍按下述顺序完成全部对局。各样本单独持有对战、节点计数和耗时，结束后按样本编号合并并重排全局 game id；改变工作线程数不会改变 `comparison.json` 或 `games.csv`。工作线程数只记在 `timings.json`，不参与确定性报告。

`--games` 始终表示配对样本（fixture）数量，而非总场数。每个样本包含有序的两支六人队伍和一个对战种子，先生成全部样本，再开始比赛。名单按 id 的 ordinal 顺序排列，使用独立的项目 `Rng(seed)` 逐队做 Fisher–Yates 打乱并取前六位，再从同一随机流抽取完整 uint 对战种子；每队都通过 `TeamCheck.Validate`。同队无重复、两方可以有相同成员。阵容生成不使用系统随机数或时间，也不受专家搜索消耗影响。所有比较模式使用完全相同的样本生成方式。

- `paired`：每个样本打两局，队伍、队内号位和种子保持原样；第一局预算专家在 side 0、无限专家在 side 1，第二局仅交换专家策略。默认总计 **600 场**，两种专家各在 side 0、side 1 打 **300 场**。各自得分率为 `(胜 + 0.5 × 平) / 600`，另列相对 50% 的百分点变化。这里的“各 300”指各侧场数，不能解读为总共只有 300 场。
- `hard`：每个样本让预算专家和无限专家分别对共同的困难电脑打一局，两局使用相同队伍、种子及专家所在位置。专家位置按样本交替，第一份在 side 0、第二份在 side 1；默认每种专家 **300 场**，各侧 150 场。直接报告各自胜率、得分率，以及 `无限专家胜率 − 预算专家胜率` 的下降百分点。负数表示预算专家更高；是否不超过 3 个百分点按胜场整数差判定，避免浮点边界误差。
- `both`：对每个样本先执行两场 `paired`，再执行两场 `hard`，默认总计 **1200 场**；两组结果分别统计。单独运行和合并运行的同一组样本及对局结果一致，合并运行中的全局 game id 不同。

胜率定义为 `胜 / 全部场数`（包含平局分母），得分率另计平局半分。两种指标分别报告，不把直接交手的相对 50% 得分变化等同于共同困难对手的胜率下降。双方始终先 side 0 后 side 1 选择行动，补位也按 0、1 顺序；使用 Core 的真实结算，不共享对手的待选行动。搜索和对战只使用 `Battle.Rng`，计时只用于实验报告，不影响预算、行动或停止条件。

成功运行覆盖输出目录中的三个文件，均为 UTF-8、无 BOM：

- `comparison.json`：比较协议编号、参数、内容指纹、Core 程序集 SHA-256、样本 SHA-256、全部队伍/种子、逐局胜方/回合数/最终状态哈希/录像 SHA-256，以及各组胜负平和百分点统计。节点摘要按双方记录模拟节点总数、单次最大节点、行动/补位决策数及分别耗尽次数；汇总也保留相同口径。困难电脑不走预算接口，其专家节点与决策统计为零。
- `games.csv`：每局一行，保留模式、样本编号、两队 JSON、种子、策略所在侧、胜方、实际 Turn 事件数、双方节点及耗尽摘要、状态哈希和录像 SHA-256。队伍 JSON 放在标准 CSV 引号单元格内。
- `timings.json`：独立保存工作线程数、总耗时和逐局耗时。单局包括构造对战与选招/补位/结算，总耗时还包括样本生成、逐局摘要计算和结果合并，不含写文件。并行时单局耗时之和不等于总耗时，也不能作为独占运行的 Bench 延迟；耗时受机器负载影响，不属于确定性结果。

默认 `games=300`、种子 1、普通难度、输出目录 `ladder_styles_out`。这里 `--games` 表示**每组的实际场数**，必须是至少 2 的偶数；默认有风格组 300 场、无风格组 300 场，共 600 场、150 个配对样本。可指定 `--level hard`，但两组及其对手始终使用同一难度，结果分开解释；普通、困难电脑各自沿用 Core 既有的风格流程。可选 `--pack` 只接受 `original_wave3`；拒绝其它模式、天梯专用参数、未知及重复参数。小样本可用于运行检查，不能作为正式验收。

赛程先冻结再开始对局：十二位 `og3_` 主播先按 id 的 ordinal 顺序排序，每个样本从此名单出发，使用独立 `Rng(seed)` 做 Fisher–Yates 洗牌，前六位为目标队、后六位为对手队，双方互不重叠且每队通过 `TeamCheck.Validate`；再从同一抽样随机流取得完整 uint 对战种子。每个样本的两局保持队内号位和种子，目标队分别在 side 0、side 1；有风格与无风格两组使用完全相同的阵容、侧别和种子。双方无赛季、禁用、首发选择或修饰器；每次行动和补位按 side 0、side 1 顺序调用 Core AI，并由 Core 结算到终局。

- **有风格组**：只有目标队六位主播保留内容包的 `AiStyle`，对手六位清空风格。
- **无风格组**：双方十二位都清空风格。目标队仍为相同的六位和同一侧别，以此计算基线。
- 每一局从输入 JSON 独立载入数据库，在创建 `Battle` 前完成风格屏蔽并调用 `Validate`，不在对战中修改配置；不改文件、技能、人设、数值或规则。每次载入核对原内容指纹，内容中途改变则拒绝继续。对局随机数仅来自各自 `Battle.Rng`。

统计只看**目标队**。胜率为 `胜 / 全部场数`，得分率为 `(胜 + 0.5 × 平) / 全部场数`，平局均保留在分母。分别列出 `无风格目标队胜率 − 有风格目标队胜率` 和得分率的下降百分点；负数表示有风格更高。验收门槛针对真实胜率，按整数条件 `(无风格胜场 − 有风格胜场) × 100 <= 每组场数 × 3` 判断，避免小数边界误差；不会把双方合并成恒为 50% 的全体得分率。`AcceptancePassed` 还要求每组至少 300 场、十二位主播均在有风格目标队中出现；覆盖记录是入队次数，不等同于实际上场次数或单个主播的独立贡献。若正式规模的冻结赛程覆盖不足，程序报错，不自动换种子重抽。
